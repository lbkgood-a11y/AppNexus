# 附件租户系统配置迁移检查

2026-11-27 · 变更范围为租户「系统配置 → 附件配置、附件管理」

`V223` 注册两项租户菜单，停用平台菜单，新增租户策略表和三个独立权限。旧规则作为冻结的初始值，规则第一次保存时才写入本租户行。台账列表、总数和下载按可信租户定位，原件及原有附件记录无需搬迁。新版本后端与新导航同步上线，旧平台 API 随之退役。

## 声明同步复核

| 项 | 实施与证据 |
| --- | --- |
| D01 | 复用配置域的 `AttachmentUploadPolicy` 和 `ManagedAttachment` 两个 Provider，分别由 V1 升为 V2、V2 升为 V3。 |
| D02 | 保留策略查看、修改及附件规则、本人列表、上传、台账和下载的操作身份。 |
| D03 | 两菜单正式路由为 `/configuration/attachment-policies` 和 `/configuration/attachments`，Controller 绑定原操作并开启统一前置权限。 |
| D04 | 策略查看、修改和台账读取改为独立租户权限。系统租户管理员按原角色授予方式补齐能力，平台授权不转入租户。 |
| D05 | 台账和计数使用同一可信租户谓词，下载额外核对可用状态。策略表各租户各类型唯一，规则读取与更新绑定相同租户。 |
| D06 | 租户台账省略原件对象地址的有效值。客户端不传租户或原件路径，信任边界在服务端。 |

| D08 | 规则依然使用文件类型、字节数、启停和版本契约。台账不再接受租户筛选，已登记的附件 ID 不变。 |
| D09 | 没有发号语义。独立规则记录使用服务端 UUID。 |
| D10 | 上传策略查询与实际上传共用当前租户规则。台账按钮通过对应租户 API 执行查询、上传和下载。 |
| D11 | 版本 0 代表尚未独立修改的初值，首次保存创建版本 1 并以唯一约束处理竞争，后续更新以租户、格式与版本匹配。历史规则和附件保留，未给历史初值伪造租户审计。 |
| D12 | 用例覆盖规则独立性、乐观锁、无权限、隔离台账和跨租户下载，执行结果见下表。 |

- 后台类型检查、Vite 生产构建、前端操作绑定检查及定向差异检查通过。
- 默认后端构建目录通过全仓权限门禁，测试编译因其他模块的 `DataGrantPolicySupport.class` 无法解析而停止。使用独立构建目录重新编译及测试，不修改权限门禁或例外。
- 首次隔离验证在 MySQL 8.4 应用全部 223 个迁移后发现数据目录拒绝同一对象中两个无父资源的根。已将台账复用到附件资料根资源，权限仍独立为 `configuration.attachment:ledger`，以修正后的 V223 重新验证。
- 修正后的 V223 通过全量迁移。隔离应用启动，`AttachmentManagementTest` 的上传幂等与跨租户下载用例通过。策略用例实际响应已显示第二租户 PNG 初值保持启用且版本为 0，原 JSONPath 断言未取到该字段，已改为检查实际返回项并单独复跑完整用例。
- 策略及台账隔离复跑通过，1 项测试无失败或跳过。环境应用 224 个迁移，其中包含同期的 V224。用例验证改动当前租户 PNG 规则后另一租户仍启用，实际上传规则接口使用各自配置，并核对列表范围、计数、权限、CSRF 和陈旧版本拒绝。日志位于 `.local/tenant-attachment-policy-retest.log`。
