# 审批服务详细设计

日期：2026-11-09。状态：工程边界与组合部署方式已确认；本次建立可编译骨架，审批业务功能待实现。

## 1. 已确认的架构

审批服务位于 backend/services/approval-service，与 platform-service 平级。
初期由 platform-service/application 的既有 PlatformApplication 显式装配，同一 JVM 运行，
不搬迁启动路径、不增加端口。启动模块是引用双方实现的唯一例外。
未来独立运行时新增审批启动装配即可，不将平台实现依赖带入审批核心。

Flowable 内嵌于审批服务，属于内部执行引擎，不另行部署 Flowable REST 应用。
仅 adapters/flowable 允许引用 org.flowable；core 不引用框架。
跨服务入口使用 contracts/approval-contracts，不暴露引擎实体或领域内部对象。
现阶段不为尚未实现的 HTTP、持久化、组织适配创建空模块。

## 2. 工程与依赖

```text
backend/contracts/approval-contracts
backend/services/approval-service
├─ core
├─ adapters/flowable
└─ architecture-tests

platform-service/application → approval-flowable-adapter → approval-core → approval-contracts
```

组合启动不授予平台领域访问审批内部实现的权利。架构测试约束：

- 审批实现不得依赖 com.appnexus.platform 下的实现。
- 平台代码除 PlatformApplication 外不得引用审批实现。
- 审批核心与公共契约不得依赖 Spring、Flowable 或适配器。
- 只有审批 Flowable 适配器允许直接引用引擎。
- 公共契约不得暴露双方实现。

Maven 编译依赖限制核心的可见范围；ArchUnit 检查组合应用类路径上的代码访问。
这属于构建期约束，不是 JVM 安全隔离，也不防止反射、动态 SQL 或人为绕过测试。
未来新增跨服务接口须评审事务、错误、权限与幂等语义，不因同进程省略校验。

## 3. 引擎装配与配置

锁定 org.flowable:flowable-spring:8.0.0，不使用自动开启多个子系统的 Boot Starter。
引擎名称 appnexus-approval。初期复用平台数据库连接池和事务管理器，
引擎表与未来审批业务表归审批服务所有，其他服务不得直接访问。
运行时禁止自动建表或自动升级；版本匹配和引擎表由受控迁移负责。
异步执行器固定关闭；后续完成租户上下文、线程池隔离和失败恢复后再增加配置。
不开放原生 Flowable REST 接口、任意脚本、表达式或 Java 类配置入口。

| 配置项 | 环境变量 | 默认值 | 用途及生效约束 |
| --- | --- | --- | --- |
| app.approval.engine.enabled | APP_APPROVAL_ENGINE_ENABLED | false | 是否装配内嵌引擎；仅表迁移完成后可启用，缺表时启动失败；不启用审批业务接口或后台执行器 |

Flowable 使用 Apache-2.0；后续引入设计器与其他依赖须单独核查许可证。
编译与容器测试只证明当前验证范围，不代表全部引擎能力或升级路径已验收。

## 4. 业务与安全约束

延续既有审批默认规则：按单据归属组织选人；空审批人暂停并告警；默认不允许自审；
支持会签、或签、依次审批；转交、委托、加签分别授权；退回目标受流程限制；
撤回同时检查审批进度和业务生效状态；超时不自动通过。

任务分配记录不能替代平台授权。审批应用入口必须重新校验可信身份、租户成员资格、
任务所有权、字段范围及强制脱敏。任务结束收回处理权限，历史查看受租户策略约束。
ApprovalContext 只是显式调用上下文，不是认证凭证，也不自动完成幂等处理。

审批服务维护审批事实，业务服务维护单据状态。后续通过可靠事件、幂等和对账衔接，
不得依赖跨服务本地事务；当前未实现审批 Outbox、回调或状态推进。

## 5. 设计器与前端边界

前端功能归 frontend/modules/approval，复用 vue-pure-admin、Element Plus 与平台公共组件。
本次不创建空前端包或无效菜单入口。
优先简化审批设计器，前端编辑带版本的审批 JSON；后端负责校验、编译为 BPMN 并发布。
高级 BPMN 编辑器按需要引入成熟内核；不承诺任意 BPMN 与简化模型双向无损转换。
发布时保留 JSON、BPMN 与策略快照；不允许编辑已发布定义悄悄改变历史。

选人、条件字段、流程发布权限均由后端契约约束，不直接开放引擎部署能力。
现有组件不适用而新增审批专用组件时，须记录需求、已检查组件及具体原因。

## 6. 后续实施顺序

1. 定义单据接入、发起与任务处理契约，确定业务状态、幂等和失败语义。
2. 建立受控引擎迁移与审批业务表；验证升级、备份和恢复。

5. 交付统一工作台、简化设计器、版本发布，再扩展加签、退回、委托及催办。

工程骨架完成不代表以上能力已实现。
