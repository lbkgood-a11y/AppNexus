# 单据提交行为统一接入

日期：2026-11-12。状态：本次实现说明；替代“提交行为等同发起流程”的旧描述。

## 行为与权限

请假业务在同一个 SUBMIT_ACTION 声明中登记 typeCode=LeaveRequest、actionCode=submit、operationKey=LeaveRequest.submit、中英文按钮名称、权限引用和支持的 DIRECT/APPROVAL 模式。目录与页面动作 API 使用同一声明；页面从 /api/leave-poc/actions 取得按钮文案及 allowed，写入仍重新授权。工作台展示操作标识与权限映射，不配置任意业务 URL。

本批为兼容已有授权，permissionCode 继续引用 workflow:start；它只是授权码，不等于启动流程，不决定提交方式，也未自动给其他用户新增授权。页面不再用工作流 start 能力决定提交按钮。未来拆分单据专用权限需显式迁移，不能通过声明变更偷偷扩权。

## 策略与执行

每个绑定包含 actionCode=submit、mode、条件及可选流程目标。旧 JSON 缺少 actionCode/mode 时分别兼容 submit/APPROVAL。首期只提供 submit 策略解析，其他动作明确拒绝，不提前提供通用执行平台。

- APPROVAL 要求兼容的明确发布流程版本；流程缺失或不可用拒绝，不自动降级。
- DIRECT 必须由代码声明支持，流程标识必须为空、版本必须为 0。业务自行决定目标状态及副作用，工作台不能填写状态值。
- 同条条件 AND，同一提交恰好匹配一条策略；可按条件混合直接和审批模式，无条件绑定不能与其他绑定共存。

用户只点击同一个“提交”按钮，业务 API 验证权限、归属、状态及依据，从存储取值，调用 resolveAction(LeaveRequest,submit)。直接策略将请假标记 ACCEPTED（已受理），保存业务提交记录，不创建工作流或审批轮次；审批策略保留原有实例创建、轮次关联及 SUBMITTED 状态，同本地事务提交。ACCEPTED 不代表 APPROVED。

固定解析结果记录行为与模式。工作流 verify 只接受 APPROVAL，不能用直接提交解析引用发起流程。平台停用在解析时持续检查，既有业务成功重放由业务状态返回，不重复执行。

## 数据与兼容

V63 扩展解析记录，旧记录默认 APPROVAL；DIRECT 允许空流程目标。V64 增加业务 ACCEPTED 状态及 leave_poc_submission 表，记录每对象依据版本的模式和解析 ID；旧审批历史不重写。既有租户绑定保持审批，未自动创建或发布直接策略。

工作台复用 ManagedDialog、Element Plus 表单、Select 和只读行为表，沿用单根布局和主题变量，不增加新 UI 库。后端仍以公开契约接入，单据中心不执行请假操作。

## 验证

真实 MySQL/Flowable 集成测试覆盖原审批链、直接提交不创建实例、重复直接提交去重、直接引用不能启动审批、非法流程目标拒绝、同一 submit 按天数选择直接受理或审批、未知行为拒绝。前端类型检查、生产构建及工作流已有回归按本机 `.local/document-action-*.log` 记录。

本次真实数据库集成测试通过，前端工作流 9 项回归通过，admin 类型检查与生产构建通过；后端组合包构建通过，本地 V63/V64 已执行并成功启动。未替租户改动或发布实际提交策略。

浏览器视觉验收尚未重新执行；此前本地地址访问审批被拒绝。远程 SDK、其他单据行为及专用权限拆分不在本批实现范围。
