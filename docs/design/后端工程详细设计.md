# 后端工程详细设计

版本：0.1；日期：2026-11-05；状态：详细设计草案，待审阅。

## 1. 依据与边界

本文依据[平台总体设计](平台总体设计.md)整理。已确认的是技术方向、领域聚合及行为原则；本文提出的模块名称、接口、表名、事务算法和运行机制为建议方案，不能视为已完成技术验证或获准开始编码。

第一期交付平台底座，不实现 SCM、WMS、巡库业务。前端 vue-pure-admin；后端 Java 21、Spring Boot / Spring Cloud；数据库 MySQL。使用 Maven、MyBatis、Spring Security、Redis、Flyway、Outbox、OpenAPI、结构化日志。确切版本、许可证及兼容性须在工程初始化前核查。

第一期一个平台基础应用，可多实例部署；领域边界不等于物理服务。API 网关、注册中心、配置中心、消息队列不作为启动依赖。审批、单据、编排、打印、报表等后续共享服务仅保留接入边界。

## 2. Maven 工程结构

根工程命名 `backend`，去掉重复的项目前缀，统一管理依赖与插件版本。目录按职责分组，领域名采用简短英文。

```text
backend/
├─ pom.xml
├─ common/                  最小共享类型与基础契约
├─ api/                     公开应用接口、DTO、事件
│  ├─ identity-api/
│  ├─ tenant-api/
│  ├─ org-api/
│  ├─ auth-api/
│  ├─ i18n-api/
│  ├─ config-api/
│  └─ audit-api/
├─ modules/
│  ├─ identity/             账号、会话
│  ├─ tenant/               租户、成员、开通配置
│  ├─ org/                  类型、单元、关系、岗位、任职
│  ├─ auth/                 角色、授权、委派、限制、模板
│  ├─ i18n/                 国际化配置与引擎适配
│  ├─ config/               字典、参数
│  └─ audit/                审计写入与查询
├─ infra/
│  ├─ db/                   数据源、事务、MyBatis 公共设施
│  ├─ security/             Spring Security、请求上下文
│  ├─ event/                Outbox 投递与消费框架
│  ├─ observe/              日志、追踪标识、指标
│  └─ i18n-engine/          统一区域化运行能力
├─ app/                     唯一 Spring Boot 启动和装配模块
└─ arch-test/               依赖、隔离及契约约束验证
```

命名约定：`identity` 表示身份认证领域，`auth` 表示业务授权领域，`security` 表示安全技术适配；三者职责保持独立。契约模块保留 `-api` 后缀，避免与领域实现模块的 Maven artifactId 重名。

### 已确认：工程命名规范

- 根工程使用 `backend`，一级模块采用 `common`、`api`、`modules`、`infra`、`app`、`arch-test`，不重复添加项目前缀。
- 领域使用简短、含义明确的英文名；同一领域在目录、契约和文档中使用同一名称，避免同义词混用。
- 领域契约统一为 `<领域名>-api`，领域实现使用领域名；技术模块按职责命名，不随意增加 `core`、`base`、`manager` 等无明确边界的层级。
- 使用小写命名，多个单词用连字符分隔；Java 包名遵循 Java 规则，不包含连字符。
- 后续新增模块沿用本规范，先明确职责及所属层次，再确定名称；需要例外时在设计文档中说明原因。

模块数量可在实现时合并，但不可消除领域边界。`api` 仅包含公开契约，不是共享实体仓库；`common` 不放账号、组织、角色实体或领域仓储。`infra` 不得依赖领域实现。

### 2.1 依赖方向

- 启动模块依赖领域实现与技术支持，完成装配。
- 领域实现依赖自身契约、最小内核和所需技术支持；跨领域仅依赖对方契约。
- 领域层不得依赖 Spring MVC、MyBatis、Redis 或其他领域实现。
- 跨领域接口通过应用层端口调用，避免实现模块相互引用。
- 组合查询使用专门读接口或投影，不能以报表需要为由跨领域关联业务表。
- 用架构测试验证禁止依赖；模块职责和允许依赖清单纳入仓库规范。

### 2.2 领域内部结构

```text
org/
└─ ...org/
   ├─ interfaces/         HTTP、事件入口及请求响应映射
   ├─ application/        命令、查询、应用服务、端口、事务协调
   ├─ domain/             聚合、值对象、领域服务、事件、仓储接口
   └─ infrastructure/     MyBatis、仓储实现、外部适配器
```

领域对象控制状态转换，应用服务协调流程；Controller 不直接调用 Mapper。持久化对象不作为领域对象或 HTTP 响应。简单字典可简化内部实现，仍保留领域归属和公开接口。

## 3. 领域与聚合落位

| 领域 | 已确认聚合 | 建议数据位置 | 关键约束 |
|---|---|---|---|
| 身份 | 账号、会话 | 平台库；Redis 承担在线会话热状态 | 账号停用全局失效，单会话可撤销 |
| 租户 | 租户 | 平台库 | 状态决定是否可访问、可执行 |
| 租户 | 租户成员、租户开通配置 | 租户库 | 同账号同租户唯一成员；授权不超开通范围 |
| 组织 | 类型、单元、关系、岗位、任职 | 租户库 | 同类型独立树、跨租户禁止、任职不自动授权 |
| 权限 | 角色、授权记录、委派、强制限制、模板 | 租户库 | 来源可追溯、强制限制优先、默认拒绝 |
| 国际化 | 配置与资源，聚合待细化 | 租户库；平台包提供基础语言资源 | 展示偏好不改业务结果 |
| 配置 | 字典与参数，聚合待细化 | 租户库 | 编码稳定、覆盖范围受声明约束 |
| 审计 | 追加记录，聚合待细化 | 平台事件入平台库，租户事件入租户库 | 最小敏感内容、受控查询、不可随意改写 |

开通配置的租户副本不能直接由租户管理员扩大：平台开通操作通过受控流程更新，租户访问由已确认有效版本判定。平台开通指令、状态与租户内生效配置的权威关系须在详细接口设计中锁定。

组织类型是树的边界；一个单元一个类型，同类型上级或直接挂租户根。建议树采用父节点字段和祖先后代索引，由组织领域维护；移动节点需防环、影响分析和并发控制。索引结构尚未锁定。

## 4. 平台库与租户数据库

### 4.0 ID 生成策略（已确认）

- 默认内部标识使用 UUIDv7，由应用创建对象时生成，永久不变；适用于聚合、实体、事件及幂等记录。幂等记录 ID 不替代请求幂等键。
- MySQL 默认使用 `BINARY(16)` 保存 UUID 原始字节，API 使用标准 UUID 字符串，前端按字符串处理。统一转换器须保证字节序一致，不使用面向 UUIDv1 的字节交换方式。
- 生成接口定义在 `common`，领域通过抽象使用，不直接依赖具体生成库；库选择及并发、随机源、时钟回拨行为须验证，不自行拼装算法。
- 各领域可定义有语义的 ID 值对象，跨聚合使用标识引用。
- 业务单号由编码服务负责，与内部 ID 分开；追踪标识遵循 OpenTelemetry 规范。
- UUIDv7 大致按生成时间有序，不保证严格全局递增，不用于业务排序、业务日期或安全访问凭证。
- 分片路由独立设计：租户标识定位数据库，未来按业务分片键定位库表，ID 定位记录；不能仅凭 UUIDv7 假设可直接定位分片。
- 默认统一采用 UUIDv7；高容量表若有实际性能证据需要例外，须专项评审，不预先混用多套算法。
- 数据库保留主键及业务唯一约束；索引容量、查询与写入表现需在目标数据规模验证。

### 4.1 逻辑数据清单

下列为逻辑实体，不是最终 DDL。

| 平台库 | 租户库 |
|---|---|
| 账号、认证资料、会话权威状态 | 租户成员、组织五类聚合 |
| 租户目录、数据库绑定与结构版本 | 权限五类聚合、开通配置 |
| 账号到租户的可进入关联 | 区域化资源、字典、参数 |
| 系统功能目录、开通指令、初始化与迁移任务 | 租户审计、领域 Outbox 与消费记录 |
| 平台审计、平台 Outbox、恢复控制记录 | 后续各领域归属数据 |

平台成员关联仅用于租户发现，不能替代租户库中成员状态检查。跨库关系用标识，不使用跨库外键或跨库 SQL。业务唯一性约束在所属租户库中建立；账号标识全局稳定。

独立库无需为每张表机械重复 `tenant_id`，但请求、事件、缓存、审计必须携带租户标识；数据源绑定元数据也记录租户身份，防止误路由。是否为特定表保留冗余租户字段待数据模型设计确定。

### 4.2 请求路由

1. 验证会话和账号状态，从服务端会话绑定取得当前租户。
2. 校验租户已初始化且允许访问；解析平台维护的数据库绑定。
3. 建立不可被业务代码随意修改的租户执行上下文。
4. 路由租户数据源，校验成员资格、系统开通、授权及强制限制。
5. 在路由确定后开启租户本地事务，执行用例并记录审计或事件。
6. 请求结束清理上下文；异步任务必须显式携带并重新验证上下文。

没有租户上下文时仅允许明确的平台接口，不得默认路由任意租户库。数据库不可达、绑定不存在时失败关闭，不能回退平台库或其他租户库。

平台仓储与租户仓储分别绑定会话工厂或受控执行器，避免平台查询因线程路由误入租户库。禁止业务层随意切换数据源。切换租户建议轮换会话上下文版本；旧请求不得被重新解释为新租户请求。

### 4.3 数据源生命周期

- 建库迁移凭据与运行期凭据分离；运行凭据限定所属库权限。
- 凭据加密保存、日志不输出，支持轮换；密钥来源待部署方案确定。
- 连接池按需建立并设置全局、单租户连接预算，空闲池可回收。
- 路由映射更新与租户迁移需排空旧连接，不在事务中途切库。
- 后台扫描由平台目录取得合法租户清单，每次执行重新建立租户上下文。

## 5. 事务、事件与一致性

### 5.1 本地事务

应用服务定义事务，事务内不跨数据库切换。单聚合写入建议乐观锁；组织移动、最后管理员保护等并发不变量需结合数据库锁与原子校验，不能只做请求前检查。

同租户数据库的跨领域命令可以在明确约定的应用协调器中共享本地事务，但只能调用公开接口；默认优先聚合内事务、事件联动，禁止不受控的长事务。

平台库与租户库之间不承诺本地原子提交，第一期不默认引入分布式事务框架。通过状态机、可靠事件和幂等补偿处理；必须即时生效的访问限制由权威状态直接阻断。

### 5.2 Outbox

每个源数据库维护自身 Outbox，业务状态与事件在同一本地事务提交。事件至少包括事件 ID、类型、契约版本、聚合标识与版本、租户、发生时间、关联与因果标识、最小必要载荷。

投递器使用领取锁或租约保证多实例竞争安全；租约到期可重新领取。消费者以事件 ID 和处理器标识去重，消费记录与目标状态更新在目标库同事务提交。目标提交后再确认源事件，因此投递语义为至少一次，不能宣称恰好一次。

聚合版本用于检测重复、过期和乱序。需要顺序的事件按聚合串行或检测版本缺口后重试；不同聚合不承诺全局顺序。失败有限重试，超过阈值进入人工排查；重放记录操作者和原因。

### 5.3 关键联动

| 操作 | 即时约束 | 异步联动 |
|---|---|---|
| 移除租户成员 | 成员状态立即阻止访问 | 结束任职、撤销授权、更新平台可进入关联 |
| 禁用账号 | 账号状态阻止所有访问 | 撤销会话、清理缓存 |
| 停用租户 | 平台状态阻止请求和任务开始 | 停止领取任务、通知在途执行器 |
| 角色与授权变更 | 新权限版本成为有效版本 | 失效缓存、更新权限读模型 |

在途写入需在提交前或关键业务动作前再次校验有效状态，并定义停用与事务提交的同步边界；无法通过简单缓存广播保证严格即时失效。

成员移除与重新加入之间需设置清理完成状态或成员生命周期版本，避免旧移除事件在重新加入后撤销新授权。事件处理限定原生命周期或授权来源。

## 6. 认证与权限执行

### 6.1 认证

Spring Security 提供过滤链与认证扩展，不将其默认角色模型替代业务授权模型。建议采用服务端可撤销会话，Redis 保存热状态，权威状态与故障策略另行验证；Token 载体采用 Cookie 还是请求头待前端与部署方案确认。

SSO、MFA 本期只提供契约、配置及验证逻辑，未实现的认证提供方不能启用；不提供可成功绕过真实认证的占位实现。基础密码流程与策略尚需确认。

全局账号停用与租户成员停用分别处理。不同会话独立选择租户。Redis 故障时不能绕过会话验证；是否允许回源及容量上限须在验证阶段确定。

### 6.2 权限管线

```text
账号/会话 → 租户/成员 → 系统开通
→ 操作授权 → 同条授权内的数据与字段策略
→ 普通授权有效结果合并 → 强制限制收口 → 最终决策
```

领域注册资源、动作、字段、可查询方式、组织及业务关系维度。规则保存为类型化条件树，不接受任意 SQL、脚本或数据库列名。MyBatis 适配器将允许的条件编译为参数化查询；不支持的条件拒绝执行，不能静默忽略。

列表过滤在分页和计数之前执行。详情及写入校验目标记录；写入尽量在数据库条件中绑定数据范围与版本，防止检查后对象变化。聚合统计、导出、打印遵循同一语义，不能先取原值再只在 UI 遮盖。

字段策略在有效授权上下文内计算，禁止把某条授权的操作与另一条的数据范围拼接。无权原值不进入响应；修改使用显式字段变更集，区分未提交、清空和替换。原文查看申请及敏感字段查询采用已确认规则。

### 6.3 缓存与预览

缓存键至少包含租户、成员、权限版本、资源动作及必要的上下文，不以角色 ID 单独缓存完整权限。权限变化通过版本检查配合失效通知，不仅依赖 TTL。严格及时生效的权威检查与缓存策略须通过并发测试验证。

权限预览复用执行引擎，返回命中授权、被强制限制的原因和最终结论。预览操作者只能检查有管理权的对象，不借预览获取无权查看的业务原值。

## 7. 国际化、审计与配置

### 7.1 国际化

集中管理语言资源、主数据翻译、异常文案和区域方案。引擎统一解析用户、公司、租户上下文；语言、时区、业务币种独立处理。前端组件与后端引擎共享规则标识及测试样本，不让每个模块自行计算。

瞬时时间建议按 UTC 存储，业务日期独立存储；金额使用十进制类型并携带币种，禁止浮点金额。主数据翻译以稳定对象标识和语言标识关联。汇率来源、精度和历史依据结构待细化。

### 7.2 审计

第一期查询登录、登出、操作日志。认证前或无租户事件写平台审计，已验证租户业务事件写租户审计。操作记录包括操作者、租户成员、动作、目标、结果、时间、追踪标识及脱敏差异；不记录密码、令牌或完整敏感载荷。

成功的重要管理变更与审计意图在所属库同事务提交，可借 Outbox 投递到审计领域公开入口；失败尝试在回滚后独立记录，避免把未提交操作记成成功。事件载荷最小化，不允许审计模块直接读其他领域表。

平台内查询由权限约束，租户管理员不能读其他租户日志。未来网关集成日志和 OpenTelemetry 调用链使用统一关联标识；技术日志不是租户业务日志的无限制替代入口。

### 7.3 配置

系统枚举与可维护业务字典分开。参数声明类型、范围、可覆盖层级和敏感等级。配置发布更新版本，消费者读取有效版本；关键参数审核能力依赖后续审批服务时，第一期采用何种受控发布流程须单独确认。

## 8. API 与错误契约

建议平台接口使用 `/api/platform/v1`，租户接口使用 `/api/tenant/v1`；路径区分作用域，不作为授权依据。契约明确 DTO、分页、排序白名单、时区与币种含义。资源标识与编码分开。

- 成功响应包含业务数据，分页结构统一。
- 错误包含稳定业务码、翻译键、受控参数和追踪标识，HTTP 状态反映认证、授权、冲突及输入错误。
- 前端不能依赖翻译后的句子判断业务结果。
- 写入契约支持幂等键、预期版本和明确的字段变更语义，按用例声明是否要求。
- 外部可见的对象不存在与无权访问响应避免泄露敏感对象存在性。
- OpenAPI 描述认证方式、作用域与错误，不向普通业务用户展示内部堆栈。

## 9. 建库、升级与恢复

租户创建通过持久化步骤任务执行：登记租户 → 建库 → 迁移 → 初始化 → 管理员关联 → 校验 → 启用。每步可重入，保存产物和错误；失败不自动删除含数据的库。平台管理流程用例独立，不依赖尚未建设的通用业务编排引擎。

Flyway 针对平台库与各租户库分别运行；租户脚本建议按统一版本序列交付，应用启动不无限制并发升级所有库。发布包声明支持的数据库版本范围，升级管理器分批执行并限制不兼容访问。

备份恢复使用运维控制状态暂停目标租户写入与任务。需要覆盖数据库、文件和平台关联。授权撤销记录须有独立于被恢复快照的校验依据；恢复后先核对撤销记录、会话、数据库版本与成员关系，再开放。该依据的存储位置、保留期和灾难恢复流程仍待专项设计，未解决前不得声称可防止旧权限复活。

## 10. 验证与工程约束

技术验证范围不涉及具体业务系统，采用最小资源验证底座行为。

| 验证项 | 通过条件 |
|---|---|
| 租户隔离 | A/B 库同标识数据互不泄露；无上下文、伪造上下文均拒绝 |
| 事务路由 | 开事务后不能切库，平台操作不误入租户库 |
| 权限组合 | 不产生跨授权拼接；强制限制、字段脱敏、查询限制一致 |
| 权限失效 | 禁用、移除、角色变化与并发请求满足确定的生效边界 |
| 聚合并发 | 最后一名管理员保护、组织防环、授权版本冲突有效 |
| 可靠事件 | 事务回滚无事件、重复和乱序可处理、跨库失败可恢复 |
| 生命周期竞态 | 移除旧事件不影响重新加入后的新授权 |
| 国际化 | 中英文回退、时区及金额格式正确且不改业务日期 |
| 迁移恢复 | 创建重试不重复、升级失败隔离、旧备份不复活撤销权限 |
| 审计 | 成败准确、原值不泄露、查询不跨租户 |

使用真实 MySQL 验证路由、锁和事务，不用内存数据库替代这些验证。架构测试检查跨领域依赖；领域单元测试覆盖实际规则，不编写只重复 getter 或框架行为的测试。

AI 开发需遵循模块依赖、契约变更、数据库迁移及安全日志规范。每项实现对应设计条目和验收证据，禁止以生成代码数量作为完成标准。

## 11. 推荐实施顺序与待决清单

本文不授权开始实施。设计确认后的推荐顺序：

1. 锁定兼容版本、工程结构和数据库路由方案。
