# 后端工程详细设计

版本：0.7；日期：2026-11-06；状态：分步审阅中；工程命名、核心框架、Valkey、租户/权限管线、Outbox、认证架构及 API 治理已确认，其他领域与运维细节待确认。

## 1. 依据与边界

实施原则：已进入正式框架功能开发，业务与技术能力直接落入正式模块，并通过单元、架构、真实基础设施集成及浏览器验收验证。只有遇到无法通过现有实现与测试确认的技术不确定性时，才隔离建立 PoC；验证结论须回归正式实现，不以 PoC 代替功能交付。

本文依据[平台总体设计](平台总体设计.md)整理。已确认的是技术方向、领域聚合及行为原则；本文提出的模块名称、接口、表名、事务算法和运行机制为建议方案，不能视为已完成技术验证或获准开始编码。

第一期交付平台底座，不实现 SCM、WMS、巡库业务。前端 vue-pure-admin；后端 Java 21、Spring Boot / Spring Cloud；数据库 MySQL。使用 Maven、MyBatis、Spring Security、Valkey、Flyway、Outbox、OpenAPI、结构化日志。Java 侧通过 Spring Data Redis/Lettuce 访问 Valkey，不依赖未经验证的服务端扩展命令。确切版本及兼容性须在工程初始化前核查。

第一期一个平台基础应用，可多实例部署；领域边界不等于物理服务。API 网关、注册中心、配置中心、消息队列不作为启动依赖。审批、单据、编排、打印、报表等后续共享服务仅保留接入边界。

### 2.0 架构设计原理

工程采用 DDD（领域驱动设计）的领域边界、模块化单体的部署方式，以及端口与适配器架构（六边形架构）的技术隔离原则，并遵循整洁架构的依赖向内原则。这些是互相配合的架构方法，不是单一的 GoF 设计模式，也不要求每个目录机械套用完整分层。

| 方法 | 本项目中的应用 | 解决的问题 |
|---|---|---|
| DDD 限界上下文 | 按 identity、tenant、organization、authorization 等领域组织模块，各领域拥有自己的模型、规则与公开能力 | 避免账号、组织、角色等业务逻辑散落在全局 Controller/Service/Mapper 目录中 |
| 模块化单体 | 第一期将领域模块装配到一个 platform-service 中，可多实例运行 | 在保留模块边界的同时降低部署、调用和事务协调成本 |
| 端口与适配器 | 用例及领域声明所需接口，HTTP、MyBatis、Valkey 和事件技术通过适配器接入 | 隔离业务规则与技术实现，便于测试及替换接入方式 |
| 整洁架构依赖原则 | 技术实现依赖业务定义的端口，核心领域不依赖 Web、数据库客户端或其他领域内部实现 | 防止业务模型被框架、存储结构和部署方式绑定 |

目录分三种职责：`services/<name>-service` 表达可部署边界，服务内的领域目录表达业务边界，`adapters` 与 `building-blocks` 表达技术能力。Maven 子模块只是构建和依赖边界，不自动成为微服务。`application` 在服务根目录表示启动装配模块；领域内部的 `internal/application` 表示用例协调，两者职责不同。

例如“创建组织”的请求由 HTTP 适配器接收并转换输入，调用组织领域的公开用例；用例协调权限、事务与领域对象，领域对象校验组织规则，通过仓储端口保存；持久化适配器实现仓储端口并调用 MyBatis。运行时会调用数据库，但源代码中的仓储接口由业务侧定义，领域不引用 Mapper。Controller 不直接调用 Mapper，数据库 PO 不直接成为 HTTP 响应。

选择这种结构是因为第一期的平台能力紧密协作，尚无证据需要独立服务；先形成清晰的数据所有权和模块接口，能够以较低运维成本实现功能，同时为后续按需拆分留下边界。简单字典等功能可简化实现；复杂领域才使用聚合、值对象、仓储等建模手段，不为分层创建空类或空包。

当前正式工程已进入功能开发：身份认证已接入 MySQL 账号、持久 OAuth 授权与 Valkey 共享会话，其余领域仍以模块骨架为主。技术验证保留在独立的 `poc-app`。以下目录和依赖规则描述目标设计，不能据此认为领域模型、端口适配器或完整边界检查已经落地。`poc-app` 不作为正式领域代码或公共代码的存放位置。

根工程命名 `backend`，统一管理依赖与插件版本。顶层先按可部署服务边界组织，服务内部再按领域模块组织；不假设一个领域必然对应一个微服务。

```text
backend/
├─ pom.xml
├─ building-blocks/          最小、稳定、无领域语义的共享构件
├─ contracts/                独立版本的跨进程契约
│  ├─ platform-events/  对外发布的集成事件
│  └─ partner-api-spec/ 外部合作 OpenAPI 规范/生成物
└─ services/
   └─ platform-service/      第一期唯一可部署服务
      ├─ identity/
      ├─ tenant/
      ├─ organization/
      ├─ authorization/
      ├─ localization/
      ├─ configuration/
      ├─ audit/
      ├─ adapters/           HTTP、持久化、安全、事件和可观测性适配
      ├─ application/        Spring Boot 装配/启动模块
      └─ architecture-tests/ 服务内模块与适配器边界验证
```

命名约定：`identity` 表示认证领域，`authorization` 表示业务授权，`security` 只表示安全技术适配。领域模块的进程内公开 API 由模块根包或明确 named interface 暴露，其他实现放入 `internal`。`contract` 一词仅用于需独立版本的跨进程消息、外部 API 规范或消费者合同，不泛化为所有领域接口的后缀。

### 已确认：工程命名规范

- 根工程使用 `backend`，一级按 `building-blocks`、`contracts`、`services` 分类；可部署单元命名为 `<name>-service`，第一期为 `platform-service`。
- 领域使用简短、含义明确的英文名；同一领域在目录、契约和文档中使用同一名称，避免同义词混用。
- 进程内领域公开能力不机械拆成 `<领域>-api` artifact，使用模块根包/named interface 与 `internal` 包边界。只有需跨进程独立版本时才创建 `contracts` artifact。
- 使用小写命名，多个单词用连字符分隔；Java 包名遵循 Java 规则，不包含连字符。
- 后续新增模块沿用本规范，先明确职责及所属层次，再确定名称；需要例外时在设计文档中说明原因。

领域模块数量可在实现时合并，但不可消除领域边界。`building-blocks` 不放账号、组织、角色实体或领域仓储；`contracts` 不是共享实体仓库，只存独立版本的跨进程契约。服务内部适配器不得反向依赖其他领域实现。

### 2.1 依赖方向

- 启动模块依赖领域实现与技术支持，完成装配。
- 领域应用实现依赖自身领域模型、端口和最小共享构件；跨领域仅依赖对方公开 API。这里的进程内公开 API 不要求另建 `contracts` artifact。
- 领域层不得依赖 Spring MVC、MyBatis、Valkey 客户端或其他领域实现。
- 跨领域接口通过应用层端口调用，避免实现模块相互引用。
- 组合查询使用专门读接口或投影，不能以报表需要为由跨领域关联业务表。
- 用架构测试验证禁止依赖；模块职责和允许依赖清单纳入仓库规范。

### 2.2 领域内部结构

```text
organization/src/main/java/<组织领域根包>/
├─ <公开用例接口、稳定类型>   其他模块可访问的进程内 API
└─ internal/                 其他模块禁止引用
   ├─ application/           命令、查询、应用服务、端口、事务协调
   └─ domain/                聚合、值对象、领域服务、事件、仓储接口
```

领域对象控制状态转换，应用服务协调流程；Controller 不直接调用 Mapper。持久化对象不作为领域对象或 HTTP 响应。简单字典可简化内部实现，仍保留领域归属和公开接口。

公开入口默认使用模块根包；确需分组时使用明确的 named interface，而不是默认再增加一个 `api` Maven 模块。`internal/application` 与 `internal/domain` 按实际规模创建，以上为 Java 包结构建议，不是当前已有目录清单。

技术实现统一落在服务级 `adapters` 中，并在适配器内部按领域分包：`app-api`、`partner-api`、`platform-api` 承接各接口面，`persistence` 实现仓储端口，`security`、`eventing`、`observability` 提供安全、事件及可观测性接入。适配器只访问所属领域公开或显式 named interface 暴露的端口，不引用领域 `internal`；需要由外部实现的仓储端口及稳定类型应显式暴露。领域内部不再并列建立重复的 `infrastructure` 目录，避免同类技术实现出现两个归属位置。

### 2.2.1 后续服务拆分原则

服务拆分以独立发布、数据所有权、性能和团队边界为依据，不按领域目录数量一对一拆分。例如审计需要独立扩容时，可新增 `services/audit-service`，迁移审计领域及其所需适配器、启动模块和测试；其他领域继续留在平台服务。

- 将原有进程内调用改为有版本的 API 或集成事件，跨进程契约放入 `contracts`，不共享领域实体或 Mapper。
- 拆出的服务独立管理自己的数据与迁移，停止其他服务直接读写其表；数据库物理隔离方式按实施阶段确定。
- 原有跨模块本地事务不能直接跨服务延续；需明确事件投递、幂等、失败补偿与一致性要求，不能只移动目录。
- 为新服务建立独立配置、发布、监控、超时及故障处理；网关、服务发现和消息设施按实际需要引入。
- 后端拆分不要求同时拆前端。`frontend/apps/admin` 仍可通过 BFF 或统一入口访问多个服务，继续复用 vue-pure-admin 布局；只有前端也需要独立发布时才增加应用装配目录。

当前仅保留上述演进原则，尚未实施微服务拆分，不预先增加空服务或分布式调用。

### 2.3 已确认：核心框架与工程约定

- 使用 Spring MVC，不引入 WebFlux；MyBatis/JDBC 的阻塞模型与 Web 技术栈保持一致。
- 提交 Maven Wrapper，根工程统一插件和依赖版本；使用 Spring Boot BOM 与 Spring Cloud BOM，不在子模块随意覆盖。
- 使用与 Boot 4.1 适配的 MyBatis Starter 4.1.x。领域模型与持久化 PO 分离，领域层定义仓储接口，基础设施层实现。
- 复杂 SQL 使用 Mapper XML，简单且可读的 SQL 允许使用注解；不引入 MyBatis-Plus，不让通用 CRUD 抽象侵入领域模型。
- 共享数据库使用一套 Flyway 迁移历史，已发布脚本不修改。
- Web 入参使用 Jakarta Bean Validation；业务不变量仍由领域模型校验，不以 DTO 注解替代。
- 使用 springdoc-openapi 3.x 从后端契约生成 OpenAPI 规范，再生成前端 TypeScript 类型和调用客户端。
- 默认不使用 Lombok；优先 Java record、构造器及显式领域方法。
- 使用 JUnit 5、AssertJ、Mockito、Spring Boot Test 与 Testcontainers。MySQL 和 Valkey 集成测试使用真实容器，不以 H2 模拟 MySQL 语义。
- 第一期使用传统 JVM 部署，GraalVM Native Image 不作为交付要求。

## 3. 领域与聚合落位

| 领域 | 已确认聚合 | 建议数据位置 | 关键约束 |
|---|---|---|---|
| 身份 | 账号、会话 | 共享库的平台级表；Valkey 承担在线会话热状态 | 账号停用全局失效，单会话可撤销 |
| 租户 | 租户 | 共享库的平台级表 | 状态决定是否可访问、可执行 |
| 租户 | 租户成员、租户开通配置 | 共享库租户表 | `tenant_id` 强制隔离；同账号同租户唯一成员 |
| 组织 | 类型、单元、关系、岗位、任职 | 共享库租户表 | `tenant_id` 强制隔离；同类型独立树、跨租户禁止 |
| 权限 | 角色、授权记录、委派、强制限制、模板 | 共享库租户表 | `tenant_id` 强制隔离；来源可追溯、默认拒绝 |
| 国际化 | 配置与资源，聚合待细化 | 共享库租户表；平台包提供基础资源 | 展示偏好不改业务结果 |
| 配置 | 字典与参数，聚合待细化 | 共享库租户表 | `tenant_id` 强制隔离；编码稳定 |
| 审计 | 追加记录，聚合待细化 | 共享库；租户事件带 `tenant_id` | 最小敏感内容、受控查询、不可随意改写 |

开通配置的租户副本不能直接由租户管理员扩大：平台开通操作通过受控流程更新，租户访问由已确认有效版本判定。平台开通指令、状态与租户内生效配置的权威关系须在详细接口设计中锁定。

组织类型是树的边界；一个单元一个类型，同类型上级或直接挂租户根。建议树采用父节点字段和祖先后代索引，由组织领域维护；移动节点需防环、影响分析和并发控制。索引结构尚未锁定。

## 4. 共享数据库与租户行级隔离

### 4.0 ID 生成策略（已确认）

- 默认内部标识使用 UUIDv7，由应用创建对象时生成，永久不变；适用于聚合、实体、事件及幂等记录。幂等记录 ID 不替代请求幂等键。
- MySQL 默认使用 `BINARY(16)` 保存 UUID 原始字节，API 使用标准 UUID 字符串，前端按字符串处理。统一转换器须保证字节序一致，不使用面向 UUIDv1 的字节交换方式。
- 生成接口定义在 `common`，领域通过抽象使用，不直接依赖具体生成库；库选择及并发、随机源、时钟回拨行为须验证，不自行拼装算法。
- 各领域可定义有语义的 ID 值对象，跨聚合使用标识引用。
- 业务单号由编码服务负责，与内部 ID 分开；追踪标识遵循 OpenTelemetry 规范。
- UUIDv7 大致按生成时间有序，不保证严格全局递增，不用于业务排序、业务日期或安全访问凭证。
- 分片路由独立设计：租户标识定位数据库，未来按业务分片键定位库表，ID 定位记录；不能仅凭 UUIDv7 假设可直接定位分片。
- 默认统一采用 UUIDv7；高容量表若有实际性能证据需要例外，须专项评审，不预先混用多套算法。
- 数据库保留主键及业务唯一约束；索引容量、查询与写入表现需在目标数据规模验证。

### 4.1 表分类与约束

- 表必须显式声明为“平台级表”或“租户表”，不允许未分类表进入生产迁移。
- 租户表的 `tenant_id` 使用与租户标识一致的 UUIDv7 `BINARY(16)`，不可为空、不可更改。新增时由基础设施层从已验证上下文填入，不接受客户端传入的字段值。
- 租户内唯一约束采用 `(tenant_id, business_key...)`；常用查询索引根据选择性以 `tenant_id` 为前导或重要组合列。
- 租户内关联默认使用同时包含 `tenant_id` 的复合关系或写入前原子校验，确保引用目标属于同一租户。
- 共享库内的物理外键按领域边界和迁移成本选择使用；无论是否使用外键，应用都必须校验租户一致性。

### 4.2 租户上下文与 SQL 执行

1. 验证会话和账号状态，从服务端会话绑定取得当前租户。
2. 校验租户已初始化且允许访问。
3. 建立不可被业务代码随意修改的租户执行上下文。
4. 在共享数据源上校验成员资格、系统开通、授权及强制限制。
5. 开启本地事务，对所有租户表 SQL 强制租户条件，执行用例并记录审计或事件。
6. 请求结束清理上下文；异步任务必须显式携带并重新验证上下文。

没有租户上下文时仅允许明确的平台级仓储和接口。普通租户仓储必须立即失败，不得将缺少上下文解释为跨租户查询。

### 4.2.1 已确认：行级隔离实现

- 使用单一受控 `DataSource`、`SqlSessionFactory` 和事务管理器，不按租户创建或切换连接池。
- 所有租户 Mapper 必须通过统一 MyBatis 隔离执行层；对 SELECT、UPDATE、DELETE 强制注入或验证 `tenant_id` 条件，INSERT 强制从上下文写入 `tenant_id`。
- SQL 解析器无法安全理解的语句、多表更新、原始 JDBC、存储过程和动态表名默认禁止；需要例外时使用单独受控适配器、专项审查和隔离测试。
- 租户标识只能来自已验证的服务端会话。请求头、URL 或请求参数只能表达切换意图，不能直接决定 SQL 中的租户条件。
- 建立租户上下文前须校验账号、会话、租户状态与会话当前租户，并生成上下文版本。上下文建立后不允许业务代码修改。
- 事务开始后禁止切换租户上下文。共享库内可在一个本地事务更新平台和租户数据，但必须由明确应用用例协调并遵守领域边界，不借此跨租户修改。
- HTTP 请求结束必须在 `finally` 语义下清理上下文。异步任务不继承线程本地状态，必须显式携带租户标识、上下文版本和最小必要身份，执行前重新验证。
- 跨租户管理与统计不关闭普通拦截器，而是使用独立 Mapper/仓储、专用权限和完整审计；普通业务代码不得引用该适配器。
- 租户条件与数据权限由同一数据访问策略管线编译，不实现两套相互独立且先后改写 SQL 的拦截器。租户边界是不可被角色、授权或管理员权限扩大的强制前置条件。

### 4.3 数据源与凭据

- 使用 HikariCP 管理共享库连接池，容量受 MySQL 最大连接数、应用实例数及运维/迁移预留约束。不再维护租户级连接池。
- 迁移凭据与应用运行凭据分离；运行账号具有共享业务表必要 DML 权限，因此数据库账号本身无法区分租户，应用行级防线和测试是强制安全边界。
- 连接凭据不明文保存于数据库、配置文件、环境日志或异常信息。密文或凭据引用与主密钥分离；主密钥来自部署环境的 Secret/KMS。
- 基础设施层定义 `SecretProvider`：私有化基础实现可读取受控挂载 Secret，后续可适配 Vault 或云 KMS。领域代码不感知密钥系统，获得的明文凭据不缓存超过必要生命周期。
- 凭据轮换期间新旧版本可短暂并存：验证新凭据、阻止新事务、排空旧池、原子切换绑定版本，确认新池可用后撤销旧凭据。
- 后台扫描由平台目录取得合法租户清单，每次执行重新建立租户上下文。

## 5. 事务、事件与一致性

### 5.1 本地事务

应用服务定义事务，事务内不跨数据库切换。单聚合写入建议乐观锁；组织移动、最后管理员保护等并发不变量需结合数据库锁与原子校验，不能只做请求前检查。

同租户数据库的跨领域命令可以在明确约定的应用协调器中共享本地事务，但只能调用公开接口；默认优先聚合内事务、事件联动，禁止不受控的长事务。

共享库使平台数据和租户数据可在明确用例中本地原子提交，第一期不引入分布式事务框架。不同服务、外部系统或长流程仍通过状态机、可靠事件和幂等补偿处理。

### 5.2 Outbox

共享数据库维护统一 Outbox。业务状态与事件在同一本地事务提交；不允许在事务提交前直接发布可被外部观测的消息。

#### 5.2.1 已确认：事件契约

- 事件作用域显式区分 `PLATFORM` 与 `TENANT`。租户事件的 `tenant_id` 必填；平台事件的 `tenant_id` 为空且作用域必须为 `PLATFORM`，不以空值暗示不明作用域。
- 统一事件信封包含 `eventId`、`eventType`、`contractVersion`、`scope`、`tenantId`、`aggregateType`、`aggregateId`、`aggregateVersion`、`occurredAt`、`traceId`、`correlationId`、`causationId` 及最小必要 `payload`。
- 领域聚合只产生领域事件，不直接调用 Outbox、Valkey、消息队列或具体消费者。应用/基础设施层将事件转换为版本化契约并入库。
- 事件类型和载荷具有独立契约版本。消费者通过显式契约 DTO 兼容读取，不将历史载荷直接反序列化为当前可变领域实体。
- 载荷仅包含消费者执行所需的最小数据，不包含密码、Token、密钥、完整敏感对象或无关快照。

#### 5.2.2 已确认：多实例投递与租约

- 第一期不引入 Kafka/RabbitMQ，多实例投递器轮询 Outbox，使用 `SELECT ... FOR UPDATE SKIP LOCKED` 分批领取。领取事务只更新租约，不在持锁事务中执行消费处理。
- MySQL 在默认隔离级别和特定索引扫描下可因 next-key/gap lock 使并发 Worker 短暂领取到空批次。Worker 对空批次使用带抖动的短退避再轮询，不将单次空结果视为队列已排空，也不假设 Worker 必然均匀分配。
- 租约状态至少包含 `workerId`、`leasedUntil`、`attemptCount`、`nextAttemptAt` 和受控 `lastErrorCode`。实例崩溃或租约超时后可被其他实例安全重新领取。
- 投递语义明确为“至少一次”，不宣称恰好一次。消费端以 `(eventId, handlerId)` 建立唯一幂等记录，目标状态更新与消费记录在同一本地事务提交。
- 租户事件消费者根据事件租户标识重新建立并校验租户上下文，不仅信任载荷；租户已停用、事件与目标不同租户或必要上下文无法验证时不执行业务变更。
- `aggregateVersion` 用于检测重复、过期和版本缺口。重复事件幂等确认，过期事件按处理器契约忽略并记录，版本缺口延迟重试或进入核对。只在业务需要时保证聚合内顺序，不承诺不同聚合全局顺序。

#### 5.2.3 已确认：失败、重放与保留

- 重试使用指数退避与随机抖动，处理器明确分类临时系统故障、不可重试契约/业务错误和需人工判断错误。不对所有异常无区别无限重试。
- 超过阈值进入待人工处理状态，不自动删除。重放必须记录操作者、原因、时间、原事件 ID 和新的重放执行记录，不静默改写原始事件载荷。
- 成功事件、消费记录与失败记录在满足审计、故障核对和合规保留期后分批归档/清理，不因为当前投递成功就立即删除。
- 未来引入消息队列时只替换投递适配器，不改变领域事件、契约版本、租户校验、消费幂等和重放审计规则。

### 5.3 关键联动

| 操作 | 即时约束 | 异步联动 |
|---|---|---|
| 移除租户成员 | 成员状态立即阻止访问 | 结束任职、撤销授权、更新平台可进入关联 |
| 禁用账号 | 账号状态阻止所有访问 | 撤销会话、清理缓存 |
| 停用租户 | 平台状态阻止请求和任务开始 | 停止领取任务、通知在途执行器 |
| 角色与授权变更 | 新权限版本成为有效版本 | 失效缓存、更新权限读模型 |

在途写入需在提交前或关键业务动作前再次校验有效状态，并定义停用与事务提交的同步边界；无法通过简单缓存广播保证严格即时失效。

成员移除与重新加入之间需设置清理完成状态或成员生命周期版本，避免旧移除事件在重新加入后撤销新授权。事件处理限定原生命周期或授权来源。

## 6. 认证与权限执行

### 6.1 认证

Spring Security 提供过滤链与资源服务器能力，Spring Authorization Server 在同一应用中提供逻辑独立的 OAuth/OIDC 授权服务。两者不以默认角色模型替代平台业务授权模型。

Web 使用 BFF 服务端会话与 HttpOnly Cookie/CSRF，原生移动端使用 Authorization Code + PKCE 和 Bearer Token，外部集成使用 Client Credentials。本地密码使用 Argon2id，第一期包含 TOTP/恢复码与高风险操作 step-up；详细范围见[认证与会话详细设计](认证与会话详细设计.md)。

全局账号停用与租户成员停用分别处理。不同设备会话可独立选择租户。Valkey 故障时不能绕过会话验证；可受限回源数据库，两者都无法验证时默认拒绝。

### 6.2 权限管线

```text
账号/会话 → 租户/成员 → 系统开通
→ 操作授权 → 同条授权内的数据与字段策略
→ 普通授权有效结果合并 → 强制限制收口 → 最终决策
```

领域注册资源、动作、字段、可查询方式、组织及业务关系维度。规则保存为类型化条件树，不接受任意 SQL、脚本或数据库列名。MyBatis 适配器将允许的条件编译为参数化查询；不支持的条件拒绝执行，不能静默忽略。

列表过滤在分页和计数之前执行。详情及写入校验目标记录；写入尽量在数据库条件中绑定数据范围与版本，防止检查后对象变化。聚合统计、导出、打印遵循同一语义，不能先取原值再只在 UI 遮盖。

字段策略在有效授权上下文内计算，禁止把某条授权的操作与另一条的数据范围拼接。无权原值不进入响应；修改使用显式字段变更集，区分未提交、清空和替换。原文查看申请及敏感字段查询采用已确认规则。

### 6.2.1 已确认：统一数据访问策略管线

租户隔离与数据权限共用一个类型化策略模型和 SQL 编译器，建议按以下顺序生成最终决策：

```text
可信身份/会话
→ 强制租户边界
→ 系统开通与操作授权
→ 每条授权内绑定的数据范围与字段策略
→ 普通授权结果并集
→ 强制限制收口
→ 业务状态与并发版本条件
→ 参数化 SQL、字段投影/脱敏与决策证据
```

- 租户边界不是一条可配置的普通授权，不参与并集，不允许以角色、强制限制例外或“超级管理员”身份绕过。跨租户端口使用平台作用域的独立用例和仓储。
- 每个可授权资源由领域声明资源标识、租户列、主表别名、可授权关系、允许查询操作、字段及脱敏方式。策略只引用这些稳定标识，不保存 SQL 片段、表名或列名。
- Mapper 方法显式关联资源、操作和访问模式（列表、详情、更新、删除、导出、统计等）。未注册或声明与 SQL 结构不匹配时拒绝执行。
- SQL 编译器一次生成租户条件、数据范围和强制限制，并在分页、计数、联表、子查询和聚合前应用。不允许先查询超集后再在 Java 或前端过滤。
- UPDATE/DELETE 的 `WHERE` 同时包含租户、记录标识、最终数据权限条件及乐观锁版本；以受影响行数区分成功、无权/不存在和并发冲突时，不通过“先查再改”单独保障安全。
- 字段权限与行条件来自同一决策结果：查询时限制投影与脱敏，写入时校验显式变更集。禁止用某条授权的行范围结合另一条授权的字段修改权。
- 策略编译结果可按租户、成员、权限版本、资源、操作和上下文维度缓存；缓存的是受控决策计划或类型化条件，不是拼接好的任意 SQL。
- 审计保存决策版本、命中授权来源和强制限制标识，但不记录敏感原值或可重放的完整 SQL 参数。

管线总体顺序、资源声明、Mapper 绑定、MyBatis 执行边界、查询分级与权限版本失效原则已确认。存在性隐藏的 HTTP 错误语义、具体 SQL AST 库、复杂度/低样本阈值和失效参数待 PoC 锁定。

### 6.2.2 已确认：`AccessPlan` 条件树与组合语义

- 条件树只允许受控类型节点：`And`、`Or`、`Not`、`Compare`、`In`、`Between`、`IsNull`、`RelationExists`、`CurrentSubject`、`CurrentOrganization` 和 `SpecifiedRecords`。新节点类型须通过平台版本升级注册，不由管理员自定义执行代码。
- 节点只引用领域已注册的稳定字段和关系标识，不接受表名、列名、SQL、脚本或表达式文本。值须通过字段声明的 UUID、日期、金额、枚举、字符串等类型校验。
- 单条普通授权先将操作、数据范围、字段策略、有效期和授权来源绑定为不可拆分的完整结果。授权内允许 `AND`、`OR`、`NOT` 及分组，多条授权只对完整结果取并集，不跨授权拼接操作、行范围或字段权限。
- 最终行条件语义为 `tenantBoundary AND (GrantA OR GrantB ...) AND NOT MandatoryDeny`。强制限制对普通授权并集统一收口，不能被角色、临时授权或字段策略绕过。
- `Not` 只能作用于已受控的条件组，不能将“不是某数据”解释为无边界全局放行；任何否定条件始终位于强制租户边界内。
- `RelationExists` 只能使用领域注册关系，例如本人负责、本人所在组织及组织与下级，不支持管理员配置任意联表。
- `SpecifiedRecords` 同时保存资源类型与记录标识，并受租户、授权有效期和强制限制约束，不允许仅以全局 ID 绕过租户校验。
- 字段策略按记录条件计算，不对所有命中授权的字段权限做无条件全局并集。同一字段可因记录范围不同分别得到原文、脱敏、隐藏或不可修改结果。
- 条件树设置深度、节点数、`IN` 元素数、关系展开规模和编译成本上限。超限时拒绝发布或执行，不生成无界 SQL。
- 规则保存规范化 JSON 和独立规则版本。发布前执行类型、边界、循环关系、试编译和成本检查；字段下线、关系不可用、编译失败或必要上下文缺失时默认拒绝。
- `AccessPlan` 返回决策版本、授权来源、命中条件和强制限制标识，供权限预览、影响分析和审计使用；不返回敏感原值或可重放的完整 SQL 参数。

### 6.2.3 已确认：字段权限与脱敏合并

- 对同一记录和字段，先独立判断每条完整授权的行条件；只有命中该记录的授权才参与字段决策，未命中授权的字段权限不得全局漂移到该记录。
- 普通授权可累加其明确授予的 `visible`、`editable`、`queryable`、`sortable`、`exportable` 和 `printable` 能力。各能力相互独立：可见不自动可编辑/查询/导出，可编辑也不自动允许查看原文。
- 普通授权的展示方式按 `hidden < replacement < masked < original` 取命中授权中最宽松的有效结果。强制限制在普通结果上最后收口，可降级展示方式或撤销编辑、查询、排序、导出和打印能力，不能扩大任何能力。
- 有编辑权但无原文查看权时只允许替换值：响应不返回原值，未提交字段表示不修改，显式 `null` 表示主动清空，新值仍执行完整类型、格式和业务规则校验。
- 无权字段优先不进入 SQL 投影；因条件字段策略必须读取后判定时，只在受控的服务端映射阶段处理，原值不进入日志、缓存或未授权 DTO。
- 字段策略按记录计算，因此同一列在同一列表页中可对不同记录分别返回原文、脱敏值、替代值或不返回。响应契约不用脱敏占位字符串混淆真实数据。
- 精确查询、模糊查询、范围查询、排序、分组和统计是独立可授权查询能力。字段可见不代表允许用这些能力推断原值。
- 导出、打印和报表按各自操作重新计算字段决策，不复用页面查看结果来扩大权限。
- 多个强制脱敏策略同时命中时选择信息泄露最少的结果；同级策略按稳定优先级与策略标识决定，保证结果可重复。
- 字段未声明或未授权时默认隐藏且不可修改。必须返回的技术/公共字段须在资源契约中显式声明，不使用默认放行。

### 6.2.4 已确认：权限资源声明与装配

- 稳定业务契约由所属领域的 `<domain>-api` 模块声明，包括资源、操作、字段和数据范围维度的稳定标识。契约不包含表名、列名、Mapper 方法或 SQL。
- 资源的物理数据映射放在领域基础设施层 `infrastructure/access`，通过 `AccessDescriptorProvider` 声明主表/别名、租户列、业务字段映射、已批准关联路径、查询能力和脱敏实现。
- Mapper 方法与资源、操作、访问模式的绑定采用领域基础设施层的集中注册，避免在每个 Mapper 方法堆叠权限注解。绑定键为可校验的 Mapper 完整方法标识，不由请求动态指定。
- Web/Integration Controller 使用简洁的操作权限注解引用领域契约常量。声明同时用于运行时操作授权和 OpenAPI `x-permission` 扩展；OpenAPI 本身不执行权限。
- 应用启动时将领域契约、物理映射、Mapper 绑定和 Controller 声明装配为只读 `ResourceRegistry`。注册表完成后不允许业务请求动态修改。
- 管理员配置及数据库授权记录只引用 `resourceId`、`actionId`、`fieldId`、`scopeDimensionId` 和 `relationId` 等稳定业务标识，不存储 Java 类名、Mapper 方法名、表列名或 SQL。
- 以下情况在构建测试或应用启动阶段失败：Controller 引用未注册资源/操作；Mapper 未绑定；契约与物理映射缺失；租户资源未声明租户列；策略引用未注册字段/关系；查询能力没有安全编译器；Integration API 暴露未批准资源。
- `arch-test` 扫描 Web Controller、Integration Controller、Mapper、原始 JDBC 调用和 `ResourceRegistry`，防止存在绕过统一数据访问管线的入口。

### 6.2.5 已确认：查询分级与 MyBatis 执行边界

| 级别 | 查询类型 | 执行方式 |
|---|---|---|
| A | 单表 CRUD、按 ID 查询 | 统一策略编译器自动生成租户、数据权限、强制限制和并发条件 |
| B | 固定且已注册联表 | 根据资源关系声明、表别名和固定查询结构编译 |
| C | 聚合、报表、仪表盘和复杂统计 | 专用只读查询模型/预聚合表与独立权限契约 |
| D | 任意动态 SQL、动态表名、未注册原生查询或存储过程 | 默认禁止；仅允许经独立适配器、专项安全评审、隔离测试和审计后例外引入 |

- A 级查询的列表与数量查询、详情与写入条件复用同一 `AccessPlan`；不允许分页内容受限而总数泄露。
- B 级的关联路径必须在 `AccessDescriptor` 注册。每个租户表均验证 `tenant_id` 一致，条件精确绑定表别名；请求不能动态选择连接表、列或方向。
- B 级 `LEFT JOIN` 的策略条件根据被保护资源放在 `ON` 或主查询的正确位置，不因简单追加 `WHERE` 而改变为 `INNER JOIN`。子查询需独立声明并编译其资源边界。
- C 级查询先应用租户与数据权限，再聚合。资源契约独立声明指标、维度、筛选、排序、分组和统计能力；必要时通过最小分组数量或低样本隐藏防止推断敏感值。
- D 级中的 `${tableName}`、`${columnName}`、管理员输入 SQL、任意动态联表、租户业务直接原始 JDBC 及存储过程自行处理租户均默认禁止。
- `AccessPlanCompiler` 负责从身份、租户、授权和强制限制生成类型化计划；`AccessQueryBuilder` 负责编译参数化 SQL AST；Mapper XML/Provider 描述业务查询主体和固定关联。
- MyBatis 插件作为最后的防绕过检查，验证 Mapper 绑定、租户上下文、策略计划与最终 SQL，不通过字符串拼接或独立重新计算权限充当“万能拦截器”。

### 6.2.6 已确认：平台跨租户作用域

- 普通租户上下文永远只访问一个租户，不提供 `disableTenantFilter`、空 `tenantId` 或超级管理员跳过租户条件的通用开关。
- 跨租户用例使用独立 `PlatformScope`，只能由已验证平台身份进入，并校验明确的平台资源和操作权限。平台开通管理权不自动包含租户业务数据权限。
- 平台管理默认只访问租户目录、开通配置、容量/运行状态、迁移/维护任务和脱敏统计。跨租户查询默认只读，优先使用专用读模型或脱敏聚合表。
- 跨租户仓储放在 `services/platform-service/adapters/persistence/platform-scope` 包和 Mapper 命名空间，须声明用途、允许租户范围、资源、字段、是否允许明细及审计类别。普通领域模块不得依赖该包，由 `architecture-tests` 强制检查。
- 平台支持人员查看单租户明细时不模拟普通租户用户登录，而是使用临时支持授权。授权明确目标租户、资源/操作、数据/字段范围、有效期、原因及工单/审批编号，继续遵守强制限制。
- 跨租户批量写入默认禁止。平台批量管理操作拆分为逐租户命令/任务，每个租户独立校验、事务、失败处理和审计，不用一条无界 SQL 修改所有租户。
- 紧急“破窗”访问单独授权，要求强认证、明确原因、极短有效期、实时告警与事后复核；仍不得绕过标记为不可例外的强制限制。
- 所有 `PlatformScope`、临时支持与破窗访问记录操作者、目的、目标租户、资源、字段范围、结果、数量和 `traceId`，不写入敏感原值。Integration API 不暴露 `PlatformScope`。

### 6.3 缓存与预览

权限数据库是权威源，Valkey 只缓存已编译 `AccessPlan` 或类型化中间结果。缓存键至少包含租户、主体类型/标识、资源、操作、上下文指纹与完整权限版本组合，不以角色 ID 单独缓存权限。

### 6.3.1 已确认：权限版本与失效

- 权限版本至少由租户权限版本、访问主体授权版本、强制限制版本、资源声明版本和租户开通版本组成。用户、集成客户端和平台主体使用不同 `subjectType`，缓存不混用。
- 授权、角色/成员/客户端状态、强制限制和开通范围变更在同一数据库事务中更新权威数据、递增对应版本并写入 Outbox 失效事件。
- 新请求先校验轻量版本。版本不一致时旧缓存立即不可用，不等待失效事件送达或 TTL 到期。Valkey 通知用于主动清理和降低旧缓存占用，不是正确性的唯一保障。
- 每个请求建立不可变 `PermissionSnapshot`，同一请求的内容/数量查询、详情、字段及审计决策使用同一版本。权限预览与影响分析显式标注使用的版本。
- 降权、撤销、成员/客户端停用及强制限制变化属于安全收紧：提交后新请求立即使用新版本；长任务和关键写入在关键动作或提交前重新校验，版本变化则中止并要求重试。普通扩权只对新请求生效。
- 缓存未命中时可从数据库重新编译。Valkey 不可用但数据库可用时，在并发上限、超时、请求合并和熔断保护下回源；不继续使用无法验证版本的本地旧缓存。
- 数据库与 Valkey 都无法验证权威权限时默认拒绝。负缓存也必须绑定权限版本并使用短 TTL，不以长时间拒绝缓存覆盖新增授权。
- Integration API Token 内的授权版本必须与权威版本匹配；客户端或授权版本变化后，Token 即使尚未到期也被拒绝。

权限预览复用执行引擎，返回命中授权、被强制限制的原因和最终结论。预览操作者只能检查有管理权的对象，不借预览获取无权查看的业务原值。

## 7. 国际化、审计与配置

### 7.1 国际化

集中管理语言资源、主数据翻译、异常文案和区域方案。引擎统一解析用户、公司、租户上下文；语言、时区、业务币种独立处理。前端组件与后端引擎共享规则标识及测试样本，不让每个模块自行计算。

瞬时时间建议按 UTC 存储，业务日期独立存储；金额使用十进制类型并携带币种，禁止浮点金额。主数据翻译以稳定对象标识和语言标识关联。汇率来源、精度和历史依据结构待细化。

### 7.2 审计

第一期查询登录、登出、操作日志。认证前或无租户事件写平台审计，已验证租户业务事件写租户审计。操作记录包括操作者、租户成员、动作、目标、结果、时间、追踪标识及脱敏差异；不记录密码、令牌或完整敏感载荷。

成功的重要管理变更与审计意图在所属库同事务提交，可借 Outbox 投递到审计领域公开入口；失败尝试在回滚后独立记录，避免把未提交操作记成成功。事件载荷最小化，不允许审计模块直接读其他领域表。

平台内查询由权限约束，租户管理员不能读其他租户日志。未来网关集成日志和 OpenTelemetry 调用链使用统一关联标识；技术日志不是租户业务日志的无限制替代入口。

### 7.3 配置

系统枚举与可维护业务字典分开。参数声明类型、范围、可覆盖层级和敏感等级。配置发布更新版本，消费者读取有效版本；关键参数审核能力依赖后续工作流服务时，第一期采用何种受控发布流程须单独确认。

## 8. API 与错误契约

接口分为第一方应用 API、外部合作 API 与平台管理 API，命名、域名、版本和废弃规则见[API 命名与生命周期管理规范](API命名与生命周期管理规范.md)。各入口可调用同一应用用例与领域能力，但 Controller、DTO、认证方式、发布节奏和 OpenAPI 契约相互独立。

### 8.1 第一方应用 API

- 服务 AppNexus Web 和原生移动端，建议使用 `app-api.<domain>` 的 `/api/...` 资源路径，不在 URL 写入 web/mobile 渠道。
- 可在共同资源契约上提供用途明确的 BFF/同步资源，不因客户端形态复制全部 API。Web 使用会话/Cookie，原生移动端使用 Authorization Code + PKCE。
- 生成 `openapi-app.yaml`，用于第一方客户端类型/SDK、联调和契约检查，不作为外部兼容承诺。

### 8.2 外部合作 API

- 服务外部系统、合作伙伴及内部其他独立系统，建议使用 `api.<domain>` 的 `/v1/...` 资源路径，不返回面向页面的组合模型。
- 契约、版本、废弃日期和兼容周期独立于前端；写入接口明确幂等键、重试语义和调用审计。
- 生成并发布 `openapi-partner-v1.yaml`，用于 SDK、合同测试、破坏性变更检查和未来开发者门户。
- 使用独立集成客户端身份，不模拟普通用户登录。集成客户端关联租户、允许资源/操作、数据与字段范围、有效期、额度及状态，并进入统一 `AccessPlan`。

#### 8.2.1 已确认：集成客户端认证与治理

- 第一期使用 OAuth 2.0 Client Credentials。每个集成客户端固定归属一个租户，不允许通过请求参数、请求头或 Token 换用其他租户。
- 客户端凭据只用于换取短有效期 Access Token，不直接作为业务 API 访问凭证。服务端只保存密钥哈希或受控凭据引用，明文仅在创建时显示一次。
- 同一客户端允许短暂并存两个有效密钥，支持无停机轮换；密钥记录创建、最后使用、到期和撤销时间。
- 高安全集成可在 Client Credentials 之上启用 mTLS 并绑定证书指纹。普通 API Key 不作为默认认证方式。
- Token 可包含客户端标识、租户标识、协议作用域和授权版本，不携带完整数据/字段策略。后端核对客户端、租户、凭据和授权权威状态，不仅信任 Token 内容。
- 客户端停用、密钥撤销或授权版本变更后必须及时拒绝已签发 Token；具体采用短 Token 有效期、权威版本校验和撤销缓存组合。
- 外部写入接口默认要求 `Idempotency-Key`，按租户、客户端、接口操作和幂等键建立唯一性。相同键与不同请求摘要冲突时拒绝，不重放第一个请求以外的载荷。
- 同时支持客户端级、租户级和接口级限流与日/月额度；限流和额度不代替业务并发控制。
- 调用审计记录客户端、租户、契约版本、接口操作、结果、耗时、流量、幂等键摘要与 `traceId`，不记录密钥、Token 或完整敏感请求。
- 第一期可由平台应用提供 Token 端点与基础治理；未来接入独立身份提供方或 API Management 时保持 OAuth 2.0 协议和业务授权边界。

### 8.3 共同契约规则

两类 API 均明确 DTO、分页、排序白名单、时区与币种含义，资源标识与业务编码分开。OpenAPI 是机器可读契约，不代替 Spring Security、操作授权或数据权限执行。

- 成功响应直接使用资源 DTO 或统一分页结构，不再包装通用 `Result<T>`。
- 错误采用 RFC 9457 `ProblemDetail` 语义，扩展稳定业务码、翻译键、受控参数、`traceId` 及字段错误；HTTP 状态反映认证、授权、冲突及输入错误。
- 前端不能依赖翻译后的句子判断业务结果。
- 写入契约支持幂等键、预期版本和明确的字段变更语义，按用例声明是否要求。
- 外部可见的对象不存在与无权访问响应避免泄露敏感对象存在性。
- OpenAPI 描述认证方式、作用域与错误，不向普通业务用户展示内部堆栈。

## 9. 建库、升级与恢复

租户创建在共享库本地事务内完成租户目录、初始配置和首位管理员成员的写入，所有租户数据使用新租户的 `tenant_id`。复杂初始数据可由可重入步骤任务补充，初始化成功前不启用租户。

Flyway 针对共享库统一运行。发布包声明支持的结构版本；大量数据回填不在单个长时间 Flyway 事务中遍历全部租户，而由可观测、可重入的分批任务执行。

### 9.1 已确认：迁移执行机制

- 共享库结构升级在受控发布阶段由单一迁移执行者完成，应用实例不同时竞争执行。
- 数据回填任务记录批次范围、租户或主键游标、租约、尝试次数和错误摘要；单批失败可重试，不破坏已完成批次。
- 已发布的 Flyway 脚本禁止修改，修复使用新的版本化脚本。生产环境禁用 `clean`，`repair` 只能作为受控运维操作，须审批并记录。
- 升级支持分批、并发上限和暂停。破坏性变更使用“扩展 → 数据迁移/回填 → 切换读写 → 收缩”；收缩前必须确认所有受支持应用版本已停止使用旧结构。

备份恢复使用运维控制状态暂停目标租户写入与任务。需要覆盖数据库、文件和平台关联。授权撤销记录须有独立于被恢复快照的校验依据；恢复后先核对撤销记录、会话、数据库版本与成员关系，再开放。该依据的存储位置、保留期和灾难恢复流程仍待专项设计，未解决前不得声称可防止旧权限复活。

## 10. 验证与工程约束

技术验证范围不涉及具体业务系统，采用最小资源验证底座行为。

| 验证项 | 通过条件 |
|---|---|
| 租户隔离 | A/B 库同标识数据互不泄露；无上下文、伪造上下文均拒绝 |
| 行级隔离 | A/B 租户同 ID 数据不互见；所有 CRUD、联表、子查询、批处理和分页计数都带正确租户条件 |
| 上下文攻击 | 伪造/缺少租户均拒绝；事务中和旧异步任务不能切换或误用租户 |
| 权限组合 | 不产生跨授权拼接；强制限制、字段脱敏、查询限制一致 |
| 权限失效 | 禁用、移除、角色变化与并发请求满足确定的生效边界 |
| 聚合并发 | 最后一名管理员保护、组织防环、授权版本冲突有效 |
| 可靠事件 | 事务回滚无事件，重复和乱序可处理，租户事件不跨租户消费 |
| 生命周期竞态 | 移除旧事件不影响重新加入后的新授权 |
| 国际化 | 中英文回退、时区及金额格式正确且不改业务日期 |
| 迁移恢复 | 创建重试不重复、升级失败隔离、旧备份不复活撤销权限 |
| 审计 | 成败准确、原值不泄露、查询不跨租户 |

使用真实 MySQL 验证路由、锁和事务，不用内存数据库替代这些验证。架构测试检查跨领域依赖；领域单元测试覆盖实际规则，不编写只重复 getter 或框架行为的测试。

AI 开发需遵循模块依赖、契约变更、数据库迁移及安全日志规范。每项实现对应设计条目和验收证据，禁止以生成代码数量作为完成标准。

## 11. 推荐实施顺序与待决清单

本文不授权开始实施。设计确认后的推荐顺序：

1. 锁定兼容版本、工程结构和行级隔离执行方案。
2. 验证双租户共享表隔离、事务和可靠事件。
3. 实现账号/租户/成员生命周期与创建流程。
4. 落实组织五聚合与权限引擎，接入授权管理。
5. 接入统一国际化、审计和配置管理。
6. 完成门户联调、迁移与恢复验证，形成底座验收。

仍须明确：版本与依赖清单、路由组件、会话载体、密码策略、权限生效并发边界、Outbox 领取协议、开通配置权威关系、国际化和权限第一期深度、审批未就绪时的配置审核、授权恢复校验依据及容量目标。


租户执行边界增量：/api/** 第一方业务入口经过账号/凭据版本校验及 TenantExecutionFilter，按服务端会话绑定重新查询有效租户成员。客户端 tenantId 参数及 X-Tenant-Id 不参与边界决定。上下文 VerifiedTenantContext 为不可变请求属性，finally 清理，不用 ThreadLocal，不向异步线程自动传播。异步用例须显式重新验证，当前不支持异步业务上下文继承。

GET /api/workspace/context 已接入此边界；成功响应包含 X-Tenant-Context-Version。缺少登录返回 401，缺少或失效租户返回 409，无法验证数据库状态返回 503。前端工作台准入改为调用该业务入口。此过滤器只建立请求身份边界，不代替业务操作授权、系统开通校验或 SQL 行级隔离；后者尚待实施，不能宣称租户业务数据已完整隔离。个人中心和 /bff/tenants 选择流程不需要预先建立租户上下文。

正式持久化已启用第一版单表租户 SQL 执行门禁：@TenantScoped Mapper 的固定 select/insert/update/delete 语句必须包含专用 __verifiedTenant 参数；prepare 阶段仅允许声明表名对应的确切 SQL 形状，并以不可被请求覆盖的已验证 BINARY(16) 租户值绑定。联表、子查询、OR/UNION、注释、多语句、动态表名、批处理、无标注 Mapper 和租户列修改均拒绝。无 VerifiedTenantContext 的请求立即失败；请求属性由 TenantExecutionFilter 在 finally 清理。MyBatis 二级缓存关闭、本地缓存为 STATEMENT，并强制 SIMPLE executor，避免缓存结果或批处理跳过租户绑定。

已用真实 MySQL 8.4 验证同 ID A/B 租户的查询/更新/删除隔离、缺少上下文拒绝和 OR 查询拒绝。测试夹具表只在集成测试创建，不进入生产迁移。

重要限制：此严格形状暂只支持显式标注 Mapper 上的单表 CRUD，不是通用 SQL AST 租户改写器；使用租户表前 Mapper 必须标注 @TenantScoped 且 SQL 逐字符合允许形状。Mapper XML、联表读模型、join/subquery、批处理和后台任务尚未适配，生产新增这些形状会默认失败。注册生产租户 Mapper 之前必须经过隔离集成测试；复杂查询需后续设计显式安全读模型/适配器，后台任务需显式重新验证并建立上下文。该实现不自动保护绕过 MyBatis 的原生 JDBC。

Mapper 范围现在默认为拒绝：每个 Mapper 必须声明 @TenantScoped 并符合单表 CRUD 固定形状，或经审查声明 @PlatformScoped 用于平台级元数据/成员资格查询。未声明 Mapper 执行时失败关闭。@PlatformScoped 不是租户隔离例外，不得访问普通租户业务表。认证与租户目录 Mapper 已明确声明平台范围；业务 Mapper 需要通过对应接口和真实 MySQL 双租户测试后才能注册。


平台级 Mapper 白名单也由 JSqlParser 在 prepare 阶段校验 SQL 实际引用表；所有引用表须包含于 @PlatformScoped 的精确白名单，解析失败或包含白名单外表均拒绝。该检查是租户边界的额外闭环，不代替字段/操作授权。新增平台 Mapper 时必须以真实 MySQL 测试证明越权表引用会被拒绝。


组织持久化首批：新增 OrganizationUnit 不可变模型和仓储公开端口，V5 迁移创建 tenant_organization_unit，复合主键为 (tenant_id,id)，名称租户内唯一。正式 MyBatis Mapper 支持当前租户列表、新建、改名、删除；SQL 白名单仅增加对应固定形状，专用租户绑定仍由验证上下文覆盖。真实 MySQL 测试以 A/B 租户相同 UUID 验证列表、更新与删除隔离。

组织操作授权、组织类型/树关系、并发版本及操作审计尚未实现，因此本批不注册组织业务 HTTP API 或前端菜单；有效租户成员身份不等同于组织管理权限。本批是组织隔离仓储增量，不是完整组织管理功能。

组织授权首批已进入正式 authorization 域：READ/CREATE/UPDATE/DELETE 权限码、租户成员维度显式授权表及 OrganizationAuthorization 判定端口已接入；SQL 白名单仅允许授权存在性查询。TenantExecutionFilter 按实际 HTTP 方法将组织单元路由映射到对应能力，在 Controller/Mapper 执行前失败关闭，租户成员身份本身不授予组织操作。

授权模型测试覆盖默认拒绝、租户/成员/能力隔离、到期及撤销拒绝。组织 API 和菜单仍未开放：本批没有任何授权授予接口或首个管理员捷径，不能通过 SQL fixture 或初始化账号给生产用户隐式授予权限。下一步需先实现受控的角色/成员授权管理、操作者权限和授权审计，再开放受保护的组织端点与 UI。


组织授权生命周期增量：新增 GRANT 管理能力，以及 V7/V8/V9 迁移（撤销操作者、追加审计、GRANT 类型）。POST /api/organization/grants 与 DELETE /api/organization/grants/{memberId}/{capability} 使用服务端租户成员上下文校验 GRANT，复核目标有效成员并在同一 MySQL 事务写授权和审计。仅允许 READ/CREATE/UPDATE/DELETE，管理能力不可通过接口委派；GET 列表也要求 GRANT。没有默认授予或首个成员特权，初始管理者来源仍需受控运维治理，本批不提供自助初始化入口或授权 UI。

授权管理存在性查询使用明确表白名单；普通成员调用与跨租户目标默认拒绝。此为组织能力授权子集，不代表完整 AccessPlan、角色继承、数据/字段权限或授权委派产品已完成。授权变更在事务内固定顺序锁定租户、目标/操作者成员和 GRANT 授权行，避免校验后状态变化；并发容量与完整委派模型仍待后续验收。组织 CRUD API 继续不开放，授权管理只面向已由受控运维授予 GRANT 的成员。
