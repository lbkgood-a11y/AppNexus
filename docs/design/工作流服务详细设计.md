# 工作流服务详细设计

日期：2026-11-10。状态：统一命名及首批运行时、持久化、API和工作台已实现，真实业务接入及浏览器验收未完成；实现矩阵与验证范围见[工作流服务构建交付](工作流服务构建交付.md)。本文件需求范围大于当前已验收能力。

## 0. 服务定位与职责边界

workflow-service 统一编排人工审核、业务办理、受控业务动作与异步结果。审批是工作流的一种使用方式，业务编排及可视化设计器纳入本次需求。
用户入口统一称“工作流中心”，前端模块规划为 frontend/modules/workflow；任务分类保留审批、办理，工作台使用“待我处理”“我已处理”“我发起的”“抄送我的”。前端模块已创建；菜单随迁移登记但默认停用，真实业务能力及引擎就绪后显式启用。

| 归属 | 负责内容 | 边界 |
| --- | --- | --- |
| 工作流服务 | 流程定义与版本、实例、节点、人工任务、动作与流转、执行历史、业务对象关联 | 保存执行事实和必要快照，不拥有业务单据状态，不直接写业务表 |
| 业务服务 | 单据及其状态、业务字段、评分或评价等办理数据、业务校验、生效及撤销规则 | 不直接完成引擎任务或修改工作流表；通过公共契约确认办理结果 |
| 平台能力 | 可信身份、租户成员、组织选人所需查询、授权、强制访问限制及脱敏 | 任务分配不替代授权；工作流仅通过公开契约接入，不依赖平台实现 |

业务编排统一纳入本服务，不另建平行业务编排引擎。工作流决定何时执行什么、由谁执行及结果如何影响后续路径；业务服务负责实际业务执行，集成模块负责协议、凭据、限流和通信，作业模块负责调度、分片和批处理运行恢复。独立日志清理等技术作业无须创建流程实例。

### 0.1 统一人工任务模型

统一抽象为流程定义/版本、流程实例、节点、人工任务、任务动作、业务对象关联及执行历史。
审核节点和办理节点共享任务生命周期、选人、多人完成规则、授权、期限、审计及并发控制。

- 决策型节点产出决定，例如通过、拒绝，按决定选择后续路径。
- 办理型节点产出业务完成结果，业务服务校验并确认完成后才允许推进。
- 节点允许组合业务填写与审核决定，不拆成两套任务引擎；设计器可以提供两类常用配置入口。
- 节点声明参与人规则、业务能力引用、输入要求、受限权限、可用动作、完成条件及流转规则。
- 业务能力由业务侧代码声明并受控注册，流程配置只能引用已开放能力，不接受任意 URL、脚本、SQL 或 Java 类。
- 节点可更新主单据，也可生成或关联其他业务对象；具体字段、存储和业务校验归业务服务，不向核心写入进仓、评分等专用逻辑。

### 0.2 状态、版本及业务衔接

单据状态与工作流状态分别管理，不要求一一对应。实例/任务执行状态、动作决定与业务结果引用分别记录；“拒绝”是决策结果，“评分”是业务能力，均不作为通用任务状态。
节点等待评分或填写时，实例仍在进行中；不因某一业务待补充就增加全局“待评分”“待评价”状态。需要暂停的特殊交互另行定义，不视为已经确认。

- 审批期间允许按需增补单据内容，可从工作台穿透到具体单据；业务服务依据身份、任务范围、字段及单据状态校验，穿透入口本身不授予编辑权。
- 暂存业务内容不自动完成任务。提交办理时，由业务服务确认内容及版本满足完成要求，再通过受幂等、并发校验保护的契约推进任务。
- 跨服务不依赖本地事务。后续以可靠事件、幂等、确认、重试和对账衔接；业务保存失败不得推进，重复提交不得重复流转。确认后内容再变更的并发约束须在接入契约中确定。
- 工作流结束不等于业务生效。结果投递或业务执行失败单独跟踪，不覆盖已经形成的流程结果，也不要求重复审核。
- 驳回后允许修改；重提建立新实例，关联同一业务对象、提交版本及历次实例，保留原意见和办理记录。
- 发布版本、节点策略及必要业务依据保留快照。增补保留变更记录；节点要求的评分、评价属于正常办理；其他增补受业务契约限制，影响已有审核依据的变更必须重审，不得静默沿用原决定。具体字段及重审路径由接入契约细化。

### 0.3 验证场景与未决事项

WMS 进仓单是首个接入场景；考核评分用于验证办理型能力。两者均为抽象模型的验证用例，不作为核心类型或字段模型。
已确认规则见第 0.5 节；具体业务能力契约、结果码、版本并发协议、字段清单、重审路径、授权接口及异常恢复操作权限仍需在详细设计中细化。两类通用执行链路已有隔离测试适配器验证，真实WMS/考核业务尚未接入。

### 0.4 命名切换

统一使用 workflow-service、workflow-contracts、com.appnexus.workflow、com.appnexus.contracts.workflow 和 WorkflowContext。
配置统一为 app.workflow.engine.enabled / APP_WORKFLOW_ENGINE_ENABLED，默认 false；引擎名为 appnexus-workflow。
这是骨架阶段的命名切换，不提供旧配置或旧 Java 类型兼容别名；已有本地启动配置需同步更新。改名不迁移或删除数据库，也不证明既有部署的引擎元数据兼容性；如已有持久化实例，切换前必须单独核验。

### 0.5 本次确认的完整需求基线

以下均为已确认需求；是否实现及验证以构建交付记录的逐项矩阵为准。

#### 流程模式与结束边界

- 审批型：实例结束表示审批决定已形成，结果通过可靠事件交付业务服务；业务生效及下游处理独立跟踪，不重新打开原实例。
- 端到端业务型：审核、办理、业务生效、下游传递及异步等待均可作为节点，定义中的步骤完成后实例才结束。
- 设计器明确展示完成边界，审批流程可作为子流程复用；复杂子流程能力分批完善。
- 审批型的结束结果与待交付记录必须原子落库，不能依赖结束后一次临时 HTTP 请求。通过、拒绝、撤回等结果可绑定受控业务处理能力，配置随版本冻结。
- 业务服务校验租户、单据版本和关联实例，以幂等方式更新单据，并在同一业务事务写入自身 Outbox。下游依据业务生效事件衔接，不直接将审批通过等同于业务生效。
- 流程终态、业务单据状态、交付/动作执行状态独立记录；结果交付失败可追踪、重试和人工恢复，不覆盖审批事实。复杂下游链路可触发关联的后续流程。

#### 任务、修改及恢复规则

- 同一单据、同一流程用途默认只允许一个运行实例；不同用途可分别发起。驳回修改重提建立新实例，旧结果不能误更新新提交。
- 任务创建时解析办理人并保存选人依据。成员禁用立即停止访问；离岗未办任务待重新分配，无人办理暂停告警，禁止自动通过。
- 审核支持会签、或签、依次审批；办理节点区分每人分别填写与多人共同完成一份内容，由节点配置，具体并发和汇总协议后续细化。
- 节点内规定填写正常办理；影响已审核依据的其他修改必须重审，保留版本和变更依据。
- 退回目标受流程限制，撤回须由业务服务确认允许；转交、委托、加签分别授权。回退不自动撤销已发生业务，补偿只能使用业务方显式提供的能力。
- 技术错误有限重试，业务错误进入人工处理；重试次数、间隔和超时按能力及节点约束配置，具体默认值在配置详细设计中确定。关键节点不允许任意跳过，所有恢复操作记录原因和审计。

#### 匹配、授权及办理界面

- 按单据类型、组织和条件自动匹配流程；未匹配或匹配冲突阻止提交并明确提示，不由用户任意选择。
- 租户业务管理员可在授权范围内编排，只能使用已注册且已授权的能力。编辑、发布、运行管理分别授权。
- 发布版本不可修改，新版本默认只影响新实例；首批不支持在途实例迁移。
- 支持工作台内办理及穿透业务页面两种方式，由业务能力提供办理界面契约，共用后端校验和任务权限约束。

#### 编排工作台与首批交付

- 工作流中心包含任务工作台、编排工作台（设计器）和运行管理；设计器是正式交付范围，不作为可选扩展。
- 设计器覆盖开始/结束、人工审核、人工办理、自动业务动作、异步等待、条件分支、并行汇合和子流程模型。复杂子流程与复杂补偿逐步完善，首批不承诺完整配置能力。
- 配置参与人、多人完成规则、输入要求、受限权限、动作、期限、输入输出映射、条件、超时、有限重试和失败路径。条件采用受控编辑器，不开放任意脚本。
- 支持草稿、权威校验、隔离的测试运行、版本比较、发布和停用；测试运行不得对生产业务产生未授权副作用。后端校验能力存在性、输入、选人、分支覆盖、并行汇合和异常路径。
- 前端编辑带版本的模型，后端权威校验并编译 BPMN；保留模型、BPMN 和策略快照，不承诺任意 BPMN 双向无损转换。
- 首批验收覆盖设计器、审核/办理人工节点、自动动作、条件分支、并行汇合、异步等待及运行管理，跑通发布、执行、业务结果和失败恢复闭环；复杂补偿与在途迁移不在首批。
- 具体试点继续使用 WMS 进仓单；办理型节点须接真实业务验证填写、暂存、提交和字段授权，具体首批业务对象尚待选定，不能用流程图发布替代业务验收。

## 1. 已确认的架构

工作流服务位于 backend/services/workflow-service，与 platform-service 平级。
初期由 platform-service/application 的既有 PlatformApplication 显式装配，同一 JVM 运行，
不搬迁启动路径、不增加端口。启动模块是引用双方实现的唯一例外。
未来独立运行时新增工作流启动装配即可，不将平台实现依赖带入工作流核心。

Flowable 内嵌于工作流服务，属于内部执行引擎，不另行部署 Flowable REST 应用。
仅 adapters/flowable 允许引用 org.flowable；core 不引用框架。
跨服务入口使用 contracts/workflow-contracts，不暴露引擎实体或领域内部对象。
现阶段不为尚未实现的 HTTP、持久化、组织适配创建空模块。

## 2. 工程与依赖

```text
backend/contracts/workflow-contracts
backend/services/workflow-service
├─ core
├─ adapters/flowable
└─ architecture-tests

platform-service/application → workflow-flowable-adapter → workflow-core → workflow-contracts
```

组合启动不授予平台领域访问工作流内部实现的权利。架构测试约束：

- 工作流实现不得依赖 com.appnexus.platform 下的实现。
- 平台代码除 PlatformApplication 外不得引用工作流实现。
- 工作流核心与公共契约不得依赖 Spring、Flowable 或适配器。
- 只有工作流 Flowable 适配器允许直接引用引擎。
- 公共契约不得暴露双方实现。

Maven 编译依赖限制核心的可见范围；ArchUnit 检查组合应用类路径上的代码访问。
这属于构建期约束，不是 JVM 安全隔离，也不防止反射、动态 SQL 或人为绕过测试。
未来新增跨服务接口须评审事务、错误、权限与幂等语义，不因同进程省略校验。

## 3. 引擎装配与配置

锁定 org.flowable:flowable-spring:8.0.0，不使用自动开启多个子系统的 Boot Starter。
引擎名称 appnexus-workflow。初期复用平台数据库连接池和事务管理器，
引擎表与未来工作流业务表归工作流服务所有，其他服务不得直接访问。
运行时禁止自动建表或自动升级；版本匹配和引擎表由受控迁移负责。
异步执行器固定关闭；后续完成租户上下文、线程池隔离和失败恢复后再增加配置。
不开放原生 Flowable REST 接口、任意脚本、表达式或 Java 类配置入口。

| 配置项 | 环境变量 | 默认值 | 用途及生效约束 |
| --- | --- | --- | --- |
| app.workflow.engine.enabled | APP_WORKFLOW_ENGINE_ENABLED | false | 是否装配内嵌引擎；仅表迁移完成后可启用，缺表时启动失败；同时装配工作流API，不自动启用交付扫描或Flowable异步执行器 |

Flowable 使用 Apache-2.0；后续引入设计器与其他依赖须单独核查许可证。
编译与容器测试只证明当前验证范围，不代表全部引擎能力或升级路径已验收。

## 4. 业务与安全约束

延续既有审批默认规则：按单据归属组织选人；空审批人暂停并告警；默认不允许自审；
支持会签、或签、依次审批；转交、委托、加签分别授权；退回目标受流程限制；
撤回同时检查审批进度和业务生效状态；超时不自动通过。

任务分配记录不能替代平台授权。工作流应用入口必须重新校验可信身份、租户成员资格、
任务所有权、字段范围及强制脱敏。任务结束收回处理权限，历史查看受租户策略约束。
WorkflowContext 只是显式调用上下文，不是认证凭证，也不自动完成幂等处理。

工作流服务维护流程执行事实，业务服务维护单据状态。后续通过可靠事件、幂等和对账衔接，
不得依赖跨服务本地事务；已实现工作流交付表、受控业务结果回传及流程推进；业务单据状态推进由真实业务适配器实现，尚未接入WMS/考核。

## 5. 设计器与前端边界

前端功能归 frontend/modules/workflow，复用 vue-pure-admin、Element Plus 与平台公共组件。
已创建真实API对接前端模块；不注册生产模拟业务能力，菜单默认停用。
优先简化工作流设计器，前端编辑带版本的工作流 JSON；后端负责校验、编译为 BPMN 并发布。
高级 BPMN 编辑器按需要引入成熟内核；不承诺任意 BPMN 与简化模型双向无损转换。
发布时保留 JSON、BPMN 与策略快照；不允许编辑已发布定义悄悄改变历史。

选人、条件字段、流程发布权限均由后端契约约束，不直接开放引擎部署能力。
现有组件不适用而新增工作流专用组件时，须记录需求、已检查组件及具体原因。

## 6. 后续实施顺序

1. 定义单据接入、发起与任务处理契约，确定业务状态、幂等和失败语义。
2. 建立受控引擎迁移与工作流业务表；验证升级、备份和恢复。
3. 接入组织选人、租户隔离及任务受限授权，完成审核与办理最小闭环。
4. 实现可靠事件、业务结果确认、失败重试和对账。
5. 交付任务工作台、编排设计器、版本发布及运行管理，完成第 0.5 节首批能力与闭环验收，再完善复杂子流程、补偿、加签、退回、委托及催办。

本节为实施顺序；当前完成度见构建交付记录，未以需求条目代替实现验收。
