# 统一事件模型详细设计

日期：2026-11-19。状态：第 4 节为已确认的平台事件信封标准；其余章节说明实施设计及首期兼容边界。基于[职责归位审查](事件与合作方接口职责归位审查.md)和当前 MySQL Outbox；现有多消费者投递及运维接口以第 13.1 节和验收记录为准。统一信封的生产接入、外部消息代理及外部消费者仍需分别实施与验收。

## 1. 目标与基本决策

建立业务事实的可靠传播机制，服务当前模块化单体，并为未来跨进程集成保留边界。默认采用同库事务 Outbox、固定代码订阅、独立消费者投递、至少一次交付与消费幂等；第一期不引入 Kafka/RabbitMQ，不使用 Redis Pub/Sub 代替可靠存储。

关键约束：

- 事件描述已经发生的事实；发布成功是随业务事务持久化成功，不代表消费者完成。
- 事件身份与内容不可变，投递、尝试与消费凭据独立；某个消费者失败不影响其他消费者已经成功的结果。
- 没有跨系统“恰好一次”承诺；同库副作用可通过事务和唯一键保证不重复提交，外部副作用依赖对方幂等/查询或人工核实。
- 事件不是授权凭据，不承载完整登录主体或 Token；同步撤权继续依赖权威库，不等待异步传播。
- 完整模型不等于一次实现全部能力。订阅、回放、跨进程传输只有接通真实执行器并验收后才能开放。

## 2. 四种消息语义分别建模

| 概念 | 含义与用途 | 对当前项目的约束 |
|---|---|---|
| 领域事件 | 某上下文内发生的业务事实，可先作为纯 Java 值 | 归业务所有者，不自动对外暴露、不要求所有领域事件持久广播。 |
| 集成事件 | 经过公开契约筛选、供其他上下文或进程消费的事实 | 由发布方负责语义、版本、数据最小化；不能直接序列化领域实体/数据库行。 |
| 命令 | 请求某个明确接收方执行操作，可被拒绝 | “发送验证码”“撤销指定会话”是命令；不能冒充已完成事件。执行成功后才产生相应事实。 |
| 定时/后台任务 | 有计划时间、进度或人工调度的工作 | 可复用租约等技术机制，但保持独立任务契约，不把所有任务类型注册成业务事件。 |

例如“客户端授权已变更”可以供多个消费者接收；“请同步外部 IAM”是一个确定目标的命令；只有对方确认后才能记录“外部 IAM 同步已完成”。补偿同样是新的业务操作，不通过修改旧事件伪造历史。

## 3. 模型职责与代码归属

| 层次 | 责任与建议公开边界 | 禁止事项 |
|---|---|---|
| 发布方领域/应用 | 定义事件语义、决定何时发生、业务版本、输出事件端口；授权继续保留 AuthorityEvents | 依赖 JdbcTemplate、eventing 适配器或通用发布接口来绕过自身不变量。 |
| 事件支持能力 | 统一事件信封、订阅/投递/重放状态规则、运行管理用例与输出端口 | 决定角色、商品、组织等业务规则或成为万能业务总线。 |
| eventing 适配器 | 序列化校验、订阅快照组装、调度、租约、处理器连接、外部传输桥接 | 导入其他上下文 internal，或代替业务消费者做授权和状态决定。 |
| persistence 适配器 | 事件、投递、尝试、回执等固定 SQL 和技术存储；保留统一 Flyway 历史 | 业务模块自行查事件表、按任意 SQL 发布或跨上下文读取业务表。 |
| 各消费方 | 通过自身输入用例处理，定义幂等与失败分类；handler 只是受控集成桥接 | 直接操作发布方表、按 payload 任意类名/URL 分发、把外部调用伪装同库事务。 |
| platform-api / security / 组合应用 | 分别负责运维 HTTP、可信主体与授权、安全技术、具体实现装配 | Controller 编排重试事务，security 持有全部事件状态机，装配类承担业务决定。 |

现有 adapters/eventing 作为真实技术迁移目标。建议在实际实施设计中建立纯 Java 的平台事件支持模块 `services/platform-service/eventing`（建议 artifactId `platform-eventing`、根包 `com.appnexus.platform.eventing`），承载真实投递/运维状态模型及公开端口；它是支撑能力，不是新的部署单元。职责依平台标准分为公开根包、port、internal.application/domain。该模块尚不存在，本次不创建空 POM；实施时先同步架构和命名规范的模块表，并用实际用例与测试同时交付。

领域只依赖自己的事件输出端口。eventing 集成桥接实现发布方输出端口，并依赖支持模块公开输入端口；persistence 实现支持模块的输出端口。各 handler 经装配接收消费方公开输入端口，不产生 API/security/eventing 循环。运维输入端口归事件支持能力，platform-api 仅调用。

`contracts/platform-events` 不作为所有事件的公共仓库。当前进程内事件语义归发布方公开边界；未来确有独立版本的跨进程平台事件时，才在此承载相应稳定传输 schema。通用信封与内部状态、Spring 类型、租约和数据库 PO 不导出给外部。

## 4. 事件信封与负载

下表是平台新事件的统一契约。必填字段为 eventId、eventType、schemaVersion、occurredAt、source、scope、scopeId、aggregateType、aggregateId、payload。发布身份和管理域由服务端发布适配器构造；跨进程接收必须经过已认证来源映射。

| 字段 | 含义、范围与缺省 |
|---|---|
| eventId | 必填，服务端分配的稳定 UUID；一次事实一次 ID，重投、重试、传输恢复不更换；历史迁移保留原 ID。 |
| eventType / schemaVersion | 必填，发布方命名空间内的稳定事实名与从 1 开始的正整数结构版本；类型格式为 <业务上下文>.<聚合>.<已发生事实>，例如 settlement.bill.confirmed。类型名不嵌入版本。旧大写类型仅在迁移适配处映射。 |
| source | 必填，代码登记的发布上下文稳定标识，不是实例主机名或任意客户端文本。 |
| scope / scopeId | 必填，PLATFORM/TENANT 和规范化 UUID；平台使用现有零 UUID 边界，租户域拒绝零 UUID。所有唯一键都使用这组非空范围。 |
| aggregateType / aggregateId | 必填，受控聚合类型与不可变业务标识；区分角色、成员、客户端等，避免同 ID 语义歧义。 |
| businessKey | 可选字符串，记录单据号等人工查询标识。按 aggregateType 和 aggregateId 稳定关联对象，有序消费另用流键及流序号。 |
| aggregateVersion | 可选非负业务版本；用于新旧判断，没有版本时为空，禁止用迁移顺序或当前查询结果伪造旧版本。 |
| orderingKey / streamSequence | 声明顺序时必填，范围内固定流键与事务分配的正整数流序号；无序事件允许为空。业务版本、流序号、schemaVersion 三者不同。 |
| occurredAt / recordedAt | 新事件必须提供 ISO 8601 UTC 事实时间，后者为内部数据库写入 UTC 时间；前者不能代替排序/提交证据，后者由数据库生成。历史发生时间未知保持 NULL。 |
| correlationId / causationId | 可选，业务链关联标识及导致本事件的命令/事件 ID；不作为授权或幂等唯一依据。 |
| traceparent | 可选且格式受控的链路上下文，采样/链路丢失不影响投递；不保存 HTTP 原始头集合。 |
| payload / payloadHash | 按类型版本登记的必填 JSON 对象，无附加字段时为 {}；规范化摘要为内部持久化元数据；禁止密码、密钥、Token、恢复码或任意对象序列化。 |
| actorAccountId | 可选，只能来自事实发生时的可信主体，仅用于业务追溯；系统执行为空，不据此重建用户会话。 |

事件实体业务内容不可变；四审计列仅描述落库及技术维护，不把更新投递状态写成事件事实发生人/时间。schema 变更需兼容检查，增可选字段不能偷偷改变语义；必填变更、删除或类型变化采用新结构版本并提供旧版解码/映射及升级期兼容矩阵。

当前两个事件继续仅存受控标识，不趁迁移扩入敏感原值。变更型通知采用“收到后读权威当前状态”；涉及历史通知或结算的消费必须使用有授权的不可变快照，不能取最新值冒充当时事实。

以下示例为租户内的结算单确认事件，使用可选单据号辅助排查。

  "eventId": "019ac0ef-3e80-7f41-8aa2-53b95d1c3a21",
  "eventType": "settlement.bill.confirmed",

  "source": "settlement",
  "scope": "TENANT",
  "scopeId": "2dc43ba2-08e6-4baa-844b-16ef70ae78fb",

## 5. 事件类型与订阅登记

EventTypeDescriptor 由发布代码登记类型、版本、来源、scope、schema、负载上限、顺序策略和是否必须存在订阅。ConsumerDescriptor 由消费代码登记 consumerId、支持类型/版本、执行模式、顺序模式、超时重试、回放资格和必要/可选级别。均为拟议概念，不是已有 Java 接口。

- consumerId 代表独立业务用途，不代表 Pod/线程/部署实例；同一 ID 的多实例竞争同一投递，不同 ID 各得一份。业务语义变更不能靠随意改名规避旧回执。
- 注册必须连接真实 handler，并校验重复 ID、无法识别类型/版本、租户域不匹配、环形模块依赖和无执行器；必需订阅缺失阻止发布或启动就绪。
- 使用代码白名单匹配类型、版本、scope，不接受管理员 SQL、SpEL、Java 类名、任意过滤脚本或 URL。过滤可以使用经过 schema 校验的固定元数据，不读取任意业务表。
- 管理员可暂停调度、恢复及受权重试，不可在线添加任意 handler 或改变事件含义。暂停不等于退订：已发布和新发布的投递继续生成，只是不执行。
- 每次发布固定订阅集合与契约 revision，并把集合摘要和预期投递数量保存下来。零订阅仅对明确允许的类型合法，记录 NO_SUBSCRIBERS，不能把必需消费静默丢掉。
- 首期采用同事务扇出，事件和所有匹配投递原子创建；超过上限拒绝整次业务事务，不部分成功。后续如采用异步扇出，必须设计持久订阅快照与幂等扇出状态，本期不混用。
- 发布进程必须拥有完整的代码订阅清单，即使某 handler 实际部署在其他 Worker。滚动发布时保持订阅清单 revision 的兼容部署，遇到未知已登记消费者就暂停而非删投递；不以服务发现瞬时在线实例决定订阅者。
- 新增消费者默认只接收启用切点后新事件，不自动补历史；退订只影响未来事件，未完成投递由明确迁移/人工取消处理，不能静默删除。

## 6. 持久化模型及约束

以下是逻辑数据模型，尚未确定新 Flyway 版本，也未执行 DDL。所有自有新表首次 CREATE TABLE 都必须直接包含 `created_by BINARY(16)`、`created_at TIMESTAMP(6)`、`updated_by BINARY(16)`、`updated_at TIMESTAMP(6)` 和准确中文列注释；时间由数据库 UTC 生成，账号来自可信上下文、无账号时 NULL。此约束覆盖本节所有表，包括追加尝试、回执、序号与回放任务。

| 拟议表 | 关键字段/约束 | 职责与所有权 |
|---|---|---|
| platform_event | eventId 主键；scope/scopeId/source/type/version/aggregate/负载及摘要；订阅快照摘要、预期投递数；可选生产幂等键 | 不可变事实，由事件支持能力管理，发布方负责语义。外部来源以 source+来源事件 ID 唯一去重。 |
| platform_event_delivery | deliveryId 主键；eventId、consumerId、消费代次 generation；scope；state、attemptCount、nextAttemptAt、leaseToken/fence、leaseUntil、订阅/处理策略快照 | 唯一(eventId,consumerId,generation)；首期 generation=live。消费者独立投递状态，禁止一次完成修改兄弟投递。 |
| platform_event_attempt | deliveryId、单调 attemptNo/fence、开始/结束时间、结果码、时延、受控外部请求标识 | 追加诊断记录，唯一(deliveryId,attemptNo)；不记录原文异常或敏感 HTTP 正文。 |
| platform_event_receipt | scope/source/eventId、consumerId、effectGeneration、处理摘要、完成时间 | 消费幂等凭据；与同库副作用同事务。live 回放仍命中原回执；重建投影使用独立明确代次。 |
| platform_event_stream | scope/source/orderingKey、lastSequence、版本 | 只对顺序流使用；同业务事务锁定流并分配序号，避免 UUID/自增号当提交顺序。 |
| platform_event_replay | jobId、受控过滤条件/边界、目标消费者与代次、原因、操作人、进度、状态、限速 | 有权回放任务；记录审批/确认依据、上限与历史快照，不允许任意 SQL。 |
| platform_event_admin_action | 操作 ID、目标事件/投递/回放、动作、原因、前后状态、可信操作者 | 追加审计，取消、解阻塞、重试、回放及清理有记录，不能仅覆盖 updated_by。 |

每张从表保存 scope/scopeId，并用复合外键或同等数据库约束验证与主事件一致；投递唯一键、回执去重键和查询都包含稳定来源/消费者含义。不能因为事件 UUID 唯一便放弃租户谓词。平台跨租户查询仅通过明确平台运维授权入口。

索引至少覆盖：消费者+状态+可执行时间；租约到期；scope+事件时间+ID；eventId 下投递汇总；scope+consumer+orderingKey+streamSequence 顺序查询；attempt/receipt 唯一约束。领取 SQL 对 due 与 expired 分支分别使用可用索引，批量锁定上限和 EXPLAIN 在实施中验证，不以 OR 扫描宣称可扩展。

逻辑事实状态和投递汇总分开。事件可汇总为 NO_SUBSCRIBERS、IN_PROGRESS、COMPLETED、ATTENTION_REQUIRED、CLOSED_WITH_EXCEPTIONS；COMPLETED 只能是快照中的全部投递 SUCCEEDED/SKIPPED。取消或转人工不能伪装全部成功。第一期汇总查询派生，若维护缓存计数须有事务更新及定期对账。

## 7. 投递状态机

| 状态 | 含义 | 可进入的后续状态 |
|---|---|---|
| READY | 已创建、等待领取；nextAttemptAt 到期才可执行 | PROCESSING；经受权操作 CANCELLED |
| PROCESSING | 本次租约持有者执行 | SUCCEEDED、SKIPPED、RETRY_WAIT、MANUAL、OUTCOME_UNKNOWN；租约到期按执行模式恢复 |
| RETRY_WAIT | 明确可安全重试的临时失败 | 到期 PROCESSING；取消前完成安全检查 |
| OUTCOME_UNKNOWN | 外部请求可能已经生效，不能直接判断成功/失败 | 经对方查询/相同幂等键核实后 SUCCEEDED、RETRY_WAIT 或 MANUAL |
| SUCCEEDED | 业务副作用和回执完成 | 不直接改回 READY；回放创建受控独立投递 |
| SKIPPED | 明确不需执行，如权威版本已更新，且有可核查原因 | 同成功，不自动重试；不能用于隐藏不支持版本或权限错误 |
| MANUAL | 超次数、永久错误、未知 schema、结果无法核实等，需要人工处理 | 授权重试 READY 或受权 CANCELLED，保留历史尝试/回执 |
| CANCELLED | 经授权放弃特定投递，原因永久记录 | 终态；不是成功，不清除外部未知结果或顺序缺口 |

暂停是消费者或任务的调度开关，不修改每条投递为成功/取消。MANUAL 充当持久死信队列，首期无需另复制 payload 到一套死信表。重试只针对目标消费者，不重置其他成功投递，不清空累计尝试历史；增加独立 retryCycle 和受控新预算。

## 8. 发布、领取、执行与恢复

### 8.1 发布事务

业务用例执行不变量与授权→更新业务/版本/审计→通过自己的事件端口构造事实→统一发布适配校验契约→持久化事件+订阅快照+各投递→同事务提交。任何一步失败整体回滚。不是业务提交后再发内存回调补写 Outbox；禁止异步线程拿到未提交事件执行。

发布幂等首先由业务命令幂等保证。调用重试不能每次生成新事实 ID；需要重复发布保护时使用受控生产幂等键（scope、source、命令请求键、事件用途/序号），同键同摘要返回原事件，同键不同摘要拒绝。一次命令可合法产生多个不同事实，不能只以 aggregateVersion 全局去重。

### 8.2 领取与租约

短事务读取可领取投递，FOR UPDATE SKIP LOCKED，写 PROCESSING、attemptNo、唯一租约 token 和递增 fence，然后提交领取。业务执行不持有批量领取事务；长任务通过固定频率心跳续租，续租必须匹配当前 token/fence。完成/失败/续租均条件更新并核对影响行数，旧 Worker 不得确认新租约。

过期恢复不是“所有任务直接 READY”：同库事务未提交则安全恢复；有外部副作用可能的任务进入核实路径或使用原稳定幂等键重试。租约只防本地状态被旧 Worker 改写，不能阻止已经发出的远程请求执行；需要对方幂等或 fencing 协议。

Worker 按 consumer 独立限额、公平轮询并设租户并发配额，单个失败/大租户不耗尽全部容量。失去租约时取消可取消的本地工作，禁止继续用过期上下文提交；已发出的远程操作仍按结果未知处理。

### 8.3 同库消费者

消费事务验证当前投递与范围→尝试写唯一消费回执→消费方应用用例执行同库副作用→写回执完成与投递成功→提交。回执插入竞争依赖数据库唯一键，不能“先查后做”。异常整体回滚；失败原因由新的短事务按有效租约记录。不能使用 REQUIRES_NEW 让副作用独立提交后再假装整体可回滚。

首次回执存在但摘要不同是契约/来源冲突，转 MANUAL，不按已成功吞掉。跨数据库的模块即使同进程也不能走此模式。

### 8.4 外部副作用与远程事件

远程执行前持久化“尝试已开始”和稳定 requestKey，再在数据库事务外调用。requestKey 从事件+业务消费者+业务效果代次生成，不含 attemptNo/leaseToken；租约恢复不换键。明确成功后本地短事务记录对方结果和回执，明确未执行的可重试错误进入 RETRY_WAIT，超时/断连/进程崩溃进入 OUTCOME_UNKNOWN。

对方支持幂等时按同键查询/重发；不支持时先查询结果、人工核实或明确选择允许重复的业务策略，不能声称恰好一次。短信验证码等带时效命令过期后不可重发，并需配额、撤销与供应商回执。

未来消息代理只增加“可靠传输消费者”：代理确认代表进入代理，不代表远端业务消费成功。远端先持久化 Inbox（即本侧 receipt/delivery 模型的接收入口）再确认代理，重复按 source+eventId+consumer 去重，死信与兼容由远端负责。消息路由不携带租约内部字段；外部来源认证、schema、安全限额全部先验证。

## 9. 顺序与并发策略

每个消费者显式选择：NONE（默认，无顺序承诺）、LATEST_VERSION（仅最新权威状态）、STRICT_STREAM（同一 scope/source/orderingKey 串行）。不承诺跨对象、跨租户或全局顺序。

- 权限失效和客户端授权变化优先 LATEST_VERSION：读取当前权威状态；可比较的版本只前进不后退，缓存失效不得使旧授权恢复。某旧通知重复不代表可以跳过必要的权威复核。
- STRICT_STREAM 的发布事务先锁定 stream 行并分配 streamSequence，和业务事实一起提交；不能用 UUIDv7 时间、created_at 或数据库自增号推断提交顺序。同一事务锁多个流时采用稳定顺序，防死锁。
- 领取条件为同消费者流内最早未解决的已路由投递；不同事件类型过滤产生的序号空洞不能当漏消息。不同消费者使用各自游标/前置投递，互不阻塞。
- 失败、MANUAL、未知结果阻塞该消费者该流，其他流继续。CANCELLED 不自动解除严格顺序屏障，必须审查前后依赖并通过受控解阻塞操作记录例外。
- 不按“上一条序号+1”全局假设补丢；需要业务版本连续性的消费者另定义间隙、快照补齐与超时处置。
- 严格流增加新消费者/历史补投时设置流切点或暂停实时流，不能在已处理新事件后直接补旧事件。跨进程乱序第一期不宣称支持严格顺序，需要远端缓存/游标/重排机制后再开启。

## 10. 错误、重试和处理策略快照

失败分类由受控错误码表达，不存堆栈、SQL、密钥、供应商原文：临时可重试、永久业务拒绝、安全/范围不符、契约版本不支持、结果未知、取消/过期。未知 RuntimeException 默认进入受限重试并告警，次数耗尽转 MANUAL；明确可能有外部副作用则优先 OUTCOME_UNKNOWN。

以下为建议缺省值，单位与修改影响集中列明；实施时放对应配置及相邻中文注释，允许每消费者受控覆盖并保存投递策略 revision。修改新默认值不暗改旧任务的有限重试预算。

| 参数 | 建议默认/范围 | 条件与影响 |
|---|---|---|
| 最大 payload | 64 KiB，建议允许 1–256 KiB | 按 UTF-8 编码后字节校验；超限回滚发布，不自动截断。首期两类失效事件只含小型标识。 |
| 单事件匹配消费者上限 | 32 个，允许 1–128 | 同事务扇出；增大会增加业务写入延迟与锁持有时间。 |
| Worker 轮询/领取批量 | 1 秒；每批 20 条，允许 1–100 | 仅领取调度；不把 20 个业务任务放在同一长事务。 |
| 每消费者/每租户并发 | 4 / 2，正整数且租户值不大于消费者值 | 同进程默认；多实例需通过数据库配额/租约验证全局限制，不能只靠 Semaphore 宣称集群限额。 |
| 租约/心跳 | 30 秒 / 10 秒 | 心跳小于租约，超时执行需续租；同库事务上限与锁等待需联动。 |
| 单次处理/外部请求超时 | 20 秒 / 10 秒 | 外部请求超时必须小于处理期限，超过进入失败或未知结果，不强行认定远端未执行。 |
| 最大自动尝试 | 5 次，允许 1–20 | 包含崩溃后的领取；人工新周期独立计数但历史总数不清零。 |
| 重试退避 | 基数 5 秒、上限 300 秒、0–20% 抖动 | 采用受限指数退避；合法 Retry-After 可延后，不提前突破限流。nextAttemptAt 用数据库 UTC 基准计算。 |
| 回放批量/速率 | 每批 100 条、每秒 10 条；均为正整数 | 与实时队列分配独立配额，避免回放拖垮正常业务。 |
| 已完成数据保留 | 暂无可自动启用的统一默认 | 各类型明确保留期限、去重窗口和法规需求后才启用清理；未知/人工/未完成记录不得按完成时间删除。 |

## 11. 回放、补投、重试和补偿

| 操作 | 事件身份/副作用规则 |
|---|---|
| 技术重试 | 原事件、原消费者、原业务效果幂等键，只增加尝试。 |
| 新消费者历史补投 | 原事件，新增该消费者 live 投递；需明确订阅启用边界、授权与历史 schema 可读性。 |
| 已成功任务重放诊断 | 默认 dry-run，不产生外部副作用，保留原 live 回执防重复。 |
| 重建派生投影 | 独立 rebuild generation、独立目标影子投影与回执；追平切点后受控切换，禁止直接冲写在线数据。 |
| 再发短信/重新打印等业务操作 | 是新的授权命令，具有新业务请求键与业务事实；不能用“回放”绕过重复执行限制。 |
| 补偿 | 业务所有者执行新的补偿命令/事实，引用原事件，不能把原成功改失败或删除原记录。 |

回放请求由平台受权运维入口提交原因、消费者、管理域、类型版本、范围/时间切点、数量上限及 dry-run；创建持久任务和审计。默认不允许跨租户汇总导出 payload。重建型回放需订阅声明可回放，外部不可逆消费者默认禁止强制清回执后重放。

在线回放与实时消费必须协调切点、顺序和配额；取消回放停止尚未领取任务，已发远程请求不能撤回，不伪造回滚。类型/版本不支持或 payload 已过保留期时明确报告不可回放，不读取最新业务对象来重造历史。

## 12. 安全、审计与运维

事件执行采用服务身份和消费方公开用例所需的受控能力，不还原发布者会话。租户边界从持久信封验证，payload 中的 tenantId/actorId 不能覆盖可信范围。租户停用/对象删除如何处理由消费者声明，事件存在不授予跨租户或停用对象执行权。

运维至少提供：事件及各消费者进度、尝试摘要、租约/下一次重试、关联链、人工队列、未知结果核实入口、暂停/恢复、单投递重试、受控取消/解阻塞及 dry-run 回放。复用 vue-pure-admin/既有管理组件，不新增独立运维 UI 体系。查询、重试、回放和取消分别登记操作权限，写操作保持既有平台 MFA/CSRF 及业务审计，Controller 只调用公开用例。

指标先从实际实现接入：发布量、未完成最老年龄、各消费者积压/成功/失败、租约过期、结果未知、死信、回放进度。租户/事件 ID 不作高基数指标标签，追溯走有权限日志和查询；告警值按真实负载定稿，本次不虚构已部署的监控。

数据清理需保证未完成事件及其快照存在；先满足各消费者、外部幂等键有效期与最大重投窗口，再清理事件 payload。即使清理 payload 也要保留必要幂等墓碑/回执和操作审计；禁止删除回执后让代理迟到消息再次产生副作用。实际备份恢复需对账远端结果，不能把恢复到旧数据库的重复调用视为新事件。

## 13. 当前模型的迁移方案

依据当前 [V40 Outbox](../../backend/services/platform-service/adapters/persistence/src/main/resources/db/migration/V40__transactional_outbox.sql)、[ReliableEvents](../../backend/services/platform-service/adapters/security/src/main/java/com/appnexus/platform/security/ReliableEvents.java)、[AuthorityEvents](../../backend/services/platform-service/authorization/src/main/java/com/appnexus/platform/authorization/AuthorityEvents.java) 和 [TransactionalAuthorityEvents](../../backend/services/platform-service/adapters/persistence/src/main/java/com/appnexus/platform/persistence/platformscope/TransactionalAuthorityEvents.java)。V41 名称虽包含 triggers，实际明确不创建触发器；发布仍是应用事务行为。

1. 先交付目标纯模型、端口和真实 MySQL 存储；所有新表首建四审计列及中文注释。新迁移版本实施时全仓查重，不修改 V40/V41/V80 等历史校验和。保留统一 Flyway、当前租户零 UUID 的平台边界。
2. 盘点全部事件发布方、Worker 和人工入口；准备明确维护窗口，停止事件相关写入或停旧应用，并停止旧 Worker、等待/核实所有在途租约后切换。只暂停 Worker 不能阻止旧发布方继续写旧表。回填和校验完成后新应用开放写入，不让旧新 Worker 同时竞争处理同一事实。
3. 保留原 eventId、租户、类型和原始审计。AUTHORITY_INVALIDATED/INTEGRATION_AUTHORITY_CHANGED 映射目标类型；旧事件未知 aggregateType/version/occurredAt 不猜测，用受限 legacy schema 标记并只接入现有失效 handler。
4. 旧 consumer authority-invalidation 映射唯一兼容订阅。已成功旧回执迁入 receipt；旧 DONE 不自动补新消费者历史投递。DONE 却缺回执的异常记录先对账，不能直接造成功凭据。PENDING 对应 READY，MANUAL 保留人工，PROCESSING 需在旧执行器退出后判定是否安全恢复；不清空尝试历史。
5. 回填只生成兼容消费者的投递，不凭未来设想生成缓存、会话或 IAM 空消费者。现有两类事件使用 LATEST_VERSION；新消费者通过明确切点注册，历史补投另走任务。
6. 切换发布到统一写入，保留 AuthorityEvents 等业务输出端口；旧 ReliableEvents 方法仅在迁移实现内部适配，不能成为永久双写。集成客户端更新/轮换仍与授权版本、旧 Token 撤销、审计及事件同事务。
7. 任务列表改为事件+消费者投递视图，旧 /bff/platform/tasks 的响应语义如有变化须同步前端和 API 契约；人工 retry 改为指定投递，不能重置整事件所有消费者。旧回执/表在完成对账和保留期后通过新迁移退役，不立即删除。
8. 切换前验证允许回退到旧版本；一旦新消费者已产生副作用，不可直接启动旧全局 DONE Worker 或回退旧库。后续故障采用暂停+修复/前向迁移，按事件 ID 对账。不把数据库回滚视为撤销已发出的远程操作。

### 13.1 独立事件工作台与首期切换契约

首期由平台事件运维域提供独立菜单。事件列表按类型、租户、时间和投递结果查询，事件详情列出消费方、状态、下次执行时间和尝试历史。事件用于定位和汇总，投递是人工重试的唯一操作目标。订阅仍由代码声明，首期仅支持同库副作用，历史补投、外部消费和严格顺序另行交付。

- 新接口为 `GET /bff/platform/events`、`GET /bff/platform/events/{eventId}` 和 `POST /bff/platform/event-deliveries/{deliveryId}/retry`。按平台管理域分别声明查询、重试与系统调度。首期沿用唯一的 PlatformTask Provider 和原平台角色授权，描述符升至 3，新增 listEvents、readEvent 和 retryDelivery 操作。人工恢复沿用 MFA、CSRF 和事务审计，新接口记录原因。
- 事件提交事务同时写入 `platform_event_delivery`，按租户、事件和稳定消费者标识唯一约束。每次领取和处理结果记录在投递尝试历史中。匹配回执、业务副作用和投递完成同事务提交。人工恢复保留回执和历史，按当前投递开启新的有限自动尝试周期。
- 业务消费注册支持同类型多个稳定消费者。两类平台权限事件仍保留原安全失效消费者，业务模块通过业务事件契约订阅。旧 Outbox 的状态列用于历史对账，实时查询和运维监控读取投递状态。
- 首期保留默认 5 秒调度轮间隔、每轮最多 20 条、30 秒租约和最多 5 次领取。临时失败按 10、20、30、40 秒退避，第五次失败转人工。永久错误直接转人工。领取后即执行，消费事务持有投递行锁并校验租约和范围。
- 存量兼容映射覆盖四类。两个权限事件归 `authority-invalidation`，入库过账及质检判定归 `inbound-batch-quality`。切换时保留原 ID、租户、已有回执、尝试次数和已知审计。缺回执的旧 DONE 对账后处置，缺失的逐次历史保留为未知。兼容映射也用于后续发布的同类型事件。
- 保留 `GET /bff/platform/tasks` 的原摘要、原权限、事件 ID 和最近 50 条语义。只投影具有固定旧消费者映射的事件，状态、次数和错误来自对应投递。保留 `POST /bff/platform/tasks/{id}/retry` 的事件 ID 契约，通过固定映射调用同一个单投递恢复用例。映射缺失或不唯一时拒绝，待调用方切换后按 API 生命周期退役。
- 维护窗口同时停止旧发布方及 Worker，确认在途事务结束后回填和对账，新旧 Worker 不混跑。新消费者产生业务副作用后的故障按事件与投递对账并前向修复。MySQL 验收覆盖四类回填、缺回执对账、租约竞争、并发人工重试以及只恢复目标投递。实际迁移版本为 V203。LEGACY_RECEIPT_MISSING 和 LEGACY_UNMAPPED 通过对账处理，双方重试入口均拒绝直接重新执行。

### 13.2 生命周期排查与操作

- 详情按事件、投递和执行尝试展示。当前契约提供事件标识、已有类型与修订号、范围标识、业务引用和审计信息。完整信封接入后增加事实时间、来源、聚合、单据号和有权查看的受控负载，并支持按事件 ID 和单据号精确定位。
- 时间线以真实落库创建时间、投递创建时间、尝试开始与结果记录时间为证据。结果区分成功、已有回执、失败和租约过期。当前最多展示最近 200 条尝试，缺失的历史明细保持未知。
- 投递显示待执行、处理中、成功和待人工。待执行且已有失败码时显示等待自动重试和下次执行时间。人工重试只针对所选投递，沿用原权限和原因审计，并刷新事件详情。长期目标是通过受控审计投影展示每次人工重试的时间及操作者。
- 验收覆盖同一事件下多个消费者独立变化、自动退避、转人工、人工排队后成功、旧记录缺少明细、权限拒绝和工作台布局。严格顺序和外部结果核实按分期能力接入。

## 14. 分期交付与验收矩阵

第一期必须闭环：类型与消费登记、完整信封、同事务扇出、多消费者独立状态、同库回执、租约/fence、有限重试/人工、租户与审计、现有两类事件迁移及运维查询/单投递恢复。提供带真实业务副作用的隔离测试消费者验证广播，不在生产登记虚构业务消费者。

第二期按真实需求交付外部副作用执行器及结果未知核实、可回放投影、严格顺序；未实现时拒绝相应 ConsumerDescriptor 模式。第三期如有独立部署才引入消息代理与远端 Inbox，不提前承诺跨进程严格顺序。完整设计保留这些边界，第一期验收不能宣称二、三期已支持。

| 验收主题 | 必须覆盖的结果 |
|---|---|
| 发布原子性 | 业务/审计/事件/全部投递同提交同回滚；事务外发布拒绝；同生产幂等键冲突拒绝。 |
| 广播与竞争 | 两个不同 consumer 各处理一次，一个失败不影响另一个；同 consumer 两个实例只能有效领取一份。 |
| 租约恢复 | 崩溃/失联恢复、心跳竞争、旧 fence 不能确认；副作用完成但确认前崩溃有正确恢复。 |
| 同库幂等 | 并发重复消费、失败回滚回执、回执摘要冲突、事务代理真实生效，不能独立提交副作用。 |
| 外部结果 | 成功响应丢失、对方重复接收、稳定 requestKey、无幂等供应商人工核实；明确不支持模式需拒绝启动/登记。 |
| 顺序与隔离 | 提交乱序、严格流前序失败、选择性订阅序号空洞、不同流不互阻，跨租户同 ID 拒绝。 |
| 登记升级 | 发布/消费滚动版本兼容、未知类型/schema/handler 拒绝、暂停仍建投递、新订阅不自动补旧。 |
| 回放与清理 | 成功 live 不重复副作用、投影代次隔离、回放切点、取消及保留策略、迟到消息去重。 |
