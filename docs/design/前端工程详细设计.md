# 前端工程详细设计

版本：0.2；日期：2026-11-05。

## 已确认的方向

- 使用 vue-pure-admin，以桌面浏览器为主，保留框架主要布局与交互。
- 第一期统一部署，支持门户与各系统独立地址，未来按需独立部署；暂不引入微前端。
- 必须模块化、结构清晰，与后端领域命名保持一致。
- 前端框架可替换、可升级，降低未来应用拆分成本；不让业务模块依赖后台模板内部实现。
- 采用 pnpm workspace、单一 `admin` 应用、领域模块化及 `infra/pure` 壳层隔离的总体结构已确认。
- 具体版本、模板适配点及验证结果仍属详细设计，尚未实施。

## 工程结构建议

建议采用 pnpm workspace，在同一仓库内提供显式包边界；第一期只有一个应用，不提前建立多个空应用。

```text
frontend/
├─ apps/
│  └─ admin/                  第一阶段应用启动和装配
├─ modules/
│  ├─ identity/
│  ├─ tenant/
│  ├─ org/
│  ├─ auth/
│  ├─ i18n/
│  ├─ config/
│  └─ audit/
├─ common/                   稳定类型与最小公共契约
├─ components/               跨领域组件与业务无关交互
├─ infra/
│  ├─ http/                  请求、错误、取消与追踪适配
│  ├─ security/              会话与权限适配
│  ├─ i18n-engine/           统一国际化前端运行能力
│  └─ pure/                  vue-pure-admin 壳层集成
└─ tests/                    架构与跨模块集成验证
```

目录名称与后端保持同义，前端不机械复制后端 DDD 四层。workspace 包名使用 `@appnexus/<名称>`，例如 `@appnexus/org`、`@appnexus/http`，通过作用域避免包名冲突，不重复堆叠前缀。

领域模块内部建议：

```text
org/
├─ api/                      接口 DTO、映射与调用
├─ model/                    前端类型、校验及纯业务展示规则
├─ application/              用例、组合逻辑与模块状态
├─ pages/
├─ components/
├─ locales/
├─ routes.ts                 框架无关的页面注册描述
└─ index.ts                  显式公开入口
```

复杂业务规则仍以服务端为准。模块内部可按规模合并文件，不为简单页面建立空层。

## 依赖与框架隔离

- 应用装配模块选择领域模块、服务地址、入口、导航及布局；模块不得反向依赖应用。
- 模块通过公开入口使用其他模块的能力，禁止导入对方内部页面、Store 或私有文件。
- 业务模块不得直接导入 vue-pure-admin 内部路由、权限工具、布局、标签页或全局 Store。
- `infra/pure` 将页面注册、菜单、布局、主题、标签页等契约适配到模板；模板升级主要落在适配层和应用壳。
- HTTP、会话、权限、国际化通过统一入口使用，不在页面重复创建实例。
- Vue Router、状态管理和 UI 库的使用限制在表现层或适配层；纯类型、规则及用例不依赖模板内部。
- 不要求包装全部 UI 控件；优先封装权限字段、组织选择、金额日期、列表查询等稳定复用能力。
- 引入依赖检查和 lint 规则，禁止深层跨包导入，以检查落实边界。

这套隔离降低替换后台模板的成本，但不承诺无成本替换 Vue 或所有 UI 组件。框架迁移仍需改写表现层；接口契约、模型和部分用例可复用。

## 模块注册与权限

模块导出稳定标识、入口页面、路由描述、菜单候选项、语言资源及所需平台能力。壳层负责转换为实际路由，不让模块自己修改全局路由实例。

后端系统开通及用户授权决定可访问范围；前端注册资源不是授权。菜单和按钮仅做体验控制，直接访问 URL、API 以及字段返回仍由后端校验。

动态菜单通过受控页面标识映射到构建内页面，不加载任意远程代码。找不到注册页时显示明确错误，不绕过权限或跳转其他租户。

## 多租户状态与统一引擎

会话上下文由平台统一维护。切换租户时取消旧请求、清空租户缓存、重建路由和授权；返回的响应需核对发起时的上下文版本，不能将旧租户响应写入新租户状态。

统一封装国际化能力，模块仅声明翻译资源和必要业务上下文。展示语言、时区与币种分别处理；前端格式化不替代后端金额计算和权限脱敏。无权限的原始字段不应进入浏览器。

多标签页与会话租户的对应关系须与后端会话方案一起确认，不能仅通过浏览器本地存储确定租户身份。

## 升级与应用拆分路径

1. 第一期由 `apps/admin` 装配所有底座模块，通过不同地址进入对应功能。
2. 业务系统接入时创建对应模块与明确公开入口，不增加对壳层内部的依赖。
3. 需要独立部署时增加新的应用装配目录，选择其模块、布局与配置，复用公共包。
4. 多个应用共享会话与租户选择的方式通过认证协议明确，不假定跨域 Cookie 自动可用。
5. 替换 vue-pure-admin 时新建壳层适配器，复用领域模块；以功能、路由、权限和主题验证迁移结果。

应用拆分不同时等于仓库拆分。workspace 内先完成独立构建，确需独立仓库时再发布版本化公共包，避免过早增加发包维护工作。

建议将模板初始版本与本地改造记录分开维护，记录升级改动，避免大规模修改上游内部实现。vue-pure-admin 的实际目录、许可证和可扩展点须读取所选版本后验证，再确定最终迁移布局。

## 验收与待决事项

- 任一模块不依赖其他模块私有文件或模板内部实现。
- 可用最小壳装配单个模块进行构建和验证，检查是否隐藏依赖全局状态。
- 替换模拟的 HTTP、权限、国际化适配器后，模块用例仍可测试。
- 租户切换时旧请求、菜单、标签页及缓存不泄露上一租户信息。
- 桌面主要页面中英文切换正常，日期和金额统一格式化。
- 一个新增示例应用能够只装配指定模块独立构建，不复制领域代码；该验证不作为正式业务场景交付。

待确认：包划分细节、服务契约生成方式、测试工具、壳层实际适配点、多标签页会话语义和浏览器支持范围。状态管理暂以 vue-pure-admin 已使用的 Pinia 为候选，项目验证后锁定。版本候选基线见[技术版本与许可证基线](技术版本与许可证基线.md)。
