# 大宗供应链仓储服务与平台集成设计

大宗供应链仓储作为独立业务服务，负责货物从接管、保管到交出的业务事实。商品、仓库拓扑、业务伙伴、身份和通用能力沿用 AppNexus 现有对象。仓储服务通过平台对象标识和公开契约接入。煤炭、钢材等品类差异由仓储策略表达。

## 1. 工程归属

| 项目 | 设计 |
|---|---|
| 业务上下文 | 大宗供应链仓储。拥有进出仓履约、提货授权、库存、保管货权及监管执行、计量验收与库内作业 |
| 构建模块 | `backend/services/bulk-warehousing-service`，artifactId 为 `bulk-warehousing-service`，Java 根包为 `com.appnexus.bulkwarehousing` |
| 运行组合 | 一期由现有 `monolith-app` 装配。模块独立编译，相关仓储写入沿用同库事务。独立进程部署需要另行确认控制权、事务及回执契约 |
| 公开入口 | `api` 暴露仓储用例和稳定读模型。领域规则在 `domain`，编排及端口在 `application`，Web、MyBatis、跨模块及事务接入在相应 `adapter` 包，装配在 `bootstrap` |
| 依赖方向 | 仓储集成适配器依赖主数据公开 API、平台公开权限接口及业务对象契约。主数据和平台通过通用 Provider 装配读取仓储声明，保持反向构建依赖为空 |
| 数据归属 | 仓储自有表及迁移归仓储模块，使用现有 Flyway 历史和全局审计规则。其他模块通过公开用例访问仓储事实 |

## 2. 已有对象与接入方式

| 仓储需求 | 现有对象或代码入口 | 仓储接入及缺口 |
|---|---|---|
| 仓库、库区、库位 | `MasterData.Kind` 中的 `Warehouse`、`StorageArea`、`StorageLocation`，公开管理入口 `MasterDataManagement` | 指令及库存引用现有 ID。堆位、筒仓和隔离位的作业用途按实际位置能力配置。开工前验证可通过公开契约准确核验租户、启停、仓库归属及父子关系。若当前列表和选项契约不足，在主数据增加窄查询 |
| 商品、规格与计量 | 现有 `Product` 声明，`ProductManagement.read`、`ProductMeasurement`、`UnitConversions` | 使用商品档案标识。规格引用以实际商品结构契约为准，确认可用粒度后定键。过账快照保存采用单位、换算依据及精度。若当前接口只能计算、无法读取稳定依据，在主数据补充公开契约 |
| 货主、仓库经营方、承运方 | `BusinessPartner` 及现有伙伴对象声明 | 仓储业务角色记录引用伙伴 ID，业务伙伴档案由主数据维护。权利登记、提货授权和限制另存权威业务证据 |
| 系统账号与仓库人员 | 平台身份、租户、组织模块，现有公开 API 使用 `VerifiedTenantContext` | 签发、收货、质检和门岗以可信上下文为准。司机或提货人可作为业务主体记录，机器回执按受控接入身份校验 |
| 功能、行范围、字段保护 | 平台 `AccessAuthorization`、`RowAccessControl`、`FieldSecurity` 等，以及 `BusinessObjects.Provider` | 在本模块唯一声明对象及操作。仓库、货主等作为真实资源维度接入，验证平台是否已有所需维度与执行方式，能力不足在平台扩展 |
| 编码、打印、审批 | 平台 `CodingManagement`、通用业务对象运行契约，以及现有打印与工作流服务 | 编号、打印数据契约、审批绑定沿用通用能力。仓储用例核验实际状态和证据，保存业务结果。未配置审批的现场操作以受控业务命令执行 |

已有主数据停用时阻断其用于新指令或新配货，历史单据沿用原稳定标识与必要的受控快照。单据和库存查询按权限展示相关主数据字段。禁止以直接读取主数据私表来补足接口缺口。

### 公开契约与实现状态

以下区分档案查询、试算和过账所需的权威证据。结论来自公开声明及其应用、持久化实现的静态追踪。

| 引用 | 可以直接复用 | 进仓契约 |
|---|---|---|
| 仓库 | `MasterDataManagement.list(c, WAREHOUSE, "", true, 1, 1, id)` 精确查启用档案，返回 ID、编码、状态和版本。经主数据读权限及适用字段保护。 `warehouseOptions` 返回仓库字典 | 单独查仓库可以复用。与位置一起参与命令校验时，由主数据统一解析和校验完整拓扑 |
| 库区、库位 | 同一 `list` 精确查 ID 或按 `scope` 筛父编码。已有实现用 `parentCode` 关联库位到库区、库区到仓库 | `MasterDataManagement.resolveStoragePosition` 输入仓库、库区、库位 UUID 和三个预期版本，返回本租户有效的仓库、库区、位置 UUID 及版本。主数据内部核验整条启用父链及仓库归属。仓储不在多次列表读取之间自行拼父链 |
| 商品、规格及 SKU | `ProductManagement.read(c, productId)` 做商品读权限和记录范围校验。`ProductStructureManagement.read(c, productId)` 返回规格、SKU、父版本及状态。SKU 有自身 ID 和 specificationId，实际有效性还依赖规格及父商品 | 商品档案可直接复用。`ProductStructureManagement.resolveIdentity`，在同一读取中判定选择的规格或 SKU 属于该商品且可执行，返回规范化身份、父商品及结构版本、基础单位。按已启用仓储粒度选择 PRODUCT、SPECIFICATION 或 SKU，同一库存核算口径不混用 |
| 单位及包装换算 | `ProductStructureManagement.measurement` 返回基础单位、商品版本和配置；`calculatePackaging` 可按包装编码试算。`UnitConversions.calculate(c, id, quantity)` 按已启用的换算规则、端点单位及量纲计算结果 | `UnitConversions.evidence` 和 `ProductStructureManagement.packagingEvidence` 在一次解析中返回来源及目标单位、规则标识与版本、系数或包装配置依据、精度及结果。无换算时校验单位等同。预览复用现有试算，正式过账避免拼接列表与试算两次读取得出依据 |
| 业务伙伴 | `MasterDataManagement.list(c, PARTNER, "", true, 1, 1, id)` 精确查启用档案，走伙伴已编译行范围与字段保护。对伙伴 UUID、状态及版本的引用可直接复用 | 一期单个货主引用无需新增接口。历史记录按既有权限读取。货主、承运方和保管方在本次业务的资格、签发权或权利依据由仓储核验 |

源码入口见[主数据管理公开契约](../../../backend/services/master-data-service/src/main/java/com/appnexus/masterdata/api/masterdata/MasterDataManagement.java)、[主数据关系读取](../../../backend/services/master-data-service/src/main/java/com/appnexus/masterdata/adapter/persistence/masterdata/MyBatisMasterDataRelations.java)、[商品结构公开契约](../../../backend/services/master-data-service/src/main/java/com/appnexus/masterdata/api/product/ProductStructureManagement.java)及[单位换算应用实现](../../../backend/services/master-data-service/src/main/java/com/appnexus/masterdata/application/product/ProductUnitConversionService.java)。

上述解析接口由 `master-data-service` 提供，继续执行可信租户、适用操作、行范围及字段保护。仓储集成适配器只消费必要字段。默认使用原可信主体调用；若业务要求仓库岗位可使用受权商品或伙伴引用但无档案详情权限，由平台声明专用引用操作及最小投影后接入。

## 3. 仓储自有对象及声明边界

| 对象组 | 仓储所有权 | 接入平台的方式 |
|---|---|---|
| 入仓履约、出仓履约 | 指令、接管、实收实发及关单。确认行及关联来源作为所属履约资源 | 声明真实签发、确认、查询、更正和适用打印操作。单据序号接统一编码 |
| 提货授权、交接执行批次 | 授权范围、期限及核销，车船或其他交接方式的执行批次与作业任务 | 独立授权对象由有权方签发撤销。批次暴露实际调度、称重引用、复核及交接操作 |
| 实物库存与作业 | 库存身份、余额、占用、在途、盘点、转换和调整。流水由业务命令追加 | 库存、盘点及调整按实际入口声明。流水及当前锁作为受控主从资源 |
| 货权与监管 | 入仓权利登记、份额、过户、冻结及解除，外部仓单状态引用 | 使用统一行范围和字段保护。货权事实与平台账号权限分别校验 |
| 计量与验收 | 原始证据、有效数量版本、样品及质量结论 | 声明实际采集、审批、替换和放行操作，接口通用接收证据类别及适用范围 |
| 仓储策略 | 匹配仓库、交付方式、商品或合同，固化版本 | 业务策略归仓储持有。平台配置、字典、权限和通用能力沿各自所有权维护 |

对象编码及版本在实现前按现有目录复核。D01–D12 按唯一身份和完整操作、真实 API、准入与数据保护、能力和契约、编码、运行接入、配置事务及交付证据逐项落位。验证对象目录、实际操作和权限路径一致，尤其是跨租户、跨货主、停用主数据引用、伪造外仓回执、复磅和冻结的并发路径。

## 4. 在现有平台上走通进仓

由统一身份取得可信租户与岗位，通过主数据公开契约核验商品、仓库、位置、货主及单位依据，之后由仓储模块接管、确认实收并过账。质检和货权分别写入仓储自有对象。组装可分配范围时使用仓储权威余额，同时校验质量、货权及监管。确认单从仓储事实派生，编码、打印和审批由平台按已发布契约接入。煤炭汽运、箱件点收或钢卷识别共用此链路，适用品类策略提供不同的数量证据和库存身份。

实施先补齐被用例实际需要的主数据公开查询和统一授权接入，再交付首个进仓闭环；出仓在同一服务内复用已形成的库存及权利事实。本文确定模块边界和接入设计，真实运行证据随功能交付记录。

当前组合运行装配进仓主数据核验入口 `InboundReceiptReferences.resolve`，复用位置、商品、伙伴、换算公开契约，返回版本与数量证据。进仓写入及当前适用范围见[进仓流程详细设计](进仓流程详细设计.md)第 7 节。
