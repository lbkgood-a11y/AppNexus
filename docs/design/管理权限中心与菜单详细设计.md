# 管理权限中心与菜单详细设计

版本：1.0；日期：2026-11-08；状态：讨论结论基线，后续实现须据此细化接口与迁移。

## 1. 目标与范围

管理权限中心第一阶段建设完整 RBAC：平台账号或租户成员绑定角色，角色绑定独立权限资源，后端以稳定权限码执行真实鉴权，前端依据同一权限结果生成菜单、路由、页面区域和操作入口。第二阶段再增加用户直接授权与具体资源分享，不改变业务代码使用权限码的方式。

本设计覆盖用户/成员、角色、权限资源、功能授权、数据权限、菜单、成员角色分配、有效权限计算、动态菜单、菜单可用性与管理、审计和缓存失效。字段权限、角色继承、跨租户继承和通用 ABAC 不作为第一阶段交付，但模型不得阻碍后续扩展。

核心原则：权限码表达业务能力；菜单、路由、按钮、超链接和接口只是能力入口。前端控制改善体验，后端鉴权才是安全边界。没有明确分类或授权时默认拒绝。

## 2. 已有能力与边界

当前系统已经具备：

- `identity_account` 全局账号及启停管理；账号不因登录自动获得业务权限。
- `platform_tenant`、`tenant_member` 及可信租户会话上下文；租户角色只分配给同租户有效成员。
- `access_role` 平台/租户角色生命周期、编码唯一、系统/自定义类型、启停、逻辑删除、乐观锁与追加审计。
- `platform_menu` 的 `DIRECTORY/MENU/BUTTON`、路由、组件、权限字符、显示、启用、排序、乐观锁与审计。
- 组织域 `READ/CREATE/UPDATE/DELETE/GRANT` 成员直授权、有效期、撤销和审计；这是 RBAC 前的受控能力，不代表统一权限中心已经完成。
- 平台管理员与租户组织管理员的过渡权威源，以及 `/api/**` 可信租户执行边界和 MyBatis 作用域门禁。

进入实现前仍需补齐独立权限目录、角色权限关系、账号/成员角色关系、统一判定端口、动态菜单计算、系统角色初始化、菜单保护模式和授权审计。现有角色管理完成了基础生命周期，但关联关系上线后还必须加入角色引用检查和权限缓存失效。

## 3. 权威模型

### 3.1 主体与管理域

平台角色的主体是全局账号：

```text
identity_account -> access_account_role -> access_role(PLATFORM)
```

租户角色的主体是租户成员，而不是全局账号：

```text
tenant_member -> access_member_role -> access_role(TENANT, tenant_id)
```

这样同一账号在不同租户可以拥有完全不同的角色。平台角色不能分配给租户成员，租户角色不能跨租户分配；所有关系由数据库约束、事务内复核和真实 MySQL A/B 租户测试共同保证。

### 3.2 权限资源

新增独立权威表 `access_permission`：

```text
id                  BINARY(16)，应用生成 UUIDv7
scope_type          PLATFORM / TENANT
code                稳定全局权限码，创建后不可修改
resource            业务资源，如 access.role、sales.order
action              READ/CREATE/UPDATE/DELETE/APPROVE/EXPORT/LOOKUP/GRANT 等
name_zh/name_en      授权中心展示名称
description          职责、边界和副作用说明
enabled              权限是否参与新授权和有效权限计算
system_managed       是否只允许迁移或受控发布维护
version              乐观锁版本
created_at/updated_at
```

权限码建议使用小写点号资源与冒号动作：

```text
access.role:read
access.role:create
access.role:update
access.role:enable
access.role:delete
access.role:grant
configuration.menu:read
configuration.menu:update
sales.order:approve
customer:lookup
```

业务代码只依赖权限码，不判断角色名、角色编码、角色 ID、菜单 ID 或按钮是否显示。

### 3.3 角色权限

角色只关联权限，不保存另一套独立的角色菜单授权：

```text
access_role_permission
├── role_id
├── permission_id
├── granted_by
├── granted_at
└── PRIMARY KEY(role_id, permission_id)
```

角色和权限必须属于兼容管理域。租户角色可以使用系统发布的租户级权限定义，但关系必须绑定当前角色租户；平台权限不能授予租户角色。授权采用“提交完整权限集合并事务覆盖”，请求携带角色版本或授权版本，防止并发管理员静默覆盖。

不采用 `role_menu + role_permission` 两套并行权威，避免菜单可见与接口权限相互冲突。授权页面可以显示菜单/权限组合树，但提交和持久化的是权限 ID 集合。

### 3.4 用户或成员角色关系

```text
access_account_role(account_id, role_id, assigned_by, assigned_at)
access_member_role(tenant_id, member_id, role_id, assigned_by, assigned_at)
```

账号/成员拥有多个角色时，第一阶段有效权限取所有启用角色、启用权限的并集。禁用账号、成员、租户或角色时，对应权限立即不再生效。第一阶段不支持显式拒绝和角色继承。

### 3.5 数据权限

授权中心同时配置“能做什么”和“能操作哪些数据”，但两者使用分层模型：

```text
功能权限：是否允许执行 sales.order:read / update / approve
数据权限：允许该操作命中的订单数据集合
```

最终允许条件：

```text
拥有功能权限
AND 数据范围包含目标数据
AND 租户边界成立
AND 领域状态与对象级规则允许
```

数据权限不得代替功能权限；拥有“全部订单数据范围”但没有 `sales.order:read` 时仍不能读取订单。数据权限也不得突破租户边界，`ALL` 始终表示当前可信管理域或当前租户内全部，不表示跨租户。

第一阶段采用可审计的结构化数据范围，不允许管理员输入 SQL、SpEL、脚本或任意表达式。建议范围类型：

```text
SELF                 本人创建、负责或明确归属的数据
ORGANIZATION         指定组织节点本身
ORGANIZATION_SUBTREE 指定组织节点及全部后代
ASSIGNED             明确分配给当前成员的数据
ALL                  当前租户或平台管理域内全部数据
CUSTOM_SET           受控资源集合，如指定仓库、公司、项目
```

不是每个业务资源都支持全部范围类型。权限目录需要声明适用的数据维度，例如订单支持组织和负责人，库存支持仓库，项目支持项目集合。授权工作台只能展示该资源已注册且后端已实现的范围类型，不能生成无法执行的配置。

推荐表结构：

```text
access_data_policy
├── id
├── scope_type                 PLATFORM / TENANT
├── tenant_id                  平台策略为空，租户策略必填
├── code                       稳定策略编码
├── name_zh/name_en
├── resource                   适用业务资源
├── range_type                 SELF/ORGANIZATION/ORGANIZATION_SUBTREE/ASSIGNED/ALL/CUSTOM_SET
├── dimension_type             ORGANIZATION/WAREHOUSE/COMPANY/PROJECT/OWNER 等
├── enabled
├── system_managed
├── version
└── 审计字段

access_data_policy_value
├── policy_id
├── value_type
├── value_id                   组织、仓库、公司或项目等受控 UUID
└── PRIMARY KEY(policy_id, value_type, value_id)

access_role_data_policy
├── role_id
├── permission_id              数据范围针对具体读取或操作权限
├── policy_id
├── granted_by
├── granted_at
└── PRIMARY KEY(role_id, permission_id, policy_id)
```

数据策略必须绑定具体权限或权限资源，不能只给角色设置一个全局“本部门数据”。同一角色可能拥有：

```text
sales.order:read    → 本组织及下级
sales.order:update  → 仅本人负责
sales.order:approve → 指定公司
inventory.stock:read → 指定仓库集合
```

多个角色的数据范围组合规则默认取并集：只要任一有效角色同时授予该功能权限和匹配数据策略，即可进入后续领域校验。不能把一个角色的功能权限与另一个角色孤立的数据策略交叉拼接；每个有效授权分支必须是完整的“角色 + 权限 + 数据策略”。这样避免用户通过组合两个不完整角色意外扩大权限。

对于无需数据范围的权限（如创建入口或公共字典），权限元数据声明 `data_scope_required=false`。需要数据范围却未配置策略时默认拒绝，不自动解释为 `ALL`。创建类操作的数据约束由目标组织、仓库、项目等字段以及领域规则校验，可登记 `CREATE_IN_SCOPE` 一类明确策略，不能沿用读取查询条件含糊处理。

## 4. 权限粒度与页面场景

权限按照业务用例建模，不按照数据库表、HTTP 方法或 UI 控件机械拆分。

### 4.1 列表与详情

列表和详情敏感程度相同时统一使用 `resource:read`。列表只提供摘要而详情包含额外敏感信息时拆为 `resource:list` 与 `resource:read`。详情链接、详情路由和详情接口共同检查详情权限；列表接口不得把未授权详情字段先返回浏览器再隐藏。

### 4.2 复杂工作台和多层主子表

工作台由多个业务区域组合时，拥有任一有效区域权限即可进入工作台壳，各区域分别检查自身读取权限。无权区域不发请求、不接收数据。一个业务用例在事务中维护主、子、孙表时只检查顶层业务权限；只有子对象可以独立维护时才拆分权限。

例如 `sales.order:approve` 可以在同一事务更新订单、库存预占和审计，不要求操作者额外持有内部表的更新权限。权限只是必要条件，单据状态、数据范围、自审限制和乐观锁仍由领域规则独立校验。

详情响应可返回对象级 `availableActions` 及稳定原因码供前端展示，执行操作时后端必须重新校验。

### 4.3 超链接、无按钮接口和联动查询

超链接使用目标资源权限；无权时显示普通文本或不展示链接，直接访问路由和接口仍拒绝。自动加载接口按其返回数据对应的能力鉴权，不因没有按钮而放行。

选择器和联动查询使用受限的 `lookup` 权限，如 `customer:lookup`。Lookup 只返回 ID、编码、名称等必要摘要，不能替代详情读取权限；联动查询还必须校验父子关系和租户边界。低敏感字典接口必须明确归类为公开、认证公共或租户公共，未归类接口默认拒绝。

## 5. 菜单模型

### 5.1 菜单职责

菜单是导航和授权交互视图，不是权限权威。节点类型职责：

- `DIRECTORY`：组织导航；通常不关联权限，有可见有效子节点时才显示。
- `MENU`：页面或隐藏路由；关联页面访问权限。
- `BUTTON`：授权树中的操作入口描述；关联业务操作权限，不产生页面路由。

同一权限可以保护一个或多个接口，也可被菜单、按钮、链接或页面区域引用。菜单结构调整不得改变角色已拥有的权限。

### 5.2 展示、可用、访问和管理分离

菜单至少具有以下独立维度：

```text
enabled             全局菜单定义是否可用
display_mode        VISIBLE / HIDDEN / CONTEXTUAL
required_permission 页面或操作所需权限
management_mode     SYSTEM_LOCKED / PLATFORM_MANAGED / TENANT_CUSTOMIZABLE
```

现有 `visible` 应通过新增迁移演进为 `display_mode`，不能修改已发布的 V13。`HIDDEN` 用于详情、编辑和审批页面：不进入左侧导航，但合法链接访问仍检查菜单可用、功能开通、权限和业务上下文。`CONTEXTUAL` 只在已选择租户、项目或其他明确上下文后参与导航。

菜单 `enabled=false` 取消前端入口和路由可用性，但不自动代表后端业务整体下线。需要同时关闭接口时应使用独立功能开关，并由前后端共同检查。

### 5.3 菜单与权限关联

第一阶段一个 `MENU/BUTTON` 节点关联一个 `permission_id`，目录不产生权限。未来复杂工作台如确需 ANY/ALL 组合，再增加：

```text
menu_permission_requirement(menu_id, permission_id, group_no, relation_type)
```

不在菜单表保存可解释执行的权限表达式字符串。勾选目录只是批量选择后代的 UI 操作，不授予目录权限；勾选写操作时，授权服务自动补齐同页面的基础读取权限并在界面提示。取消页面读取权限时同步移除依赖操作权限，具体依赖由权限元数据维护，不能仅根据树的父子关系猜测。

### 5.4 菜单管理保护

菜单管理权限独立定义：

```text
configuration.menu:read
configuration.menu:create
configuration.menu:update
configuration.menu:enable
configuration.menu:delete
configuration.menu:publish
```

访问某业务菜单不代表能修改菜单配置。`SYSTEM_LOCKED` 节点仅允许迁移或受控发布维护；`PLATFORM_MANAGED` 由平台管理；`TENANT_CUSTOMIZABLE` 允许租户有限覆盖。租户不能修改 `code/type/route/component/permission/system_key`，只允许调整别名、显示和排序等明确白名单字段。

系统菜单增加不可变 `system_key`；安全逻辑不能依赖名称或固定 ID。菜单写操作继续使用乐观锁并追加变更前后快照审计。

### 5.5 租户菜单策略

平台菜单为定义权威，租户覆盖使用独立表：

```text
tenant_menu_policy
├── tenant_id
├── menu_id
├── enabled_override      NULL/TRUE/FALSE
├── visible_override      NULL/TRUE/FALSE
├── alias_zh/alias_en
├── sort_order_override
├── updated_by
├── updated_at
└── version
```

`NULL` 表示继承平台。平台禁用或锁定是上限，租户不能重新启用或修改。租户个性覆盖不影响权限关系。个人隐藏、收藏等偏好放在更后阶段，且只改变本人导航，不撤销权限或阻止直接访问。

## 6. 有效权限和动态菜单

第一阶段有效权限：

```text
有效权限 = 启用主体所属启用角色的启用权限并集
```

平台请求读取账号的平台角色；租户请求使用可信 `VerifiedTenantContext` 中的成员和租户读取租户角色。任何客户端 tenantId、角色列表或权限声明都不参与权威计算。

动态导航判定顺序：

```text
菜单全局启用
AND 功能已部署并开通
AND 当前管理域/租户适用
AND 租户策略允许
AND 用户满足 required_permission
AND 上下文条件满足
AND display_mode = VISIBLE（导航场景）
```

目录在至少一个后代有效可见时显示。路由访问不检查个人隐藏，也不要求 `VISIBLE`，但必须检查菜单/功能可用、页面访问权限、上下文和数据范围。后端接口只检查业务权限及领域约束，不依赖菜单是否显示。

前端只能加载构建内受控 `component_key` 映射，不根据服务端字符串加载任意脚本。权限变化后重建菜单、清理失效标签页和页面缓存，不使用浏览器 Token 存储。

## 7. 统一鉴权端口

后端提供集中式端口，业务 Controller/应用服务不直接查询关系表：

```java
boolean hasPermission(ExecutionSubject subject, String permissionCode);

boolean hasResourcePermission(
    ExecutionSubject subject,
    String permissionCode,
    String resourceType,
    String resourceId
);
```

第一阶段同时提供功能判定和结构化数据范围查询：

```java
DataScope resolveDataScope(
    ExecutionSubject subject,
    String permissionCode,
    String resourceType
);
```

列表查询必须在数据库查询前把 `DataScope` 编译为受控仓储条件，不能先查出全量数据再在 Java 或浏览器过滤。详情和写操作使用相同范围对目标行执行存在性/条件更新，避免查询后授权状态变化和跨范围对象泄漏。编译器只接受注册的维度和固定 SQL 形状；未知策略、解析失败、缺少上下文均失败关闭。

`hasResourcePermission` 组合 RBAC、数据范围和领域对象关系，后续再叠加用户分享授权。接口保护可使用统一注解或策略调用，但必须在应用用例入口再次保持明确边界。所有 `/api/**` 接口必须登记为公开、认证公共、租户公共或权限保护；未登记默认拒绝，并通过架构测试防止遗漏。

## 8. 缓存、生效和并发

权限结果可以按 `accountId + tenantId/memberId + authorityVersion` 缓存，权威数据仍在 MySQL。账号角色、成员角色、角色权限、角色状态、权限状态或租户状态变化时，在同一事务更新对应授权版本并写审计；请求发现版本变化后重新计算。不能依赖固定 TTL 承诺及时撤权。

授权覆盖更新使用乐观锁和固定加锁顺序。角色授权变更、成员角色变更、授权版本更新与审计必须处于同一 MySQL 事务。Redis/Valkey 只存派生结果；失效消息失败时版本校验仍应阻止旧权限长期生效。

## 9. 审计

至少记录：

- 角色创建、编辑、启停、删除。
- 角色权限全量变更，包含增加和移除集合。
- 平台账号角色分配和移除。
- 租户成员角色分配和移除。
- 菜单定义、保护模式、可用性和租户覆盖变更。
- 系统角色/菜单初始化和受控发布。

审计包含操作者、管理域、目标、原因、请求追踪 ID、变更前后必要快照和时间，不记录密码、Token、会话凭据或无关个人数据。业务变更和审计原子提交；失败操作不能记录为成功。

## 10. 现有组织直授权过渡

`organization_capability_grant` 当前是生产中的受控成员直授权，不能在 RBAC 上线时静默忽略。过渡采用双读、单写迁移：

1. 将组织能力注册为统一权限码，如 `organization.unit:read/create/update/delete` 与不可普通委派的 `organization.permission:grant`。
2. 创建租户系统角色 `TENANT_ADMIN` 并为其配置对应权限；租户创建时原子创建系统角色及首位管理员角色关系。
3. 对现有有效组织授权生成等价角色或成员角色关系，并生成可审计迁移报告。
4. 统一鉴权管线在过渡期同时读取 RBAC 和旧授权，结果取并集，但旧授权管理接口停止产生新的非迁移关系。
5. 对账通过后切换为仅 RBAC，保留旧表历史只读期，最终通过新迁移收缩；任何阶段均不得扩大权限。

第二阶段用户直授权应使用通用分享模型，包含权限、具体资源、授权人、来源和有效期；不复用角色关系，也不改变 RBAC 角色权限表。

## 11. 管理端页面

授权中心使用同一业务工作区，至少包含：

- 角色权限：选择平台或当前租户角色，在菜单/权限组合树上配置权限。
- 数据权限：在选中功能权限后配置该权限支持的数据范围、维度和值；只展示后端已注册能力。
- 用户角色：平台账号分配平台角色。
- 成员角色：当前租户成员分配本租户角色。
- 有效权限解释：只读展示权限来源角色、状态和失效原因，便于审计排错。

授权工作台建议采用三栏或分步布局：左侧角色，中间功能权限树，右侧当前权限的数据范围配置与有效结果摘要。授权树展示目录、页面和操作，但保存权限 ID；无菜单权限按业务资源分组，不能为了进入树而伪造按钮。

数据权限区至少展示：

- 当前功能权限是否要求数据范围。
- 资源支持的范围类型和数据维度。
- 组织树、仓库、公司、项目等受控值选择器。
- 多角色并集后的有效范围预览，以及当前编辑角色的贡献范围。
- `ALL` 的明确影响提示和高风险确认。
- 未配置、部分配置、已配置和继承结果，不以颜色单独表达。

功能权限与数据策略在同一次授权提交中原子保存；取消功能权限时同步删除该角色下对应数据策略关系。需要数据范围的功能权限如果未完成配置，不能提交。页面明确区分已保存状态、未保存修改、父级批量选择、自动补齐依赖和部分选中；提交完整集合并显示权限及数据范围差异确认。全站复用 vue-pure-admin、Element Plus、`BusinessWorkspace`、`ManagementTable`、`ManagedDialog`、主题、i18n 和 `@appnexus/icons`。

菜单管理继续独立页面，增加展示模式、保护模式、页面权限关联与租户覆盖入口。系统锁定字段以只读文本和原因说明展示；前端禁用不能替代后端保护。

## 13. 分阶段实施

### 阶段 A：权限目录和统一判定

创建 `access_permission`、注册现有用户/角色/菜单/组织业务权限、实现统一鉴权端口及默认拒绝架构测试。此阶段不改变现有菜单展示。

### 阶段 B：角色授权、数据权限和主体角色

创建功能权限、数据策略及主体角色关系表，提供功能权限和数据范围一体化全量覆盖接口、授权版本与审计；实现平台账号角色和租户成员角色管理。补系统角色初始化及角色删除引用检查。首批只启用组织、本人、全部以及已有明确业务维度，未实现的维度不得出现在管理页面。

### 阶段 C：动态菜单

菜单关联权限，新增 `display_mode/management_mode/system_key`，实现动态导航和隐藏路由。迁移静态平台角色路由控制，不让前端角色字符串成为安全权威。

### 阶段 D：租户菜单策略与旧授权迁移

实现有限租户覆盖，迁移组织直授权并完成双读对账，最终切换统一 RBAC。

### 阶段 E：用户直授权和资源分享

增加带资源范围、来源和有效期的直接授权；有效权限解释能区分角色来源与分享来源。

## 14. 验收基线

- 平台和租户管理域不可混用，真实 MySQL A/B 同 ID 测试覆盖读写隔离。
- 无角色、禁用主体、禁用角色、禁用权限均默认拒绝；撤权在明确版本边界内生效。
- 菜单隐藏、个人偏好或前端按钮不能绕过直接路由和接口鉴权。
- 列表/详情、工作台区域、超链接、无按钮接口和 Lookup 均有明确权限归类与最小字段响应。
- 需要数据范围的权限未配置时默认拒绝；`ALL` 不跨租户；多角色只合并完整授权分支，不能交叉拼接扩大权限。
- 列表在 SQL 查询前应用范围，详情和写操作使用同一范围条件；禁止查全量后在 Java 或前端过滤。
- 组织、仓库、公司、项目等策略值在保存时复核当前管理域，引用停用或移除后按策略规则立即失效并可解释。
- 授权全量覆盖、并发冲突、审计失败回滚、缓存失效和旧授权迁移对账通过。
- 动态菜单只引用构建内组件，无模拟权限、浏览器 Token 或未接通入口。
- 中英文、深浅主题、桌面/窄屏/手机、键盘和焦点验收通过。
