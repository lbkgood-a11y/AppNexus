## 2026-11-09 接口安全域登记

正式 security 适配器新增 `EndpointPolicy`，将 Controller 登记为登录公共、本人自助、租户上下文、租户业务、平台管理或授权管理安全域。架构测试要求每个 `@RestController` 必须声明安全域，新增未登记 Controller 会直接失败；当前架构测试 3 项通过。该登记是默认拒绝的第一层门禁，不能替代方法级权限码、租户隔离、CSRF 和用例层复核。后续仍需把混合授权 Controller 细化到方法级资源/操作登记。

新增只读旧授权对账端口及 `GET /bff/platform/authorization-reconciliation`。报告分页列出仍有效的 `access_member_permission`，逐条使用与运行时一致的主体、角色、快照、权限和有效期条件判断是否已被统一 RBAC 覆盖，并返回有效旧授权总数及未覆盖总数。只有 `uncovered=0` 才具备关闭旧双读的前置条件；当前能力不自动迁移、不删除历史表，也不把旧授权直接解释为新角色，避免静默扩权。真实 MySQL 角色/授权测试 13 项通过。

V30 将存量旧成员权限按“租户 + 成员 + 权限”分别迁移为受保护系统角色和独立授权快照，保留每条授权自己的到期时间，组织单元旧能力映射为当前租户 `ALL`，禁止合并角色后跨分支拼接。普通组织授权入口的新增、撤销和列表已经切换为统一快照，不再新增 `organization_capability_grant` 或 `access_member_permission`。V31 增加统一有效租户权限只读视图，角色、授权、字典、账号/成员保护和组织管理权门禁全部改读 `organization.permission:grant`；首位管理员初始化不再写旧镜像。功能权限、数据范围和组织能力运行时也已删除旧表双读，旧表新增记录不再放行，仅保留历史与对账。空库 V1–V31 迁移及相关 29 项测试通过。

V32 新增 `platform_menu_resource`，把页面与统一授权资源的关联落库；授权目录不再在 Java 中按组件路径维护资源映射。租户角色和授权中心菜单分别绑定 `access.tenant.role:read` 与 `access.tenant.role:grant`，导航快照继续逐次调用统一权限判定，撤权后下一次读取立即移除入口。菜单、组织授权和角色相关测试 25 项通过。

前端平台路由已移除 `PLATFORM_ADMIN` 静态角色 meta，无租户空态的管理入口改为读取 `/bff/platform/access` 权威结果。菜单集合继续由 `/bff/navigation` 原子替换，直接业务路径由服务端允许路径守卫控制，后端接口仍独立校验；前端角色字符串不再作为平台入口安全判断。admin Vue/TypeScript 类型检查通过。

方法级端点登记开始实施：新增 `EndpointOperation` 标准注解，角色管理 15 个、授权管理 29 个、平台管理 13 个、菜单管理 5 个、字典管理 10 个、组织领域 20 个端点均登记对应稳定权限码。平台授权端点使用 `access.role:grant`，租户及平台代管租户授权端点使用 `access.tenant.role:grant`；平台目录、菜单和字典按各资源读写操作登记。组织类型、关系、岗位、任职与负责人目前沿用已发布的 `organization.unit:*` 执行边界，不虚构尚未进入目录的新权限码。架构测试要求这六个 Controller 的每个 HTTP 映射必须带该注解，新增遗漏端点直接失败。架构测试现为 4 项通过。注解只承担契约和门禁，不替代用例现有的权威锁、租户校验、乐观锁及审计。

组织旧 CRUD 与组织授权共 10 个端点也已登记，架构门禁扩大到八个 Controller。新增 `EndpointOperationInterceptor`，对带契约的 `/api/**` 端点在进入 Controller 前使用 `TenantExecutionFilter` 的可信账号/租户/成员上下文调用统一 `AccessAuthorization`；缺少权限返回稳定 `OPERATION_NOT_AUTHORIZED`。`/api/organization/**` 已有范围感知能力过滤器和 `GRANT_DENIED` 专用契约，通用拦截显式排除该路径，避免双重门禁改变能力探测或错误语义。租户切换、组织授权和角色相关 23 项测试通过。

### 2.2 后端领域与用例

- `PermissionCatalog`：平台/租户权限目录。
- `AccessAuthorization`：统一功能权限判定。
- `RolePermissionManagement`：功能权限与数据策略完整快照原子保存。
- `SubjectRoleManagement`：平台账号角色和租户成员角色完整快照保存。
- `DataPolicyMetadataCatalog`：范围类型和受控资源元数据。
- `DataScopeAuthorization`：`SELF / ORGANIZATION / ORGANIZATION_SUBTREE / ALL / DENY` 解析。
- `EffectiveAuthorizationQuery`：按权限码解释来源角色、数据范围及未生效原因。
- 授权覆盖写、角色/主体版本推进和审计均处于同一 MySQL 事务。
- 需要数据范围的权限未配置策略时返回 `DATA_SCOPE_REQUIRED`，不能保存半成品授权。
- 组织范围值在保存时复核当前租户及启用状态；`DENY` 不能作为持久化策略。

### 2.3 系统角色与旧授权过渡

- 平台固定系统角色：`PLATFORM_SUPER_ADMIN`。
- 租户系统角色编码：`sys_tenant_admin`；`system_key` 包含租户 UUID，保证全局唯一。
- 新建平台管理员或租户管理员时，会原子补齐系统角色、权限、数据策略和主体关系。
- 租户管理员的数据范围权限初始化为当前租户 `ALL`，不表示跨租户全部。
- 迁移期鉴权采用三路双读：
  1. 统一 RBAC；
  2. V17 `access_member_permission`；
  3. `organization_capability_grant`。
- 旧授权仍保留用于对账和回滚，尚未停止旧写入，也尚未切换为仅 RBAC。

### 2.4 组织仓储数据范围

- 组织列表、修改和删除开始在 SQL 中应用数据范围。
- `ALL`：当前可信租户全部组织。
- `ORGANIZATION`：指定组织。
- `ORGANIZATION_SUBTREE`：通过递归 SQL 限制指定组织及其后代。
- `SELF`：现有组织模型没有可靠的创建人或负责人语义，当前失败关闭。
- 创建组织缺少明确父级授权上下文，当前仅允许 `ALL`，避免扩大权限。
- 迁移期旧组织直授权按原有语义解析为当前租户 `ALL`。

## 6. 关键安全约束

- 菜单、路由和按钮可见性不是安全边界。
- 平台角色不能授予租户成员，租户角色不能跨租户分配。
- 租户接口的租户和成员只能来自 `VerifiedTenantContext`。
- 数据范围必须进入 SQL 查询或条件写入，禁止查全量后在 Java/前端过滤。
- 未配置、未知范围、缺少上下文和无法无损合并的策略均失败关闭。
- `ALL` 永远只表示当前可信管理域或当前租户。
- 不得把密码、Token、会话凭据写入授权审计、注释或示例。
- 不得修改已发布迁移；所有演进继续新增 V25 及后续迁移。
