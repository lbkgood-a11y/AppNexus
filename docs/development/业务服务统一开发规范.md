# 业务服务统一开发规范

状态：当前开发强制基线。现有代码的验证范围与环境边界以《架构重构查缺补漏审查》为准；新增功能仍须执行门禁，不能套用旧功能的验收结论。

## 1. 概念与唯一来源

| 概念 | 规范 | 唯一权威位置 |
|---|---|---|
| 对象 | 长期业务实体或业务记录，如 Warehouse、InboundOrder；不得以 Controller、页面分组或技术服务代替对象 | 模块公开对象声明 |
| 分类 | MASTER_DATA、TRANSACTION、CONFIGURATION、LEDGER、SYSTEM；审批/打印不改变分类 | 对象声明 |
| 操作编码 | 对象内稳定语义，如 create、update、submit；不采用 platformCreate 等传输场景名称 | 对象操作声明 |
| 操作标识 | objectType.operationCode，全局唯一；平台代管和租户自助若语义相同，使用明确不同执行入口/授权策略表达 | 操作声明 |
| 权限码 | resource:action；角色授权使用，不能当按钮或对象标识 | 权限目录及真实执行器 |
| 页面 | 路由、组件及管理域；不拥有业务规则 | 页面注册表 |
| 能力 | 审批、打印等可选服务接入，不是业务权限 | 操作能力声明 |

已通过业务 Provider 声明的操作，接口只 reference=true 引用；禁止重复名称、权限和页面。平台 EndpointOperation 是接口权限的唯一来源，OperationBinding 不重复 permissions。当前两类声明方式仅为不同模块的接入形式，不能重复登记同一操作；统一聚合后校验唯一性。

每个功能必须执行[业务对象完整声明规范](业务对象完整声明规范.md)，复用或新增所属对象唯一 Provider，在设计、编码和交付时逐项核对 D01–D12。完整声明覆盖对象/操作、页面/API、权限、工作流、编码、打印、数据契约、统一运行端口及生命周期；不适用项记录具体理由和证据，遗漏或未接通执行不得交付。

## 2. 服务职责

业务服务负责对象校验、状态机、事务、并发版本及自身记录存取，通过同一对象 Provider 暴露一次运行能力。公共执行器负责契约字段投影、关联配置解析及专业能力分派；公共审批桥接负责任务准入、实例/版本核验和重复终态判定，对象只保存已验证结果及业务事实。禁止为每个对象重复定义工作流处理器、打印取数 Provider 或能力目录；能力配置仍由专业服务拥有。禁止以元数据登记代替真实对象运行实现；禁止通用执行器接收任意 SQL、URL 或客户端事实后修改业务状态。

模块间仅依赖公开契约，不读取另一模块数据库表，不深层导入实现。业务对象配置不存业务正文；条件事实须由业务服务在授权后重读。主数据不强制接入审批或打印，不支持的能力不展示配置入口。

## 3. 授权与诊断

认证账号、可信租户成员、操作功能权限、数据范围/字段、对象归属及业务状态分层判定。菜单显隐仅导航；隐藏不等于无权，停用按真实准入拒绝。所有请求由后端复核，前端准入不能用于放行。

主体来自会话和可信租户过滤器，禁止客户端指定操作者。未知操作/权限、空权限组和不完整上下文默认拒绝。跨租户同 ID、撤权、过期、停用及并发变更必须有反向测试。不得借用无关资源权限；新资源需配独立语义权限及受控迁移。

诊断复用执行判定，返回通过、阻断、未检查、不适用，禁止把未检查当通过。必须保留无角色来源的缺失权限。查询他人先校验管理权；对象无权时不泄露存在性。预检只读，不创建解析、流程或打印任务；瞬时结果不保证后续执行成功。

### 3.1 统一权限模型强制接入

**所有接入业务对象强制声明与执行（2026-11-20）**：凡接入平台的业务对象及其实际操作，必须在唯一 `BusinessObjects.Provider` 中声明，并在真实服务端路径接入统一权限体系。已有对象复用原 Provider；存量注解兼容不构成新增或改造功能的豁免。禁止只有菜单、按钮、权限码、目录或执行器登记而没有实际授权执行。查询、详情、创建、修改、删除、启停、批量、导入导出、回调和后台任务等实际入口均须反查归属；系统管理、自助和公开入口明确声明管理域、准入类型及受控边界，不适用行范围也不能省略声明与准入。

每个对象交付必须建立“实际入口→对象/操作声明→统一准入→范围/字段决策→真实读写→正反向测试”证据链，分别检查遗漏声明、遗漏执行和绕过执行。创建验证目标归属，更新验证原记录及适用的目标归属，删除验证目标记录，批量验证全部受影响记录；写入授权与业务修改保持事务一致，不能用查询权限、先查后按裸 ID 写入或前端过滤替代。缺声明、缺实际执行、可绕过或缺少适用验证证据，均必须阻断交付；自动化未覆盖的部分必须人工逐入口复核，不能宣称 CI 已全面保证。

授权配置须区分功能授权与数据范围，公共配置能力采用“对象默认范围＋操作显式覆盖”的目标模型：范围继承不授予功能权限，不能将查询范围自动当作写权限。默认范围、操作覆盖、成员继承角色与模板快照必须明确区分；不同操作仅支持各自真实声明并执行的范围，不支持的配置拒绝，缺少有效策略默认拒绝。该模型须先完成公共契约、存量策略迁移与真实执行验证再开放，不能仅在页面折叠相同值就宣称支持持续继承。当前能力及改造边界见[授权配置与权限接入门禁梳理](../design/授权配置与权限接入门禁梳理.md)。

所有新增、修改的权限管理与权限控制必须走平台统一权限模型，覆盖功能授权、角色与成员授权、数据范围、字段保护及其查询、写入、引用等实际执行入口。禁止业务模块自行构建平行权限体系；本条同时适用于人工开发和 AI 生成代码。

**新增功能创建即接入（2026-11-20）**：所有未来新增功能均须在设计、编码及首次交付时接入统一权限模型，覆盖单据、非单据及各类引用入口。必须提交统一对象/操作声明、真实服务端功能准入、适用的记录/条件范围和字段保护，以及正向业务与反向越权证据；不得先上线、后补权限。现有公共能力不足时先扩展统一模型和公共执行层，不得复制业务私有权限逻辑。

系统管理功能继续遵守其专用管理域和管理权边界，自助/公开功能须通过统一声明明确准入类型及数据边界；并非所有操作都适用记录级授权，但不适用项必须逐项说明理由、执行入口和验证证据，不能因为没有行范围而省略统一准入。纯界面草稿等非授权交互按既有规则登记。存量与新增入口一并纳入统一执行边界。单据状态转换、非单据维护和跨对象引用复用公开权限计划及执行端口，业务只声明数据依据和实现业务约束。

1. **唯一声明与管理入口**：对象、操作及数据能力按统一声明登记，角色、成员和策略通过现有授权中心及平台公开管理接口管理。不得为单个业务对象新增独立权限管理页面、授权 API、策略表或配置存储；业务页面需要授权入口时复用统一管理能力。未来记录共享等授权关系也必须先纳入统一模型，不能作为普通业务关联绕过此要求。
2. **统一判定与执行**：使用平台公开授权入口；行范围通过 `AccessPlanning / AccessPlan` 决策并复用 `RowAccessControl` 公共执行能力，字段保护复用 `FieldProtection` 及统一算法。不得自行查询或拼接角色、成员、组织关系推断访问权，不得复制范围合并、标准权限谓词编译、字段脱敏或权限缓存实现。不得以管理员名称、角色编码、创建人相同等硬编码分支放行。
3. **业务适配边界**：允许业务适配器提供代码固定的列/关联映射，将统一模型结果用于 SQL、事务锁定和写入校验；允许校验对象状态、目标归属真实性、主从一致性等业务约束。适配器不得增加未声明的放行分支、自行计算另一套可见范围或用业务校验替代平台授权。租户边界必须始终强制，ALL 不表示跨租户；前端显隐和预检不能替代服务端执行。
4. **能力不足先扩展公共模型**：先记录实际场景、现有缺口和查询效率要求，再在统一声明、策略契约、公共决策/执行、管理界面及测试中完成必要扩展，然后接入业务对象。不得以赶进度、业务特殊或历史代码为由另建专用授权机制；不支持的策略不得配置或默认放行。仅新增业务接口或转发类不能宣称已实现统一控制。
5. **交付审查**：列明声明位置、公开调用、公共执行接入和保留的业务约束，检查未新增平行管理入口、策略存储及本地授权算法。验证列表、总数、详情、写入和适用的引用路径，以及跨租户、撤权、过期、无策略拒绝；影响查询时提供代表性数据下的执行计划和性能证据。历史未迁移能力记录差距，不能作为新实现模板，也不能因发布本规则而宣称全仓已统一。

本条规定统一接入边界，数据权限具体契约和当前能力上限执行[业务对象数据权限声明标准](业务对象数据权限声明标准.md)。现有架构、包说明及业务测试只能证明各自覆盖的内容，本条尚未被自动检查覆盖的部分必须人工审查并记录。

## 4. 页面接入

执行《前端 UI 与代码生成规范》，复用 BusinessWorkspace、ManagementTable、ManagedDialog、Element Plus 和现有主题/i18n。按钮绑定操作标识，不能直接拼权限码。能力分组从统一操作结果投影，不建立领域平行权限端点。disabled 只表达业务条件、加载和并发状态，不能冒充完整授权。

对象目录显示真实对象、分类、操作和能力；功能清单显示页面/对象到操作、权限和实际接口。授权中心管理授权及诊断，菜单管理只管理导航。必须覆盖加载、空态、错误、无权、冲突和保存结果，中英文、深浅/System、移动端一致。

取消、复制、纯草稿编辑、导航等可登记非授权交互例外；涉及 API 写入不得通过例外逃避操作绑定。动态表达式、公共事件委托及提交/确认处理均须审查副作用。

## 5. 数据与接口

统一使用 object_type/objectType、operation_code/operationCode、operation_id/operationId。数据库列与公开 DTO 含义一致，不保留 action/type/operation 多套同义编码。历史迁移保持校验和，新增迁移一次性转换数据、JSON、菜单及授权关系；不增加运行时旧协议回退。

接口使用固定 HTTP 方法和路由，敏感读取 no-store；写入校验 CSRF、乐观锁及需要的幂等键，不自动重放业务写操作。金额、数量、时间、版本、默认值和环境限制提供中文标准注释；敏感凭据不进日志、示例、审计正文。

### 引用名称解析

业务记录引用持久化稳定 ID 或编码，业务读取响应从契约明确声明引用类型、标识来源和显示字段。列表按当前页、主从按已加载区域收集引用，使用公共批量解析器去重分批，再回填名称。引用参与行可见性时，以受控候选批查询引用后再生成可见行及游标。缺失名称使用占位，已签发单据的历史展示按单据契约使用签发快照。

名称由拥有对应数据的模块按可信租户和原对象的功能、行及字段权限批量提供。提供方应使用固定、参数化的集合查询，禁止批量接口内逐标识查询，禁止业务 SQL 跨模块 JOIN 取名。批量端口可由同进程或远程适配器实现，远程端复核可信调用主体和委托边界。缓存可放在提供方内部，命中不授予查看权限；按名称排序和筛选使用分页前的专用查询契约。

### 5.1 全局记录审计

所有自有持久化表（主表、明细、关系、配置及系统业务记录）必须具备下列四列，不能仅在人员模块实现。记录审计与追加操作日志互补，不能用日志代替字段，也不能用最后修改字段代替历史操作日志。

未来新建表必须在首次 `CREATE TABLE` 定义中直接包含全部四列及中文列注释，不能将其留给后续补漏迁移。该要求同样适用于关联表、日志表、队列表及中间表，不以“只存关系”“只追加”“临时中转”作为省略理由。新增账号列使用 `BINARY(16)`，新增时间列使用 `TIMESTAMP(6)`，遵守下表的可信主体、UTC、只读及事务约束；系统执行没有可信账号时允许 NULL。历史表仍用新版本迁移补齐，不修改历史校验和。

| 数据库列 / API 字段 | 强制含义与约束 |
|---|---|
| created_by / createdBy | 实际创建账号 UUID；可信认证主体，不是被代表人员或租户成员；客户端不可指定 |
| created_at / createdAt | 数据库生成的 UTC 创建时间点，微秒精度；API 使用 ISO 8601，前端按语言及时区格式化 |
| updated_by / updatedBy | 实际最后修改账号 UUID；创建时与创建人一致，修改时在原业务事务中更新 |
| updated_at / updatedAt | 数据库生成的 UTC 最后修改时间点；创建时初始化，修改时与业务写入同事务更新 |

创建信息在正常修改、启停、发布、批量和冲突更新时不可覆盖。回滚、乐观锁失败、无权及跨租户拒绝不能推进记录审计。匿名、后台任务及机器主体没有实际账号时保持 NULL，不沿用上一请求主体；历史未知字段保持 NULL，禁止填成迁移执行者或迁移时刻。明细变更按业务聚合约定同步推进父对象审计。物理删除的历史责任由现有追加操作日志保留，四列不代表删除历史。

前端仅展示原读取权限已允许的记录审计，不提供任意表名或 ID 的全局审计查询入口。详情及列表审计详情复用公共 Element Plus 描述列表与 ManagedDialog，只读、不进入编辑提交契约。缺失时间显示“历史未记录”，缺失账号显示“系统执行或历史未记录”，不得猜测真实操作者。名称仅可从已授权公开目录解析，不能为展示审计人扩大账号目录读取权限。

Flyway 历史迁移校验和保持不变，补列使用新迁移。Spring Authorization Server 的 oauth2_*、Flowable 的 ACT_*/FLW_* 及 Flyway 自身表属于上游协议/引擎结构，不直接加业务审计列；对应自有业务表仍须覆盖。新增自有表及新的执行入口必须验证四列、可信主体、事务、历史未知值、跨租户和前端展示，不得仅更新登记清单宣布完成。

建表交付必须同时审查首次 CREATE TABLE 定义，并运行 `GlobalRecordAuditTest.ownedTablesHaveAllFourColumns`。该测试在真实 MySQL 完成迁移后扫描全部自有基础表，因此会自动纳入未来新表；发现任何缺列即失败。现有 CI 的后端 Maven verify 包含此集成测试，禁止为新建自有表增加第三方前缀排除、删除断言或跳过测试来获得通过。直接建表定义的审查与迁移后真实结构检查互补，后者不能证明首次建表语句本身已完整。

## 6. 开发与交付顺序

所有功能交付必须逐项执行[功能交付门禁要求](功能交付门禁要求.md)，记录适用性、真实业务及安全证据；新增功能统一权限接入属于必审项，不得因仅完成编码或登记而标记交付完成。

1. 明确真实对象、分类、操作、权限、业务前置条件与可选能力。
2. 声明唯一契约及真实接口，实现后端事务、授权和业务规则。
3. 接入页面、按钮和能力投影，更新中英文及诊断说明。
4. 编写数据迁移，验证旧数据到新结构，并核对无运行时兼容分支。
5. 运行操作引用检查、类型检查、前后端构建、架构及相关真实数据库正反向测试。
6. 用管理员和普通用户完成真实页面主流程与失败流程，检查主题和窄屏。
7. 对齐最终源码、运行产物、迁移版本、测试证据和交付文档；未验证明确列出，不宣称全面完成。

仓库根目录检查：node frontend/scripts/check-operation-bindings.mjs。该脚本只验证静态覆盖，不能替代业务代码审查。禁止通过重生成全部例外或删除失败断言获得通过。

## 7. 查缺补漏关闭标准

每个缺口记录代码位置、影响、修复、正反向证据、部署状态。不能仅以“已改名”“已登记”“构建通过”关闭架构缺口；功能不适用需说明业务理由。本次六项工程缺口的闭环结果见审查记录；新增对象、权限和页面必须重新提供其正反向证据。

### 7.1 六边形分层交付门禁（2026-11-19）

新增和改造复杂业务服务时，必须同时交付领域规则、应用用例、应用定义的必要输出端口、真实技术适配器及组合装配。领域负责业务状态与约束，应用协调授权、事务和聚合，JDBC、MyBatis、HTTP、JSON、引擎及缓存实现放在对应适配器；不能把业务规则整体搬进持久化类以获得表面分层。事务端口必须保证原聚合、关联、字典引用及审计的原子性，不能因拆类产生独立提交。

纯领域规则不得依赖 Web、Spring、数据库客户端、审批引擎或应用及适配器实现；业务用例通过业务语义端口访问外部能力，禁止定义接收任意 SQL、表名、URL 的通用端口。启动装配模块中的 application 与领域内应用用例层须区分，不以禁止装配代码依赖框架的方式误用门禁。

架构检查必须扫描正式组合应用加载的自有服务，并明确验证已迁移边界存在，防止仅限制 domain 包而把所有业务写在包外绕过。复杂业务不能套用简单字典的简化理由；已有存量尚未迁移的代码需记录具体缺口，不得通过扩大例外清单宣布关闭。交付证据必须包含领域规则测试、真实数据库事务及越权反向测试；原公开接口、可信主体、租户隔离、幂等、锁与审计行为均需保持或经明确业务设计变更。

当前实施范围、剩余职责和验证边界见[业务服务六边形分层改造](../design/业务服务六边形分层改造.md)，该记录不代表全仓库重构已经完成。


## 字典标准统一（2026-11-17）

字典编码、项编码及业务值统一执行[字典编码与业务值标准](字典编码与业务值标准.md)。V102 一次性转换已知存量值与业务引用，保留字典项 ID、名称、启停及创建信息；无法确定含义的历史项保留并停用，不再用于新选。新租户使用版本化标准资源，不再使用 `v_` 哈希作为预置编码。V89/V91 及旧资源仅作为不可变历史迁移保留，运行时初始化使用当前标准资源，不恢复旧资源或运行时别名。

## 业务对象数据权限声明

新增和改造对象的数据权限统一执行[业务对象数据权限声明标准](业务对象数据权限声明标准.md)。对象/操作继续使用原唯一来源，数据权限作为同一BusinessObjects.Descriptor.dataAccess的一部分声明，范围只引用operationCode并从原操作派生权限码；不再单独提供数据权限Provider。行范围、字段只读/脱敏/隐藏必须对应真实执行器。能力目录代码发布、策略授权中心保存，不接受任意SQL或表名。
