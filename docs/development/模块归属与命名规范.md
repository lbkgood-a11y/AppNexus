# 模块归属与命名规范

生效日期：2026-11-19。适用于后端目录、Maven 模块、Java 包的新增、重命名及归属调整。与[架构与分包边界](架构与分包边界.md)、[后端标准工程结构与 AI 生成约束](后端标准工程结构与AI生成约束.md)共同执行。

## 1. 三种边界分别表达

- 业务上下文表达业务语言、规则和数据所有权。
- Maven 模块表达构建和依赖隔离，不代表独立运行进程。
- 部署应用表达启动、配置和运行组合，位于 `backend/applications`。

当前采用模块化单体：平台、主数据、业务对象、打印和工作流由 `applications/monolith-app` 统一装配。`services` 是业务能力工程集合；其中 `*-service` 表示逻辑业务服务工程，不承诺独立部署。只有确有独立发布、运行隔离或扩缩容需求时，才另行设计部署单元。

因此，同一进程部署不要求合并业务模块；业务模块有独立 POM 也不要求创建独立启动类、HTTP 调用或数据库实例。

## 2. 当前能力归属

| 工程 | 能力分类与职责 | 归属决策及边界 |
|---|---|---|
| platform-service | 平台基础能力：身份、租户、组织、授权、配置、本地化、审计 | 保留现有上下文；不能成为所有共享代码和业务数据的容器 |
| platform-service/business-object | 对象元数据与能力配置：对象/操作目录、编码规则、审批和打印绑定 | 归入平台独立 businessobject 上下文，artifactId 为 platform-business-object；公开契约与内部用例隔离，技术实现进入平台集中适配器，不直接塞入 configuration |
| master-data-service | 业务主数据：商品、业务伙伴、仓库及库区等 | 保留在平台之外；业务被全站使用不改变其业务所有权，后续按真实上下文细化 |
| print-service | 通用支撑能力：打印规则、模板与打印任务生命周期 | 保留独立能力模块，核心规则与存储、渲染、设备等技术实现隔离 |
| workflow-service | 通用支撑能力：流程模型、审批运行、任务与流程引擎接入 | 保留独立能力模块，隔离 Flowable 等引擎依赖；不拥有业务单据状态机 |

产品上称为“平台能力”，不代表代码必须移动到 `platform-service`。以上分类是职责说明，不新增一层 Maven 聚合，不要求创建 `capabilities` 等目录。

业务对象模块不保存各业务对象正文、不代替业务执行；工作流提供审批能力，审批结果由原业务用例验证并落地；打印的数据供给经原业务授权后取得。不得因组合运行或移动目录而跨模块读表、导入内部实现或绕过授权。

## 3. 目录与 Maven 命名

目录和 artifactId 使用小写英文单词与连字符（kebab-case），以明确业务语义命名，避免中文、空格、下划线、团队人名及无语义缩写。现有确定的映射保留，不为追求表面一致批量重命名。

| 对象 | 新增命名规则 | 示例与边界 |
|---|---|---|
| 普通业务工程 | `services/<context>-service`；默认 artifactId 与工程目录同名 | `inventory-service`；默认单 Maven 模块，不能按每个对象自动建工程 |
| 平台上下文模块 | `platform-service/<context>`；artifactId 为 `platform-<context>` | 目录 `organization`，artifactId `platform-organization` |
| 平台技术适配器 | 沿用固定目录；artifactId 使用既有 `platform-…-adapter` 约定 | `adapters/persistence` 对应 `platform-persistence-adapter`；既有 `platform-api` 对应 `platform-management-api-adapter`，不得创建同义模块 |
| 已有多模块工程的核心 | 沿用 `core`；artifactId 为既定能力前缀加 `-core` | `workflow-core`、`print-core`；不要求普通单模块服务再拆 core |
| 已有多模块工程的适配器 | `adapters/<responsibility-or-technology>`；artifactId 为既定能力前缀加职责或真实技术及 `-adapter` | `workflow-flowable-adapter`、`print-persistence-adapter`；先证明构建隔离需要再新增物理模块 |
| 部署应用 | `applications/<deployment>-app` | `monolith-app`；业务规则不进入启动应用 |
| 版本化跨进程契约 | `contracts/<capability>-contracts`；独立客户端按已有 `-client` 约定 | `workflow-contracts`；不为普通进程内调用自动新增 contracts 工程 |
| 隔离技术验证 | 沿用现有 PoC 区域及明确 `poc` 名称 | 正式业务不得依赖 PoC；不得将 PoC 名称用于正式能力 |

新上下文名称优先表达稳定业务概念，如 `inventory`，不以页面名、表名、HTTP 路由或实现框架命名业务上下文。不使用 `new`、`v2`、`temp`、`manager` 等作为长期模块区分方式；真实版本化协议另行明确兼容策略。

现有 `services`、`*-service` 名称继续沿用，以避免另建平行布局。未来若统一调整工程术语，必须在单独迁移中更新 POM、脚本、CI、文档、扫描与装配，不能只改目录。

## 4. Java 包命名

包段使用全小写英文，不含连字符、下划线或驼峰。多词业务概念采用稳定组合词；业务概念通常用单数，已有固定技术名如 `contracts` 保留。目录名和 Java 包名不要求逐字符一致。

| 用途 | 规则或既有映射 |
|---|---|
| 普通业务根包 | `com.appnexus.<context>`，例如 `com.appnexus.inventory` |
| 平台上下文根包 | `com.appnexus.platform.<context>`，例如 `com.appnexus.platform.organization` |
| 现有多词及能力映射 | `master-data-service` → `com.appnexus.masterdata`；`platform-service/business-object` → `com.appnexus.platform.businessobject`；`print-service` → `com.appnexus.printing`；`workflow-service` → `com.appnexus.workflow` |
| 普通服务职责包 | `api`、`application`、`domain`、`adapter`、`bootstrap`；按需要细分功能，如 `application.warehouse` |
| 平台业务职责包 | 公开根包、`port`、`internal.application.<feature>`、`internal.domain.<feature>` |
| 技术实现包 | 普通服务采用 `adapter.web`、`adapter.persistence`、`adapter.integration` 等；存储统一采用 `adapter.persistence`；历史 `adapter.jdbc` 随受影响完整用例迁移，不复制平行实现 |
| 测试包 | 默认对应生产包；仅在存在真实独立测试职责时增加测试包，并维护包说明 |

普通服务采用 `adapter` 单数，平台工程的聚合目录采用 `adapters` 复数，这是不同层次的固定约定。平台现有 `com.appnexus.platform.persistence`、`com.appnexus.platform.security` 技术根包按既有标准维护；新增内容按真实职责落位，不为名称统一平行复制实现。

禁止采用 `com.appnexus.services.…` 将构建目录照搬为业务包层级；禁止把 Maven 的 `-service` 后缀写进上下文根包。`application` 是用例层，`applications` 是部署工程目录，两者不得混用。

不使用 `common`、`utils`、`base`、`misc`、`impl` 作为绕过业务归属的收纳包；业务根包外不得再随意建立全局 `controller/service/mapper` 横向目录。`domain` 中禁止设置按数据库表或框架划分的 `mapper`、`entity` 等技术分层。已有存量命名不因此自动合规，也不要求在无关任务中批量改名。

`public` 关键字和类名中的 `Service` 不表示模块公开边界；公开范围按 api 或平台公开根包及明确 port 约束。新增包必须有准确的中文 `package-info.java`，并有架构检查覆盖实际生产类。

## 5. 新增及重命名前的必填记录

在任务设计或交付记录中补充以下字段，可与架构归属表合并：

| 能力分类 | 上下文与业务所有权 | 工程目录/artifactId | Java 根包及功能包 | 公开入口/允许依赖 | 部署应用 | 新增或改名原因 |
|---|---|---|---|---|---|---|
| 平台基础/对象元数据/通用支撑/业务 | 实际规则及表所有者 | 实际名称 | 实际包 | 实际边界 | 当前 monolith-app 或经设计的组合 | 现有模块不能承载的具体原因 |

检查现有同义能力和包后再新增，禁止仅为缩短目录把不同上下文合并。重命名必须核对 POM、Java 引用、组件扫描、配置绑定、反射、资源路径、脚本、CI、架构测试与文档，并运行受影响检查；保持历史 Flyway 校验和及既有安全、事务和公开协议。不得因改包逃出扫描而获得表面通过。

对象能力已按上述归属迁入平台；其他模块不因本次迁移宣称分层全部完成。

类型后缀、技术前缀、Controller/Mapper/仓储端口及实现的职责落位，强制执行[后端类型命名与分包规范](后端类型命名与分包规范.md)；存量位置不构成新增或修改代码的豁免。
