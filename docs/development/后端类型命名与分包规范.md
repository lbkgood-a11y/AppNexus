# 后端类型命名与分包规范

生效日期：2026-11-20。适用于全部自有后端正式、测试及 PoC 代码的新增、修改、重构和审查。人工与 AI 同等执行。本文统一类型命名和职责落位；业务所有权、依赖矩阵继续执行[架构与分包边界](架构与分包边界.md)及[后端工程标准](后端标准工程结构与AI生成约束.md)。

## 1. 先职责，后命名

每个类型先确定业务上下文、架构职责、业务功能及允许依赖，再确定名称和位置。Java 类型使用 UpperCamelCase，方法和变量使用 lowerCamelCase，包段使用小写英文；标识符使用明确业务词汇。禁止通过改名掩盖技术依赖、以调用者命名存储接口、复制历史混层或创建无职责转发层。

## 2. 类型及落位

| 职责 | 强制命名 | 普通服务位置 | 平台位置 |
|---|---|---|---|
| HTTP 入口 | `<业务职责>Controller` | `adapter.web.<feature>` | 对应 `app-api`、`platform-api`、`partner-api` 模块 |
| 公开业务用例 | `<业务职责>UseCase`，明确聚合职责可用 `<业务职责>Management` | `api.<feature>` | 上下文公开根包 |
| 应用用例实现 | `<业务职责>Service` | `application.<feature>` | `internal.application.<feature>` |
| 业务仓储输出端口 | `<业务对象>Repository` | `application.<feature>` | 上下文 `port` |
| 专用查询输出端口 | `<业务职责>Queries` | `application.<feature>` | 上下文 `port` |
| 仓储或查询持久化实现 | `MyBatis<端口职责>` 或 `Jdbc<端口职责>` | `adapter.persistence.<feature>` | persistence 模块的对应功能包 |
| MyBatis SQL 映射接口 | `<业务对象或存储职责>Mapper` | `adapter.persistence.<feature>` | persistence 模块的对应功能包 |
| 数据库存储模型 | `<业务对象>Po` | 持久化适配包 | 持久化适配包 |
| HTTP 输入、输出 | `<操作>Request`、`<业务职责>Response` | Web 适配包 | 对应 API 适配包 |
| 技术装配 | `<业务或技术职责>Configuration` | `bootstrap` | 对应技术适配器或部署装配包 |
| 集成桥接 | `<对侧能力><本侧职责>Adapter` | `adapter.integration.<feature>` | 对应集成职责的技术适配包 |

纯模型按真实职责命名为业务名、`Id`、`Rules` 等，不为简单模型虚构聚合、工厂或领域服务。用例稳定输入输出不使用 HTTP Request/Response 或数据库 Po 替代。内部类型同样按职责命名，不用 `Impl`、`Helper`、`Manager`、`Util` 掩盖责任。

`Repository` 表示业务存取契约，`Mapper` 表示 MyBatis SQL 映射，`Jdbc`/`MyBatis` 表示实现技术，三者不能互换。仓储端口不能移入持久化层；Mapper 不得承担权限决策、业务状态机或完整用例。无需业务仓储抽象的专用存储操作可使用有明确语义的输出端口，不强行把事务、发号或外部能力命名为 Repository。

禁止 `TaskManagementControllerSqlMapper`、`PersonnelServiceSqlMapper` 等绑定调用类的命名；应根据实际查询或写入职责命名。禁止把使用 MyBatis 的实现继续命名为 `Jdbc…`，也不能仅因接口访问数据库就将其称为 Repository。

## 3. 分包与构建边界

普通服务按 `api/application/domain/adapter/bootstrap` 分职责，再按功能细分；存储统一使用 `adapter.persistence.<feature>`，不并存同职责的 `jdbc`、`dao`、`repository` 平行包。已有 core/adapters 多模块保持构建隔离，Java 包仍按实际职责分离；混合模块不能成为把 Controller 放入存储或引擎包的理由。

平台业务模块仅保留公开根包、`port`、`internal.application`、`internal.domain`；Mapper、数据库实现和 PO 进入平台 persistence 适配器。普通业务 HTTP 按调用对象进入对应 API 模块；security 仅承载安全技术边界及认证协议、会话专用入口。业务 Controller 不进入领域、应用、存储或部署启动模块。

历史 `adapter.jdbc` 是待迁移位置，不是新增实现的长期豁免。受影响完整用例迁移时统一归入 persistence，不复制平行实现。物理 Maven 模块改名须同步父子 POM、依赖、启动脚本、CI 和产物路径；Java 包迁移与构建模块迁移分别核验，禁止以包迁移宣称模块职责已完成整改。

Controller 只调用公开用例；应用通过输出端口协调存储和事务；持久化实现负责固定 SQL、映射、锁及技术异常。跨上下文只调用公开契约。禁止在 Controller 直接注入 Mapper、访问 JDBC、调用存储实现或编排业务事务；禁止为了避免拆分而放宽公开边界。

## 4. 迁移与强制门禁

变更前提供“原类型/包 → 目标类型/包 → 职责 → 公开边界 → 调用方 → 验证”对照，检查同包可见性和循环依赖。同步 Java 引用、静态及通配导入、MyBatis namespace 和 statement 引用、资源路径、Mapper/组件扫描、Bean 名称、反射类名、序列化类型名、对象 responseType、测试、脚本及当前设计说明。历史验收记录保留当时事实，历史 Flyway 不修改。

保留 HTTP 路由、请求响应、错误码、可信主体、功能及数据权限、字段保护、审计和事务语义。按 D01–D12 复核受影响声明，类名改变涉及字符串绑定时必须同步；语义不变不擅自升级业务版本，说明无需迁移策略的依据。

每个自有源码包维护准确的中文 package-info.java。架构检查必须命中实际生产类型，按 Controller 注解/类型、MyBatis 注解及仓储实现依赖检查落位，不能只匹配正确包名而漏掉错放类型。源码盘点与依赖检查分别提供证据；文本扫描不能代替真实装配、数据库及正反向安全验证。

命名、落位、依赖或适用验证任一失败或未验证，必须在 docs/validation 中逐项记录并阻断交付。禁止扩大排除、缩小扫描、生成例外清单或仅移动文件宣称符合六边形架构。发布本规范不代表存量已全部整改，也不代表 CI 已全量自动保证。
