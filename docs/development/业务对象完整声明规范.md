# 业务对象完整声明规范

生效日期：2026-11-20。适用于每个功能的新增、修改、修复、重构和审查，人工开发与 AI 生成代码同等执行。

## 1. 每个功能必须有声明归属

每个功能必须在设计、编码和首次交付时明确所属业务对象及操作，并通过该对象唯一的 `BusinessObjects.Provider` 提供完整 `BusinessObjects.Descriptor`。已有对象上的功能复用并更新原声明，不为每个按钮、接口或页面创建重复对象；新增真实业务对象才新增 Provider。系统管理、自助、公开、查询、后台任务和无页面功能同样必须明确对象归属、管理域及准入类型，不能因没有业务表或行权限而省略声明。

纯导航、取消、未产生服务端副作用的草稿交互沿用既有非授权交互登记规则，仍须说明所属对象/页面和交互性质；不得为此虚构服务端操作。纯文档、构建或基础设施维护不虚构业务对象，但必须在交付记录说明所影响的对象契约或无业务功能变化的依据。

声明必须覆盖本规范全部检查项；“完整”是逐项确认适用性并接通实际执行，不是给每个对象强行开启所有能力。不适用项必须写明业务理由、契约缺省语义、对应入口及验证依据；禁止留空、遗漏或统一写“不涉及”。既有契约允许空集合、空绑定或 null，不代表新功能可以不评估、不说明或默认放行。存量对象本次新增或修改的功能必须补齐相关声明及执行，其他差距明确记录，不能宣称全仓已迁移。

## 2. 完整性检查清单

下列 D01–D12 每个功能均须逐项记录。代码可表达的元数据由唯一 Provider 声明；事务、部署及不适用理由等非契约字段在设计和交付记录中关联说明，不另造一套可写对象目录。

| 编号 | 必查内容 | 声明位置及完整性要求 |
|---|---|---|
| D01 | 对象身份与归属 | `Descriptor.objectType/nameZh/nameEn/module/version/category`；标识稳定唯一、名称中英文齐全、业务分类与模块归属准确；安全语义变化升级版本并迁移受影响策略 |
| D02 | 全量操作 | `Descriptor.operations`；覆盖查询、详情、创建、修改、删除、启停、提交、撤回、审批结果、打印、导出、批量及机器入口等实际存在的操作；逐项核对，未提供的操作不得虚假登记；`operationId=objectType.operationCode` |
| D03 | 入口、页面与交互 | 操作的页面、真实 HTTP 方法/路由、别名及 `interaction`；无页面、回调或后台入口明确调用方与可信身份；Controller 仅 `reference=true` 引用，接口权限遵守 `EndpointOperation` 唯一来源，前端绑定操作标识；非授权交互有受控登记 |
| D04 | 功能准入与管理域 | 操作权限及统一准入、`dataAccess.scope` 和实际管理域保持一致；明确租户、平台、自助或公开边界；匿名及机器身份不得伪造账号，不借用无关权限或以菜单显隐放行 |
| D05 | 行范围与主从资源 | `dataAccess.resources/operationScopes/dimensions`；主从资源、稳定资源键、中英文名、支持范围、条件类型与运算符齐全；仅引用本对象操作，列表/COUNT/详情/主从/写入及适用引用执行一致，可信租户谓词独立强制 |
| D06 | 字段保护 | `DataResource.fields/responseType`；逐项评估敏感字段、只读/脱敏/隐藏、自动响应绑定或显式执行方式，以及写入、集合替换和删除保护；业务事实及能力数据投影不得泄漏受保护原文 |
| D07 | 通用能力与协议 | `operations[].interaction` 及 `capabilities[]`；工作流、打印、消息及其他实际需要的能力逐项评估，声明契约编码/版本、触发来源、服务、完成方式、引用、用途和结果；能力不足先扩展公共模型和驱动器，不能只登记枚举或入口 |
| D08 | 数据契约与事实 | `Descriptor.fields` 与各 `Capability.fields/dataContract/dataVersion` 按各自用途声明；字段键、类型、必填、单位及缺省行为准确；`Capability.schema()` 派生数据契约，专业服务不重复维护字段副本；真实值由业务服务授权后重读，不来自客户端自报事实 |
| D09 | 编码 | `Descriptor.codingFields`；逐个需要发号的字段声明 `field/operationCode/maxLength`，说明手工或自动编码、规则关联、发号入口及失败行为；规则内容归编码服务，发号不替代保存时授权、唯一性和长度校验；无编码字段时明确不开放发号 |
| D10 | 统一运行接入 | 同一 `Provider.runtime()` 提供 `BusinessObjectRuntime`；核对实际需要的 read/execute、能力前置业务约束、审批记录及终态保存实现；公共执行器负责字段投影、绑定解析、专业能力分派及公共审批桥接，禁止逐对象重复专业 Provider 或接线；纯目录场景说明无执行端口的依据，不得伪装为已接通 |
| D11 | 配置、生命周期与事务 | 说明代码声明、平台启停、租户绑定、专业服务配置的所有权，及实际规则/流程发布版本/打印场景关联；覆盖状态前置条件、版本、锁、幂等、回调真实性、失败回滚、审计和契约迁移；能力声明不是任意编排授权 |
| D12 | 验收与变更一致性 | 声明→目录→配置→页面/API→运行端口→公共执行→业务事务逐项对照；提交真实正反向证据，覆盖适用的跨租户、无权限/无策略、撤权/过期、受限字段、版本冲突、重复及伪造回调、能力故障；未接通能力不展示配置或执行入口 |

## 3. 资源与配置唯一来源

- 业务契约由对象 Provider 发布；工作流和打印使用 `Operation.interaction.capabilities`，编码字段使用 `Descriptor.codingFields`，权限资源使用 `Descriptor.dataAccess.resources`，三者不得混用。
- 专业服务目录从统一声明派生。流程定义和发布、编码规则、打印模板与场景仍由对应专业服务拥有；平台启停及租户绑定引用已声明且实际支持的目标，不把业务正文存入配置目录。
- 同一对象只接入一次运行端口，不另建工作流业务 Provider、打印取数 Provider、私有权限目录或重复字段清单。模块间仅依赖公开契约。
- 不支持的消息、事件或调度驱动不能因为协议存在枚举就开放；新增能力须同时完成声明、公共驱动、配置接入和正反向验证。

具体授权规则执行[业务服务统一开发规范](业务服务统一开发规范.md)和[业务对象数据权限声明标准](业务对象数据权限声明标准.md)。本规范不放宽默认拒绝、租户隔离及字段保护要求。

## 4. 每次功能变更的声明同步复核

每次相关功能发生新增、修改、修复、重构、重命名、停用或删除，均必须检查对应声明是否随实际行为同步更新；即使未修改 Provider 文件，也不能跳过检查。共享组件、公共契约或执行器的变更须追踪所有受影响对象，不能只检查直接修改的模块。

以本次实际差异为起点，逐项对照 D01–D12，核对对象/操作身份、名称、页面和 API、权限与管理域、资源及字段、范围与条件、工作流/打印协议、编码字段、数据契约、运行端口和关联配置。删除或重命名时检查悬空引用、存量策略、租户绑定和已发布契约；安全语义或输入/结果语义变化按对应版本规则升级并完成必要迁移，不修改历史快照伪装兼容。

每次交付记录必须包含以下变更对照表，列出全部受影响对象及声明项；相关项仍须逐项完成 D01–D12，不用本表替代完整清单。

| 功能变更及实际差异位置 | 对象/操作 | 声明文件及检查项 | 变更前后语义 | 声明处理结论及依据 | 版本/迁移/引用影响 | 验证证据 |
|---|---|---|---|---|---|---|
| 填写实际变更 | 填写稳定标识 | 填写 Provider 及 D 编号 | 填写实际差异 | 已同步更新 / 已复核无需修改，并说明原因 | 填写处理结果或不需要的理由 | 填写最终差异及实际检查结果 |

“无需修改声明”必须证明原声明仍准确覆盖变更后的行为，不能仅以 Provider 无差异或编译成功作为依据。提交前及最终交付前均需复核；后续追加变更影响先前结论时必须补查并更新证据。发现实现与声明不同步、遗漏受影响对象、缺少复核依据或必要版本迁移，必须阻断交付。

## 5. 开发顺序与交付阻断

所有接入平台的业务对象均须执行[统一权限模型强制接入](业务服务统一开发规范.md#31-统一权限模型强制接入)，D04–D06、D10、D12 必须关联真实准入、范围/字段执行和正反向证据。唯一 Provider 或 Executor 的存在不能证明所有操作已受控；必须从实际入口反查，并分别记录遗漏声明、遗漏执行、绕过执行的检查结果。发现任一缺口或适用项未验证，必须阻断交付，不得以存量兼容或纯目录登记代替接入。

1. 设计前建立“功能—对象—操作—入口—能力—执行器—验证”对应关系，逐项评估 D01–D12。
2. 编码前完成契约设计；实现时同步更新唯一 Provider、真实运行入口、公共执行接入及必要迁移，不先上线后补声明。
3. 从实际路由、Controller、页面操作、回调、后台任务及业务用例反查声明，检查遗漏和重复，不能只从已有声明出发自证完整。
4. 在 `docs/validation/` 逐项记录 D01–D12：适用性及理由、声明文件/对象/操作、真实入口/执行位置、状态、命令或人工检查证据、未验证范围。状态沿用交付门禁的通过/失败/未验证/不适用。
5. 任一必需声明遗漏、重复、失真、缺少实际执行，或适用项失败/未验证，均不得标记完成交付；执行[功能交付门禁要求](功能交付门禁要求.md)。

本规范是强制人工及 AI 检查要求，不表示当前启动校验或 CI 已自动覆盖 D01–D12，也不代表存量对象已全部符合。
